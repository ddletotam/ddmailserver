# Контракт поведения iOS / iPadOS / macOS-клиента

Договорённости о поведении и устройстве Apple-клиента ddmail. Пишется **до кода**
и живёт по тем же правилам, что `desktop-behavior-contract.md` и
`android-behavior-contract.md`: **меняешь поведение — правишь этот файл в том же
коммите.** Ссылки — на типы и функции, не на номера строк.

**Основа — Android-контракт.** Семантика (что такое диалог, папки, спам, ветки
отправки, календарь, напоминания) у мобильных клиентов одна, и здесь она не
переписывается: раздел, где сказано «как Android §N», означает «то же правило,
слово в слово». Этот файл описывает только **как** — механизмы Apple — и места,
где платформа вынуждает поступить иначе. Такие места помечены **Отличие от
Android** с причиной.

Статус разделов: **решено** — делаем так; **проверить на устройстве** — решение
держится на допущении, которое подтверждаем живым iPhone/iPad; **открыто** — §12.

## 0. Принципы

- **Нативно, без компромиссов** (как Android §0). Swift + SwiftUI, механизмы
  платформы: URLSession, Keychain, APNs, BackgroundTasks, UserNotifications,
  WKWebView, QuickLook, String Catalog. Rust-ядро через FFI, KMP, Flutter,
  Catalyst — не используются.
- **Один код — три системы.** Одно приложение SwiftUI, собранное нативно под
  iOS, iPadOS и macOS (не Catalyst и не «iPad-приложение на Маке»).
  Платформенные ветки (`#if os(macOS)`) — только там, где механизм разный:
  меню и горячие клавиши Mac, сохранение файлов, фоновая работа.
- **На Маке клиент заменит Slint-десктоп** (решение пользователя 2026-11-11),
  когда догонит его по функциям (§10) и будет выглядеть лучше. До этого Slint
  остаётся основным клиентом Mac, Apple-клиент на Маке — сборка для проверки.
- **Сервер — источник правды о смысле** (как Android §0). Где десктопный или
  Android-контракт говорит **что**, клиент обязан совпадать.
- **Иконки вместо надписей** (правило №1 мобильных клиентов, Android §0) —
  SF Symbols, у каждой кнопки-иконки `accessibilityLabel`. На Маке в меню
  приложения — текст (так устроены меню macOS), в панели окна — иконки.
- **Выглядеть как приложение Apple.** Системные компоненты (`List`,
  `NavigationSplitView`, `.toolbar`, `Menu`, `.sheet`, `.swipeActions`,
  материалы, Dynamic Type, тёмная тема) — по умолчанию. Свой компонент —
  только там, где системного нет (лента беседы, шкала календаря) или где
  системный ставит компоновку, отличную от десктопа (первая строка раздела,
  поле поиска с выпадашкой, табы папок — `docs/mobile-layout.md`), и он
  повторяет метрики и анимации системных.
- **Компоновка = компоновка десктопа** (решение владельца 2026-11-13,
  `docs/mobile-layout.md`): где этот файл и `mobile-layout.md` расходятся —
  прав `mobile-layout.md`.
- **Скорость разработки не приоритет.** Решения — по качеству результата.
- **Наблюдаемое читается в теле экрана.** Замыкания `ForEach`,
  `safeAreaInset`, `overlay`, `Binding(get:)` и подобных SwiftUI вызывает
  лениво, вне отслеживания `@Observable`: прочитанное только в них экран не
  перерисует. Значения модели берутся в `body` в локальные константы и
  передаются внутрь (так чинили цвета строк, табы папок и вопрос о загрузке,
  который на Маке не появлялся, 2026-11-11).
- **Мак: колонка беседы.** На macOS 27 `NavigationSplitView` считал отступ
  колонки беседы с лишней шириной боковой панели разделов (замер при
  `TabView(.sidebarAdaptable)`: колонка с x=770, лента — с 914). Отступ
  берётся из измерения правого края колонки списка
  (`MailView.detailColumn`), а не из безопасной области; без боковой панели
  разделов он нулевой, измерение оставлено как страховка.

## 1. Платформа и сборка — решено

- **Код:** `mobile/ios/` в этом репозитории.
- **Минимальные версии: iOS / iPadOS / macOS 27** — те, что стоят на устройствах
  пользователя; совместимость со старыми не нужна, свежий SwiftUI используется
  без обходов. Если какое-то из устройств не получит 27 — опускаемся до 26.
- **Язык:** Swift 6, строгая проверка конкурентности (`complete`).
- **Устройства проверки:** iPhone 15 (iPhone15,4, iOS 27.0.1), iPad Pro 13″, MacBook
  (Apple Silicon). Симуляторы — iPhone 18 Pro и iPad Pro 13-inch (M5) на iOS 27.2.
- **Bundle ID:** `ru.letotam.ddmail` — как пакет Android.
- **Проект Xcode генерируется** из `mobile/ios/project.yml` (XcodeGen). Сам
  `.xcodeproj` в git не хранится: его правка руками и конфликты слияния —
  главный источник поломок iOS-проектов.
- **Логика — в локальном Swift-пакете** `mobile/ios/DDMailKit`, приложение —
  тонкая оболочка из экранов. Пакет собирается и тестируется `swift test` на
  Маке без симулятора.

### Модули DDMailKit

| Модуль | Что внутри | Аналог Android |
|---|---|---|
| `DDMailAPI` | HTTP-клиент `/api/desktop/v1` (URLSession, `Codable`), WebSocket, refresh токена | `:core:api` |
| `DDMailStore` | кэш на SQLite (GRDB): схема, миграции, запросы | `:core:db` |
| `DDMailSync` | движок синхронизации, доменные типы, папки диалогов, цвета айдентик | `:core:sync` |
| `DDMailAuth` | вход, токен в Keychain, автонастройка | `:core:auth` |
| `DDMailCalendar` | развёртка повторов, планировщик напоминаний | `Recurrence`, `ReminderPlanner` |
| `DDMailMIME` | разбор и сборка писем: кодировки, QP/base64, RFC 2047/2231, адреса, даты, структура частей, `cid:` | — |
| `DDMailNet` | соединение с почтовым сервером: TLS сразу (`NWConnection`) и STARTTLS (`URLSessionStreamTask`), построчное чтение с таймаутами | — |
| `DDMailIMAP` | кодек IMAP (литералы, ENVELOPE, `VANISHED`, modified UTF-7) и клиент: вход, SELECT с QRESYNC/CONDSTORE, FETCH, STORE, MOVE, APPEND, IDLE | — |
| `DDMailSMTP` | отправка: STARTTLS обязателен на 587/25/2525, AUTH PLAIN/LOGIN, точка-экранирование | — |
| `DDMailDAV` | CalDAV/CardDAV внешних учёток: обнаружение, iCalendar и vCard, общий календарь и книга с ddmail | — |

Цели Xcode: приложение (iOS + macOS) и Notification Service Extension
`DDMailNotificationService` (iOS + macOS, §7).

- **Протоколы почты — свои модули, без пакетов.** IMAP-кодек, SMTP и MIME
  написаны в `DDMailKit` (решение 2026-11-12): swift-nio-imap тянет цепочку
  пакетов, а клоны с GitHub на Маке рвутся (см. зеркала ниже). Сеть —
  платформы: неявный TLS — Network.framework; STARTTLS — `URLSessionStreamTask`
  (`startSecureConnection`), потому что Network.framework не включает TLS на
  уже открытом соединении. Доверие в обоих — системное хранилище, TLS 1.2+.
  Данные, пришедшие до рукопожатия STARTTLS, рвут соединение (защита от
  внедрения открытым текстом). Тесты — на записанных сессиях серверов; живая
  проверка `LiveIMAPTests` — по учётке из окружения.
- **Кэш — GRDB, не SwiftData.** Нужны явные миграции, версия схемы, точный
  контроль запросов и один писатель — то, что Android получает от Room.
  SwiftData скрывает SQL и миграции и менялась от версии к версии; ради
  «системности» платить предсказуемостью кэша не стоит. GRDB — единственная
  сторонняя зависимость логики; добавить ещё одну — решение с причиной в этом
  файле.
- **Тесты — Swift Testing.** Порты из Android переносятся **с теми же
  тестовыми векторами** (`IdentityColors`, `DialogFolders`, `Recurrence`,
  `ReminderPlanner`): смысл общий, совпадение проверяется тестами, а не на глаз.

### Сборка и установка — удалённо с Мака

Разработка идёт на станции (WSL), Мак — только сборочный узел; за ним не
работают. Код уезжает на Мак `rsync` по SSH в одну сторону (Мак не в Syncthing
и не в git: иначе получим два источника правды):

```bash
mobile/ios/scripts/mac.sh test             # swift test пакета DDMailKit
mobile/ios/scripts/mac.sh build            # rsync → xcodegen → xcodebuild (симулятор iOS и macOS)
mobile/ios/scripts/mac.sh run iphone|ipad  # поставить в симулятор, запустить, скриншот сюда
mobile/ios/scripts/mac.sh uitest           # сквозные UI-тесты на настоящем сервере, скриншоты шагов
mobile/ios/scripts/mac.sh device iphone    # собрать с подписью и поставить на устройство (devicectl)
```

- Хост — алиас `mac` в `~/.ssh/config` станции. Каталог на Маке —
  `~/build/ddmail-ios/` (рабочая копия) и стандартный DerivedData Xcode — вне
  синкаемого дерева, как требует правило workspace.
- Скриншоты и видео симулятора — `xcrun simctl io`, с устройства — по
  `devicectl`; файл забирается на станцию.
- Устройства спарены с Маком один раз кабелем, дальше установка по сети.
- **Подпись в SSH-сессии:** связка ключей login в сессии SSH заблокирована
  («User interaction is not allowed»); скрипт разблокирует её перед
  `xcodebuild`. **Секреты станции — `~/.config/ddmail-ios/`** (вне git, как
  `~/.config/ddmail-android`): `keychain-password` — пароль входа на Мак,
  `test.env` — учётка для `uitest`, `team` — команда подписи, `asc.env` и
  ключ — App Store Connect API, `apns.env` и ключ `.p8` — APNs для живой
  проверки push. В `project.yml` команды нет.
- **XcodeGen** — релизная сборка в `~/.local/xcodegen` на Маке, вызывается по
  полному пути: через симлинк он не находит свои пресеты настроек, и проект
  выходит без `SUPPORTED_PLATFORMS`, `ONLY_ACTIVE_ARCH` и прочих умолчаний.
- **Пакеты SwiftPM — через локальные зеркала на Маке** (`~/src-mirrors`):
  полный клон GRDB (с историей и подмодулем `SQLiteCustom`) через туннель
  обрывается, поверхностный — проходит. `mac.sh` прописывает зеркала и для
  `swift test`, и для `xcodebuild` (`mirrors.json` пакета и рабочей области
  проекта), подмодуль перенаправлен `git config url.<зеркало>.insteadOf`.
  Пакеты `xcodebuild` лежат в постоянном `~/build/ddmail/SourcePackages`.
  Новая зависимость — новое зеркало (поверхностный клон нужного тега).
- **Мак — та же цель и те же UI-тесты** (`mac.sh uitest mac`): режим
  автоматизации включён на Маке (`automationmodetool
  enable-automationmode-without-authentication`), XCUITest на macOS снимает
  весь экран — так Мак-версию видно без доступа к экрану по SSH. Приложение
  подписано командой: связке ключей с защитой данных нужно право
  `keychain-access-groups` (без него на Маке `errSecMissingEntitlement`; оно
  же потом общее с NSE). `App/DDMail.entitlements` генерирует XcodeGen.
- **UI-тесты** (`UITests/`, XCUITest) — сквозные сценарии в симуляторе на
  настоящем сервере; без учётки из окружения пропускаются. Пароль вводится
  вставкой из буфера: программная клавиатура симулятора iOS 27.2 теряет цифры
  и знаки в защищённом поле.
- **Версия** — `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` в `project.yml`;
  бампается при любой правке клиента, как у десктопа и Android.
- **Аккаунт разработчика** — платный Apple Developer Program (команда
  `F2MHZQSN5H`, с 2026-11-12): push, App Group, TestFlight. Кэш Xcode на Маке
  может помнить только Personal Team — команда подписи берётся из
  `~/.config/ddmail-ios/team` станции (`DDMAIL_TEAM`). Профили с push и App
  Group Xcode заводит сам (`-allowProvisioningUpdates`) по ключу App Store
  Connect API из `~/.config/ddmail-ios/asc.env`: `mac.sh` кладёт его на Мак
  во временный каталог (700, файл 600) только на время сборки и удаляет.

## 2. API и сессия — решено

Как Android §2, с такими механизмами:

- **Токен — в Keychain**, класс доступа `AfterFirstUnlockThisDeviceOnly`: фон
  (push, BGTask) должен уметь сделать refresh при заблокированном экране, а
  на другое устройство через резервную копию токен уезжать не должен. Группа
  доступа Keychain общая с Notification Service Extension. Пароль не хранится
  нигде.
- **Классификация ошибок** — как Android §2: 401 после неудачного refresh →
  «нужен вход»; 403 — ошибка действия с текстом сервера; отказ самого
  `/auth/refresh` любым кодом → «нужен вход»; таймаут, 5xx, обрыв — временное,
  с бэкоффом.
- **«Нужен вход»** — несмываемая плашка над содержимым с кнопкой «Войти», кэш
  виден.
- **WebSocket** — `URLSessionWebSocketTask`, токен **только заголовком**
  `Authorization: Bearer`. **Отличие от Android:** `?token=` в URL не шлётся
  вовсе — переходный период ему не нужен, клиент новый, а сервер заголовок
  уже принимает.

## 3. Подключение (первый запуск) — решено

Как Android §3 (email → `/.well-known/ddmail` на `mail.<домен>`, `<домен>`,
MX-хостах → вход или ручной адрес), механизмы:

- **MX — через системный резолвер** `DNSServiceQueryRecord`
  (`kDNSServiceType_MX`, `dns_sd`): работают внутренние домены и
  корпоративный DNS, как у Android (`DnsResolver`) и десктопа.
- **Только https.** Доверие — системное хранилище, в том числе корневые CA из
  установленных профилей, если пользователь включил им полное доверие
  (Настройки → Основные → Об этом устройстве → Доверие сертификатам). Своей
  проверки сертификатов клиент не делает.
- Пароль при поиске никуда не уходит. Поле пароля — `textContentType(.password)`,
  связка ключей iCloud может его подставить.

## 4. Синхронизация — решено

Модель — как Android §4 (беседы с водяным знаком `server_now_ms`, журнал
`/changes`, версия формата id в `meta`, тела заранее от свежей беседы к
старой, пустое тело перезапрашивается, мутации оптимистично с откатом).

- **Один писатель кэша:** движок синхронизации — `actor`; все записи в GRDB
  идут через него. Фон и push-расширение не синхронизируют одновременно:
  оба берут межпроцессную блокировку (`ProcessLock.sync`, `flock` файла в
  App Group, держится секунды); экран её не берёт — его проход и проход
  расширения идемпотентны, а держать блокировку файла общего контейнера при
  уходе в фон iOS не даёт (0xdead10cc). Проход отменяется вместе с
  вызывающим (бюджет расширения, истечение фоновой задачи).
- **«Загружать письма заранее?»** — тот же вопрос с тремя ответами и без
  ответа по умолчанию. «Только по Wi-Fi» — запросы докачки с
  `allowsExpensiveNetworkAccess = false` и `allowsConstrainedNetworkAccess =
  false`: система сама не пускает их через сотовую сеть, точку доступа и
  режим экономии трафика. Открытие беседы качает её тела по требованию
  всегда.
- **Когда синхронизируемся:** при выходе приложения на экран; по событию WS;
  по push (§7); `BGAppRefreshTask` — страховка от потерянного push (время
  выбирает iOS, обычно реже, чем раз в 15 минут Android). Докачка тел в фоне —
  `BGProcessingTask` (с сетью; «Только по Wi-Fi» — без дорогой сети).
- **Mac:** приложение живёт и после закрытия окна (как десктоп с треем), WS
  держится, пока оно запущено; BGTask на Маке нет.

## 5. Почта — решено

Всё из Android §5 переносится без изменений смысла: диалог = набор адресов,
роли, табы папок над списком (без «Все»), ветки отправки, optimistic send,
правила уведомлений, спам («В спам» с ответами «Адрес» / «Домен»; отдельный список, не зазывает, не ходит в сеть,
картинки только по плашке на письмо), скрытые папки, `auto_read` исполняет
только десктоп, локальный поиск, цвет строки по группе айдентики, аватарки,
картинки по отправителю, свои имена и аватарки диалогов с сервера, «В папку» /
«Убрать из папки» одной записью документа папок, склеек нет. Порт `folders.rs`
— `DialogFolders.swift` с тестами Android.

Механизмы:

- **Поиск** — поле в первой строке списка, справа от бургера, и выпадашка
  поверх списка (`MailSearch`, `SearchDropdown`; десктоп §4 «Поиск»); сам
  список поиском не фильтруется. Секции по порядку:
  - **«Написать по адресу …»** — строка похожа на адрес (`parseEmailLike`,
    как `parse_email_like` десктопа): касание или Return открывает новую
    беседу с этим адресатом (`MailModel.startNew`, десктоп
    `enter_compose_mode`) — строка «Новая беседа» над диалогами, справа
    пустая лента с композером в фокусе; письмо уходит веткой «новое»
    (`ComposeModel.sendNew`), пузырь-заглушка сразу, настоящая беседа
    открывается, как только придёт синком (`sentTarget`). Это **единственный
    путь к новому письму**: кнопки «Написать», FAB, карандаша нет;
  - **«Диалоги»** — локально на каждое нажатие (`searchConversationHits`):
    имя, адрес любого участника, тема; вторая строка — что совпало; спама
    нет; открытие — переходом в папку диалога;
  - **«Контакты»** — адресная книга (`ContactsModel`, грузится для поиска и до
    захода в «Контакты»); адреса собеседников найденных диалогов не
    повторяются; касание — беседа с этим адресом (свежая есть — она, нет —
    новая, `MailModel.write`);
  - **«Сообщения»** — серверный поиск ddmail-учёток (`GET /search`,
    `SessionAPI.searchMessages`) с паузой 300 мс; у IMAP-учёток его нет.
    Касание — беседа, в которой лежит письмо (по id письма или Message-ID).

  Сравнение без учёта регистра и диакритики средствами Foundation
  (`localizedStandardContains` / `folding`), кириллица складывается
  правильно. Esc и «⊗» — закрыть и стереть.
- **Множественный выбор** — пункт «Выбрать» меню строки (долгое нажатие,
  правый клик), дальше системный режим правки `List` (`EditMode` на
  iPhone/iPad, выбор Cmd/Shift-кликом на Маке); первая строка на время выбора
  — «✕ Выбрано: N · Выбрать все», действия — панелью под списком. Состав действий и подтверждение удаления — как Android §5.
- **Свайпы** (`.swipeActions`) — как предложение Android §11: вправо
  «Прочитано/Непрочитано», влево «В папку…»; удаления и спама свайпом нет.
  На Маке свайпы трекпадом работают так же, плюс контекстное меню по правому
  клику с теми же действиями.
- **Папки — меню полосы табов и настройки** (десктоп §4 «Папки диалогов»,
  §5г). Долгое нажатие (Мак — правый клик) по табу: «Все прочитаны»,
  «Настроить…», «Удалить» (подтверждение — подменю «Удалить «…» — диалоги
  вернутся во «Входящие»»); по табу и пустому месту полосы — «Новая папка»
  (создаёт «Папка N» и сразу открывает её настройку) и «Показать скрытые (N)»
  / «Не показывать скрытые» (`MailModel.showHidden`, на сессию; таб скрытой —
  бледнее). У «← Входящие» и «Спама» — только общие пункты. Папок нет —
  полосы нет; все скрыты — полоса есть, пустая, ради этого меню.
  Настройка папки (`FolderEditorView`, окном из меню или из «Настройки →
  Папки»): имя, значок (до 4 символов, `clipFolderIcon`), «Получено на» —
  переключатели своих адресов всех учёток, «Домены» — текстом через запятую
  (`splitFolderList`), «Диалоги: все / 1:1 / группы», «Не показывать в
  списке», «Забыть ручные назначения», «Удалить папку». Кнопки «Сохранить»
  нет: правка уходит через 800 мс после последнего изменения и при уходе с
  экрана; поля при этом не пересоздаются. «Настройки → Папки»
  (`FoldersSettingsView`): «Показывать папки» — выключатель устройства
  (`settings.foldersOn`; выключено — в документе для списка остаются только
  системные папки, «Спам» — таб), список папок с переходом в настройку,
  перестановкой (порядок = приоритет правил) и удалением с подтверждением
  («на всех устройствах», если папки на сервере). Хранение — как раньше:
  документ ddmail-учётки (`/api/desktop/v1/dialog-folders`), без неё —
  локальный (`LocalDialogFolders`). Любая правка — замыкание над документом
  (`DialogFolderSource.editFolders`): при `409` она повторяется поверх
  свежего чужого документа, чужая правка не затирается.
- **Композер: форматирование** (десктоп §3а). Строка ввода — системный
  `TextEditor` над `AttributedString` (iOS/macOS 26+), без своей строки
  кнопок: на iPhone/iPad жирный, курсив, подчёркнутый — системным меню
  выделения («Формат»), с клавиатурой ⌘B/⌘I/⌘U умеет само поле; на Маке —
  меню приложения «Формат» (⌘B/⌘I/⌘U). Ссылка — ⌘K или «+» → «Ссылка из
  буфера»: адрес из буфера обмена (только http, https, mailto) — на
  выделение, без выделения вставляется сам адрес. Адреса в тексте — ссылками
  при сериализации (автоссылки). Картинки — «+» → «Картинка из буфера» и
  снимки из «Фото» (HEIC — в JPEG; видео — вложением): своим блоком под
  текстом, уходят inline-частями с `Content-ID`, HTML ссылается `cid:`.
  Тело — две версии (`RichText`): `text/plain` и `text/html` (`<div>`-абзацы,
  пустой — `<div><br></div>`, `<b>/<i>/<u>/<a>`); без форматирования HTML
  строится из текста, как раньше. Прочие атрибуты (кегль, цвет) в письмо не
  уходят. Сервер ddmail принимает это в `/send` как десктоп (`html`,
  `attachments[].content_id`); IMAP-учётки собирают письмо `MIMEBuilder`
  (`multipart/related`). Пересылка (окно) — по-прежнему простым текстом.
- **Optimistic send** (десктоп §2): пузырь-заглушка сразу и с тем же HTML,
  что уходит (картинки — `data:`-URI); «✓ Отправлено» — плашкой над
  композером ~2 с; ошибка — заглушка убирается, текст с форматированием
  возвращается в пустой композер, причина — строкой над ним. После отправки
  синк учётки — сразу и через 2.5 → 7 → 15 → 30 → 60 с. Новое письмо:
  беседу ждёт `SentTarget` — её id, посчитанный по тому же правилу, что
  сервер и `ConversationBuilder` (набор From+To+Cc, свои адреса учётки слева
  от `|`); запасной признак — набор собеседников равен адресатам. Пришла —
  «Новая беседа» сменяется ею (если пользователь не ушёл в другую), а
  заглушка переезжает в неё (`ComposeModel.carriedStubs` →
  `ConversationModel.carry`), пока письмо не пришло: беседа с этим адресом
  могла быть и раньше, тогда переход случается до прихода письма. Список
  прокручивается к открытой строке (`ScrollViewReader`): новая строка встаёт
  сверху, а `List` держит позицию по прежней первой — без прокрутки она
  оказывалась бы выше края (так «пропадала» беседа на Android).
  Прежняя сверка «собеседники == адресаты» не находила письмо на свой же
  другой адрес: у такой беседы собеседник — отправитель (`…|self`).
  **«Отправлено» = сервер принял в очередь**, не «доставлено». С 2026-11-13
  сервер кладёт копию в «Отправленные» **в момент приёма**, а не после
  доставки (десктоп §1): беседа есть сразу, даже если письмо висит в очереди
  (как письмо владельца на домен без MX, чей хост молчит на 25-м порту), и
  приходит WS `message_sent` с `rfc_message_id`. Подсказки `awaitingDelivery`
  («Сервер принял письмо, но ещё не доставил…») больше нет (0.0.7). Ответ
  `/send` несёт `rfc_message_id` (`SendReceipt`): `SentTarget` ждёт беседу и
  по нему — беседа, в ссылках которой есть этот Message-ID, та самая, даже
  если id беседы посчитан иначе, чем у сервера; проверка цели — и после
  каждого синка учётки (`MailModel.sync(only:)`), не только при смене кэша.
- **Статус доставки (0.0.7, десктоп §1).** Поля сервера: в теле письма
  (`/conversations/messages`) `delivery_status` (`""` — неизвестно, считать
  доставленным; `pending`, `delivered`, `failed`), `delivery_reason`,
  `delivery_error` (причина словами на языке пользователя),
  `delivery_failed` (кому не доставлено); в ссылке письма в `/conversations`
  — `delivery_status`, у строки беседы — `last_delivery_status`
  (`MessageBody`, `MessageRef`, `ConversationDTO`, `DeliveryState`).
  - **Кэш** (миграция GRDB `v3-delivery`): столбцы
    `conversations.lastDeliveryStatus` и `conversation_messages.deliveryStatus`;
    тело хранит поля в своём JSON. Миграция стирает `<учётка>/conv_full_ts` —
    следующий синк полный, иначе статусы старых бесед дельта не принесла бы.
  - **Пузырь** рисует общий документ ленты (договорённость с Android: JS и
    CSS — за ним). Клиент кладёт в каждое письмо порции (`FeedBatch.Message`)
    поле `delivery: {status, error, failed}` из тела; в журнале
    (`category: web`) — строка `feed …: uid N delivery=…` на каждое своё
    письмо со статусом. Меню пузыря (нативное) под заголовком пишет «Не
    доставлено — адреса: причина» или «Отправляется…».
  - **Строка беседы:** `failed` — красный `exclamationmark.circle.fill` у
    времени, `pending` — `clock` (`DeliveryMark`); на открытой (зелёной)
    строке — белым. Остальное — ничего.
  - **На лету.** WS `delivery_status` (`ServerEvent`, `LiveUpdates`): статус
    сразу ложится в кэш (`SyncEngine.applyDelivery` → ссылка, тело, строка,
    если письмо в беседе последнее по uid), затем обычный синк. Без сокета
    статус приносит дельта: ссылка с новым статусом делает закэшированное
    тело устаревшим (`SyncEngine.deliveryStale`), оно перезапрашивается (нет
    связи — показывается старое). Открытая беседа сравнивает статусы ссылок
    (`FeedWindow.redelivered`) и перерисовывает показанные пузыри на месте:
    `ddm.update(batch)`, если документ его умеет (письма с теми же uid
    заменяются), иначе `ddm.delivery(uid, delivery)`, иначе — `ddm.set` всем
    окном (`FeedBatch.updateScript`).
  - Отказ приходит ещё и письмом от `MAILER-DAEMON` во «Входящие» — обычной
    беседой.
  - **IMAP-учётка:** статуса у её писем нет (пусто = доставлено): SMTP
    провайдера принял — письмо доставлено (`SendReceipt` с `delivered`).
    Ошибка SMTP — заглушка убирается, текст возвращается, строка над
    композером красным «Не доставлено: причина» (у ddmail отказ `/send` —
    «Не отправлено: …»: сервер письмо не принял).
- **Вложения:** касание — просмотр QuickLook (`.quickLookPreview`); долгое
  нажатие — «Открыть», «Поделиться», «Сохранить в Файлы» (`fileExporter`).
  Mac: «Сохранить в Загрузки» и открыть программой по умолчанию.

## 6. Раскладка — решено

Источник — `docs/mobile-layout.md` (компоновка = компоновка десктопа). Здесь —
как это сделано на Apple.

Раскладка — по **классу ширины окна** (`horizontalSizeClass` и ширина
контейнера), не по модели устройства: так она работает в Split View, Slide
Over, Stage Manager на iPad и в окне любого размера на Маке.

| Где | Раскладка |
|---|---|
| iPhone (compact), узкое окно iPad | колонка почты на весь экран; беседа — поверх, «‹» и свайп от края назад |
| iPad / Mac, широкое окно | `NavigationSplitView` из двух колонок, всегда обе (`columnVisibility .all`, `.balanced`, без кнопки панели): слева колонка почты, справа беседа |

- **Колонка почты сверху вниз, ничего больше:** строка «бургер + круглое
  поле поиска на всю ширину» (`SectionBar`, `MailSearchField`), полоса табов
  папок (`FolderTabs`), диалоги. Над первой строкой нет ни заголовка «Почта»,
  ни large title, ни кнопок панели (системная панель навигации у корня
  раздела скрыта — `sectionRoot()`; на Маке у окна убраны заголовок и
  кнопка боковой панели).
- **Табы папок — как у десктопа:** текст, выбранный — зелёный с
  подчёркиванием, счётчик у выбранного зелёный, у остальных серый; пока
  выбрана папка — первым «← Входящие» со счётчиком инбокса. **«Спам» — таб
  этой полосы** всегда (системная папка, последней, без счётчика;
  `buildMailList`), пункта «Спам» в меню нет.
- **Разделы — только бургер** (`BurgerMenu`, десктоп `view-menu-open`):
  системное меню поверх раздела «Почта, Календарь, Контакты, Задачи,
  Настройки», текущий отмечен галочкой. Бургер — в левом верхнем углу первой
  строки **каждого** раздела. Таб-бара, бокового rail'а, боковой колонки
  разделов (`TabView(.sidebarAdaptable)`) нет. Смена раздела — замена
  содержимого окна; состояние разделов живёт в моделях рабочего
  пространства.
  - Календарь: бургер, ‹ Сегодня ›, заголовок периода, (iPad/Mac —
    Месяц/Неделя/День), «+». На iPhone ‹ › листают ленту месяцев. Список
    календарей — «Настройки → Календари», как у десктопа.
  - Контакты: бургер, «Контакты», «+»; ниже поле «Поиск контактов»; ниже список.
  - Задачи: бургер, «Задачи», «Показать выполненные».
- **«Настройки»** — пункт бургера, окно поверх (как модалка десктопа). В них
  учётки и «Добавить учётку», загрузка заранее, уведомления, календари.
- **Смена раскладки не теряет контекст:** открытая беседа, черновик,
  выбранный таб — в модели сцены и `@SceneStorage`.
- **Mac — несколько окон** (`WindowGroup`): беседу можно открыть отдельным
  окном (меню строки «Открыть в новом окне»). Меню приложения и горячие
  клавиши ведут туда же, куда бургер и поиск: ⌘N «Новое письмо» — фокус в
  поле поиска (адрес вводится там же), ⌘R ответить, ⇧⌘F переслать, ⌘⌫
  удалить, ⇧⌘N проверить почту, ⌘1…⌘4 разделы, ⌘, настройки.
- **Клавиатура на iPad** — те же горячие клавиши, что на Маке
  (`.keyboardShortcut`).

## 7. Push и фон — решено, доставку на устройстве проверить

- **На экране** — WebSocket; события как Android §7 запускают синк.
- **В фоне — APNs.** Постоянного соединения нет (iOS его и не даёт).
- **Push не несёт персональных данных** (152-ФЗ: APNs — серверы Apple за
  рубежом, это трансграничная передача третьему лицу). В push — только факт
  «есть изменения». Отправитель, тема, адреса не кладутся **никогда**.
- **Механизм — видимый push + Notification Service Extension.**
  **Отличие от Android:** «тихий» push (`content-available`) iOS
  придерживает по своему усмотрению и не доставляет вовсе, если приложение
  смахнули из переключателя — на нём уведомления не построить. Поэтому сервер
  шлёт видимый push с обезличенным текстом («Новые письма») и
  `mutable-content: 1`; расширение просыпается до показа (до ~30 с), делает
  дельта-синк через общий кэш в App Group и **заменяет текст** на настоящий
  (отправитель, тема) из своего кэша — данные на телефон приходят по нашему
  каналу, а не через Apple.

### 7.1. Сервер (сделано 2026-11-12)

- **Регистрация — одна на все платформы:** `POST /api/desktop/v1/push/token`
  под JWT, тело `{"kind":"apns|hms|fcm","token":…,"environment":"sandbox|production","topic":"ru.letotam.ddmail"}`
  (окружение — только у APNs). Идемпотентна: повтор обновляет строку. Ответ
  `{"kind","delivery"}` — настроена ли у сервера доставка этой службой (без
  ключа токен хранится, push не идут). `DELETE` того же пути (`{"kind","token"}`
  или `?kind=&token=`) — выход из учётки на устройстве; нет такого — тоже 200.
  Токен APNs — hex, хранится в нижнем регистре; у HMS/FCM — base64url.
- **Таблица** `push_tokens` (миграция 055): пользователь, служба, токен,
  окружение APNs, topic, `created_at`/`updated_at`/`last_sent_at`. Ключ —
  (пользователь, служба, токен): две ddmail-учётки одного сервера на одном
  телефоне — две строки. Больше 20 устройств у пользователя — вытесняются
  давно не обновлявшиеся.
- **Когда шлётся** (`internal/push`, `Dispatcher` на `notify.Hub`): только на
  настоящее новое входящее — событие `new_message` с id письма (локальная
  доставка, синк внешних ящиков, письмо о сбое календаря; спам их не
  публикует). Возврат из спама руками (`new_message` без id) и прочие события
  push не будят. **Коалесинг:** не больше одного push пользователю за 10 с —
  первое письмо будит сразу, пачка в окне — одним push в его конце.
- **APNs** (`push.APNs`): HTTP/2, token-based auth — JWT ES256 ключом `.p8`
  (`kid` — key id, `iss` — team id), токен провайдера кэшируется на 50 минут
  (на `ExpiredProviderToken` — перевыпуск и один повтор). Заголовки:
  `apns-push-type: alert`, `apns-topic` = bundle id, `apns-priority: 10`,
  `apns-expiration` — сутки. Без `apns-collapse-id`: следующий push заменил бы
  уведомление о другой беседе. Окружение — по токену (`sandbox` →
  `api.sandbox.push.apple.com`). Payload — ровно
  `{"aps":{"alert":{"title":"ddmail","body":"Новые письма"},"mutable-content":1,"sound":"default","thread-id":"mail"}}`.
  Ответы `410`, `BadDeviceToken`, `Unregistered` — токен удаляется у всех
  пользователей; прочие ошибки — в журнал, токен остаётся.
- **Конфиг** `push.apns` в `config.yaml`: `key_file`, `key_id`, `team_id`,
  `topic`, `environment` (`auto` — по токену; `sandbox`/`production` — только
  такие токены). Нет секции — доставка выключена, сервер работает как
  раньше; ключ не читается — ошибка в журнале, сервер работает без push.
  Ключ `.p8` — секрет сервера, вне git. HMS и FCM — интерфейс `push.Sender`
  и секции конфига, без реализации (Android §7).
- **Тесты:** фальшивый APNs на `httptest` (HTTP/2): форма запроса, подпись
  JWT, кэш токена, повтор, удаление отвергнутых, payload без ПДн, путь от
  события хаба до APNs, коалесинг; обработчики; таблица — на Postgres.
  Живая проверка — `TestLiveAPNs` (ключ и токен из окружения).

### 7.2. Клиент

- **Права** (файлы `App/DDMail-iOS.entitlements`, `App/DDMail-macOS.entitlements`
  — у push на iOS и macOS разные ключи, XcodeGen делает один файл на цель):
  `aps-environment` (`com.apple.developer.aps-environment` на Маке) —
  `development` в Debug, `production` в Release (`DDMAIL_APS_ENVIRONMENT`
  в `project.yml`); App Group — `group.ru.letotam.ddmail` на iOS и
  `<команда>.ru.letotam.ddmail` на macOS (`DDMAIL_APP_GROUP`, в Info.plist —
  `DDMailAppGroup`, по нему `AppGroup.id`): на Маке группу с префиксом
  команды система разрешает без записи в профиле и без вопроса пользователю,
  а `group.…` без профиля спрашивала бы; на iOS группа регистрируется в
  портале разработчика и назначается обоим App ID (приложению и
  расширению) — это делается вручную один раз: автоматическая подпись по
  ключу App Store Connect API включает возможность App Groups, но саму
  группу не заводит и не назначает (у API нет такого ресурса); группа связки ключей
  `$(AppIdentifierPrefix)ru.letotam.ddmail` — общая с расширением, поэтому
  существующие сессии в Keychain переносить не нужно: группа та же, что была.
- **Регистрация** (`PushService`, `DDMailPush.PushRegistry`): после
  разрешения на уведомления, при каждом выходе на экран и после добавления
  учётки — `registerForRemoteNotifications()` (APNs советует при каждом
  запуске), токен из делегата приложения → `POST /push/token` **каждой живой
  ddmail-учётке**. Что зарегистрировано — `токен|окружение` по учётке в общих
  настройках: повтор ничего не шлёт; новый токен — старый `DELETE`, новый
  `POST`; ошибка (нет сети, сервер старой версии отвечает 404) — повтор при
  следующем выходе на экран. Окружение — из Info.plist (`DDMailAPSEnvironment`):
  `development` → `sandbox`.
- **Снятие:** удаление учётки — `DELETE` её же сессией до того, как секрет
  стёрт (запрос без хранилища токена: обмен не вернёт сессию в Keychain);
  выключатель «Новые письма» — `DELETE` у всех учёток, включили — `POST`.
- **Общий контейнер App Group** (`AppGroup`, `DDMailAPI`): кэш GRDB
  (`Library/Application Support/ddmail/cache.sqlite`), список учёток
  (`accounts.json`), общие настройки (рубежи уведомлений, «Новые письма»,
  токен и регистрации), блокировки. **Перенос** при первом запуске новой
  версии (`AppModel.migrateStorage`): список учёток — копией, затем удаление
  старого; кэш — резервной копией SQLite (`MailStore.moveDatabase`: журнал
  WAL входит в копию), атомарной заменой и удалением старых файлов; рубежи и
  выключатель — из настроек приложения в общие (`SharedState.migrate`). Не
  вышло — старое остаётся, перенос повторится при следующем запуске.
- **Кэш на два процесса:** открытие и миграции схемы — под
  `NSFileCoordinator`; занятая другим процессом запись ждёт до 10 с. На iOS
  приложение в фоне «усыпляет» базу (`MailStore.suspend()`, GRDB
  `observesSuspensionNotifications`): усыплённый процесс с блокировкой
  SQLite в общем контейнере система убивает (0xdead10cc); фоновые задачи
  будят её на время работы. Расширение записало — уведомление Darwin
  `ru.letotam.ddmail.cache-changed`, приложение на экране перечитывает списки
  (`MailStore.externalChange`: наблюдения GRDB чужую запись не видят); на
  выходе на экран — то же самое.
- **Notification Service Extension** (`DDMailNotificationService`, iOS и
  macOS, `DDMailPush.PushCatchUp`): дельта-синк всех ddmail-учёток
  параллельно, не дольше 20 с, под межпроцессной блокировкой синка (файл в
  App Group; фоновый проход приложения берёт её же; не дождались за 5 с —
  синк всё равно, дельта идемпотентна). Сессии — из общей группы Keychain;
  обменянный токен записывается туда же. Внешние IMAP-учётки не синкаются
  (push у них нет, §13.4), но их беседы идут в бейдж.
- **Что показывать** — `NotificationPlan` по кэшу всех учёток, как у
  приложения (рубеж по uid учётки, спам и скрытые папки молчат). Рубежи
  общие и читаются-пишутся под блокировкой уведомлений одним куском —
  о письме уведомляет кто-то один: расширение или приложение.
  - есть новое — push становится уведомлением первой беседы (заголовок —
    имя, текст — тема и «новых: N», `threadIdentifier` и `userInfo` —
    `ref` беседы), остальные беседы — отдельными уведомлениями с id = `ref`,
    как у приложения;
  - всё синхронизировано, а показывать нечего (скрытая папка, прочитано на
    другом устройстве, уже уведомило приложение, «Новые письма» выключены) —
    права подавить показ у расширения нет (§12), поэтому уведомление
    тихое: `passive`, без звука, «Почта обновлена», `threadIdentifier`
    `ddmail.stale`; приложение снимает его при следующем синке, а на экране
    не показывает вовсе;
  - не успели, нет сети, нужен вход — обезличенный текст как есть
    (`threadIdentifier` `mail`); тап открывает приложение, после синка оно
    снимает этот push и показывает уведомления бесед.
- **Приложение на экране:** push о беседе, которая открыта, и «нечего
  показать» не показываются (`willPresent`); открытие беседы снимает и её
  push (беседа — в `userInfo`, id у push свой).
- **Бейдж** — число бесед с непрочитанным вне скрытых папок
  (`setBadgeCount`); ставится и из расширения (`content.badge`), и из
  приложения после каждого синка.
- **Mac:** push работает так же (APNs на macOS, расширение — в `PlugIns`),
  пока приложение не запущено; запущенное держит WS.
- **Проверено** (2026-11-12):
  - тесты пакета (`DDMailPushTests`: регистрация, перенос настроек, проход
    расширения на фальшивом сервере, бюджет времени, блокировка; перенос
    кэша — `MailStoreTests`); сквозные UI-тесты iPhone и iPad — зелёные;
  - **живой push в симуляторе iPhone:** симулятор получил настоящий токен
    APNs (sandbox), push отправлен серверным `push.APNs` со станции
    (`TestLiveAPNs`); письмо с Mail.ru на ящик тестовой учётки — расширение
    синхронизировало и показало «denis.danilin@internet.ru / Отчёт за
    ноябрь», бейдж 1; повторный push без нового — тихое уведомление без
    баннера; письмо самому себе сервер не считает входящим (дубль копии в
    «Отправленных») — уведомления нет, как и должно;
  - **перенос данных:** версия 0.0.2 на симуляторе iPad вошла в учётку
    (кэш с непереписанным WAL), поверх неё поставлена 0.0.3 — в App Group
    те же 1060 бесед, 3571 письмо и 8 служебных ключей, учётка без
    повторного входа, старые файлы удалены, `reminders.json` остался в
    контейнере приложения;
  - подписанная сборка macOS: push, App Group, Keychain у приложения и
    расширения; профили Xcode завёл сам по ключу App Store Connect API.
- **Не проверено:** iPhone, iPad и Мак живьём — устройства и экран Мака
  заблокированы; сборка на устройства iOS ждёт регистрации App Group в
  портале (см. права выше).

## 8. Отображение писем — решено

Модель — Android §8 без изменений: **один WKWebView на беседу**,
переиспользуемый; окно отрисовки по 20 писем с удержанием позиции; Shadow DOM
на письмо; нормализатор на JS внутри документа — **тот же код**
`mobile/shared/conversation-doc/`, кладётся в ресурсы приложения при сборке;
кэш результата нормализации с версией нормализатора.

Механизмы WebKit (отличаются от WebView Android и сильнее его):

- **Документ — со своей схемы** `ddmail-doc://` через `WKURLSchemeHandler`:
  `/assets/…` (документ), `/cid/<uid>/<cid>` (части письма),
  `/remote?uid=…&u=…` (внешняя картинка через прокси приложения, правила
  спама — как Android §5). Схема обрабатывается только нашим кодом.
- **Сеть мимо нас закрыта списком правил** `WKContentRuleList`: любые
  `http(s)` и прочие схемы, кроме `ddmail-doc` и `data:`, блокируются движком.
  **Отличие от Android:** WKWebView не даёт перехватить запросы `https` (на
  Android их видит `shouldInterceptRequest`), поэтому нормализатор
  переписывает внешние адреса картинок на `/remote`, а всё, что он пропустил,
  гасит список правил — второй рубеж. Плюс CSP документа (`script-src 'self'`,
  `img-src 'self' data:`), как у Android.
- **Мост — в мире страницы, и это осознанно.** Документ ленты общий с
  Android, и его собственный скрипт (`conversation.js`, грузится со своей
  схемы) и есть мост: `window.webkit.messageHandlers.ddm`. Изолированный мир
  (`WKContentWorld`) тут ничего не добавляет: чужой код в страницу не попадает —
  `<script>` и `on*` вырезает чистка, инлайн не исполняет CSP (`script-src
  'self'`), а сеть, кроме своей схемы и `data:`, режет `WKContentRuleList`.
  Письма — в shadow root, каждое в своём.
- **Мост** — `WKScriptMessageHandler` (ответов документу не нужно: команды
  идут вызовами `ddm.*`): долгое нажатие на пузырь,
  ссылка, чип вложения, адрес → нативный код. Меню — нативное
  (`UIContextMenuInteraction` / контекстное меню Mac), ссылки — во внешнем
  браузере (`openURL`), вложения — §5.
- **Хранилище WebKit — непостоянное** (`WKWebsiteDataStore.nonPersistent()`):
  куки и кэш письма не переживают беседу.
- Масштаб широких писем — как Android (`zoom` по измеренной ширине, пересчёт
  на смене размера окна); на iPad и Маке окно меняет ширину часто.

## 11. Календарь, напоминания, задачи, контакты — решено

Смысл — Android §12–§15 целиком (окна по месяцу, развёртка повторов по
стенным часам пояса устройства, «весь день», видимость только на этом
устройстве, календарь и книга для новых записей — только назначенные
пользователем, форма по подтверждению, перенос драгом, задачи, сводная книга
контактов). Android копировал вид у Apple — здесь он нативный: шкала дня и
недели, лента месяцев iPhone, сетка месяца и год iPad.

**Задачи — создание, правка, удаление (0.0.5)** — как Android §14 (там же
серверные эндпоинты `POST /tasks`, `PATCH`/`DELETE /tasks/{id}` и поле
`components` у `/calendars`). «+» — последним в первой строке раздела, после
«Показать выполненные». Форма — лист (`sheet`, `Form`): заголовок, заметка,
«Срок» (выключатель), «Весь день», дата или дата и время (`DatePicker`),
«Список» (`Picker`, только у новой; по умолчанию первый список задач). У
существующей — «Удалить задачу» с подтверждением; задача из списка только
для чтения открывается без правки. Логика — `DDMailCalendar/TaskBoard.swift`
(порт `TaskBoard.kt`, проверяется `swift test` на фальшивом API):
оптимистично, отказ откатывает строку и показывает причину.

**Напоминания — отличие от Android по механизму:** у iOS нет будильника,
который будит приложение в срок. Поэтому каскад не «взводится по звеньям», а
**планируется целиком** локальными уведомлениями `UNUserNotificationCenter`
(по одному на каждое звено каскада и «Наступило») на окно посева
`[сегодня, +8 суток)`.

- **Лимит iOS — 64 ожидающих локальных уведомления на приложение.**
  Планируются ближайшие по времени; при каждом пересеве (запуск, синк,
  `calendar_updated`, BGTask) окно сдвигается. Переполнение не теряет
  ближайших — теряет только дальние, которые доедут следующим пересевом.
- «Событие уже идёт!» при опоздании больше 2 минут — **не нужно:**
  уведомление показывает система точно в срок, опоздать может только
  выключенное устройство, и тогда оно покажет пропущенное само.
- **Смахнуть = «✕»** (тишина по вхождению): категория с
  `customDismissAction`; приложение получает смахивание и снимает оставшиеся
  звенья этого вхождения. **«Напомнить позже» — отличие от Android:** у
  действий уведомления iOS набор задаётся категорией заранее, а не на каждое
  уведомление, поэтому шаги фиксированные — 5 мин, 15 мин, 1 ч и «в момент
  начала»; шаг, который лёг бы после начала, становится началом. Каскад
  заменяется одним сроком, как на Android.
- **Звенья, которые система уже показала**, приложение не повторяет: сервис
  помнит id поставленных уведомлений и при пересеве продвигает каскад по тем,
  чей срок прошёл. Пересевы последовательны, просьбы во время прохода
  сливаются в один повтор (`ReminderService`).
- Решение пользователя держится за «начало + название» вхождения — как
  Android §13 (и логика — порт `ReminderPlanner` с его тестами).
- Скрытый календарь снимает свои ожидающие и показанные уведомления.
- Отдельного разрешения на «работу в фоне» и точные будильники на iOS нет —
  нужно только разрешение на уведомления (с `timeSensitive`, чтобы
  напоминание пробивалось через «Фокус» — **проверить**, нужен ли для этого
  entitlement).

## 13. Внешние учётки — решено

Смысл — `mobile-external-accounts.md`; здесь — механизмы Apple.

### 13.1. Учётки

- **Несколько учёток вперемешку** (`MailAccount`, `DDMailAuth`): `ddmail`
  (токен сессии) и `imap` (IMAP + SMTP паролем). Ключ — `account_key`
  (`логин@хост`; у IMAP — хост IMAP). Беседа определяется парой
  (учётка, id) — для экрана это `Conversation.ref`; выбор, уведомления,
  окна Мака и «последняя беседа» хранят `ref`, а не голый id.
- **Хранение:** список учёток — JSON в Application Support (секретов в нём
  нет; восстановленная из резервной копии учётка без секрета просит входа),
  секреты — Keychain `AfterFirstUnlockThisDeviceOnly`, запись на учётку
  (`KeychainAccountStore`): у ddmail — сессия, у IMAP — пароль. Старая
  единственная сессия (`KeychainSessionStore`) при первом запуске новой
  версии становится первой учёткой.
- **Провайдер почты** (`MailProvider`, `DDMailSync`): `SyncEngine` (ddmail) и
  `ImapEngine` (IMAP) — две реализации одного протокола; экран
  (`MailModel`) держит беседы всех учёток одним списком по дате и отдаёт
  действие провайдеру учётки беседы. Ошибки обоих — `APIError`
  (`.unauthorized` — нужен вход этой учётки).
- **Кэш один на все учётки** (GRDB, миграция `v2-accounts`): первичные
  ключи бесед, писем и тел уже включали `accountKey`; служебные ключи
  ddmail-учётки (курсор журнала, водяной знак, документы) получили её ключ
  в имени (`<account>/journal_seq`) — две учётки не делят курсор.
  Удаление учётки стирает её беседы, спам, тела, заголовки IMAP и служебные
  ключи (`MailStore.clearAccount`), её секрет и уведомления.
- **Рабочее пространство** (`Workspace`) собирается заново при смене набора
  учёток (добавили, удалили, вошли заново) — без потери кэша. Календарь,
  задачи, контакты, аватарки и документ папок ведёт первая ddmail-учётка;
  без неё папки диалогов — локальный документ того же формата
  (`LocalDialogFolders`).
- **Состояние «нужен вход» — у каждой учётки своё** (`AccountLink.status`);
  плашка «Войти» — по учётке, остальные работают.
- **Рубеж уведомлений — по учётке** (`NotificationPlan.watermarks`): у
  учёток своя нумерация писем, и рубеж одной не глушит другую.
- **Настройки → Учётки:** список с состоянием, «Войти заново», «Удалить
  учётку» (с подтверждением), «Добавить учётку» — окно подключения поверх
  приложения.

### 13.2. Подключение и автонастройка

- **Одно окно** для первого запуска, «Добавить учётку» и «Войти» (`ConnectModel`):
  адрес → поиск → нашёлся ddmail — вход на сервер; иначе найденные
  IMAP/SMTP и пароль (с подсказкой о пароле приложения для известных
  служб); «Я знаю все настройки» — ручная форма (IMAP/SMTP: хост, порт,
  TLS или STARTTLS; логин; «SMTP без авторизации»; имя в письмах).
  Открытого текста в форме нет вовсе.
- **Поиск** — порт `discover.rs` (`MailDiscovery`, `DDMailAuth`): те же фазы,
  порядок кандидатов, таблица служб (`MailPreset` — порт `mail_presets`),
  служба по MX, автонастройка Thunderbird только по https, таймауты TCP 3 с
  и ответ 8 с, «побеждает первый успешный по порядку доверия», прогресс от
  верхней границы (51 проверка). MX — `DNSServiceQueryRecord`. Отмена поиска
  рвёт соединения проверок (иначе `URLSessionStreamTask` ждал бы час).
- **Проверка входа** перед сохранением (`AccountCheck`): IMAP, затем SMTP, по
  25 с; ошибки — по-русски с указанием сервера («Входящая почта (IMAP):
  неверный логин или пароль.»), текст TLS — как есть.
- **Один ящик — одна учётка:** ddmail и IMAP с одним ключом одновременно
  не подключаются (кэш и документы общие по ключу) — окно просит удалить
  прежнюю.
- **Настройки учётки IMAP:** имя в письмах и «Другие мои адреса».

### 13.3. IMAP: синк, беседы, тела, изменения

- **`ImapEngine`** (`DDMailSync`) — актор учётки; два соединения: синк и
  действия (тела, флаги, перенос), чтобы открытие беседы не ждало долгого
  первого синка; каждое — команды по одной, оборвавшееся переиспользуемое
  соединение — один повтор на свежем. Пароль читается из Keychain при
  каждом входе, в памяти не держится.
- **Папки** — SPECIAL-USE (`\Sent`, `\Drafts`, `\Junk`, а также `\Spam`, как
  пишет Mail.ru), иначе по именам (списки десктопа плюс русские имена).
  Окна: 5000 / 2500 / 1250 / 500 последних писем, нижний UID окна — по
  номеру одного письма, дальше всё по UID.
- **Проход по папке** (`syncFolder`): EXAMINE (только чтение, `\Recent` не
  трогаем); сменилась UIDVALIDITY — заголовки и тела папки прочь, поколение
  +1; новые — `UID FETCH <последний+1>:*` (или ничего, если UIDNEXT тот же);
  флаги и удалённые — QRESYNC (`SELECT … (QRESYNC …)`), иначе CONDSTORE
  (`CHANGEDSINCE` + `UID SEARCH UID окно`), иначе FLAGS всего окна и
  разница. Живые замеры (2026-11-12): ящик `lucky` (≈2800 писем INBOX)
  первый проход 2 с, повторный — 1,2–1,5 с; ни у сервера ddmail, ни у
  Mail.ru CONDSTORE нет — работает запасной путь.
- **id письма для ленты** — роль (3 бита) · поколение UIDVALIDITY (18 бит) ·
  UID (32 бита), в пределах 2^53 (число JavaScript ленты). INBOX — старшая
  роль: рубеж уведомлений учётки — максимум id.
- **Беседы** — `ConversationBuilder`, порт десктопа и сервера; где они
  расходятся, правит сервер (имя собеседника — с «комментарием» в скобках,
  как `extractName`; адрес учётки добавляется в набор письма без своего
  адреса). Айдентики сервера ddmail, подключённого по IMAP, берутся
  `GETMETADATA /shared/vendor/ddmail/identities` (как десктоп). Сверка
  `LiveCompareTests` на ящике `lucky`: все беседы совпали с ddmail по id,
  метке и айдентике, кроме писем без своего адреса в заголовках (рассылки
  на группу): сервер знает внешний ящик, из которого письмо пришло, а IMAP
  этого не сообщает — у них адрес учётки, как у десктопа. Сквозной тест
  `ImapFlowTests.testLuckyIMAPMatchesDdmail` проверяет то же через UI.
- **Тела** — `BODY.PEEK[]`, разбор `DDMailMIME` в модель тела сервера:
  html, text, вложения с номерами, части `cid:`. Встроенная часть, на
  которую HTML не ссылается, — вложение (правило `hideInlineAttachment`
  сервера), синтетический `text/calendar` — нет. Сырые письма — в памяти
  (до 32 МБ): части и вложения открытой беседы не перекачиваются.
  Докачка заранее — своим соединением, «только по Wi-Fi» —
  `prohibitExpensivePaths`/`prohibitConstrainedPaths` у `NWConnection`.
- **Изменения** — оптимистично в кэше, отказ сервера — откат и сообщение:
  прочитано — `UID STORE ±FLAGS.SILENT (\Seen)`; удаление — `\Deleted` и
  `UID EXPUNGE` (без UIDPLUS — `EXPUNGE`); «В спам» — `UID MOVE` в Junk (без
  MOVE — COPY и удаление), одна кнопка без правил; «Не спам» — в INBOX.
  Нет папки Junk — пунктов «В спам» нет.
- **Отправка** — SMTP учётки-владельца адреса «От» (`ComposeModel.owner`, как
  `owner_for` десктопа): MIME `DDMailMIME.MIMEBuilder`, затем копия в
  «Отправленные»: через 5 с `UID SEARCH HEADER Message-ID`, не нашлась за
  15 с — `APPEND` с `\Seen`; у Gmail не делается.
- **«От кого»** — айдентики всех учёток, учётка открытой беседы первой;
  у ddmail, подключённого по IMAP, адрес по умолчанию — объявленный
  сервером (`is_default` в METADATA): введённый при подключении адрес сервер
  может не разрешать для отправки (553 «not owned»). Адрес ничей — «Не
  через что отправить».
- **Живая проверка** `LiveSendTests` (2026-11-12): Mail.ru — письмо себе с
  вложением дошло во «Входящие», копия в «Отправленных» одна (Mail.ru кладёт
  сам, поиск по Message-ID её нашёл — APPEND не понадобился); ddmail по IMAP
  — копия в «Отправленных» одна.

### 13.4. Новая почта и фон

- **На экране:** у каждой IMAP-учётки — IDLE на INBOX своим соединением
  (`ImapEngine.watch`, канал `ImapLive`); событие — инкрементальный синк этой
  учётки, пачка событий сливается в один синк (400 мс). Перевыдача IDLE
  каждые 25 мин — DONE шлёт таймер, пока чтение ждёт сервер, соединение
  остаётся. Обрыв — переподключение не чаще раза в 30 с; без IDLE у
  сервера — опрос раз в 2 мин. Неверный пароль — «нужен вход» этой учётки и
  конец наблюдения. Ушли с экрана — каналы закрыты (как WebSocket ddmail).
  Живая проверка: письмо себе на Mail.ru будит IDLE.
- **В фоне** push у внешних учёток нет: `BGAppRefreshTask` синкает все
  учётки разом (ошибка одной не мешает другим) и строит уведомления из
  кэша по тем же правилам, что у ddmail (спам и скрытые папки молчат,
  рубеж — по учётке). На Маке приложение живёт с закрытым окном, IDLE
  держится, пока оно на экране.
- **«Нужен вход»** — у каждой учётки своя плашка с «Войти» (окно
  подключения с сохранёнными серверами — остаётся ввести пароль); кэш
  учётки виден.

### 13.5. Внешние CalDAV и CardDAV

- **Источники** (`DDMailDAV`): у календаря и контактов протоколы
  `CalendarSource`/`ContactsSource` с именами методов API сервера —
  `SessionAPI` (ddmail) их реализует как есть, `DAVCalendarSource` и
  `DAVContactsSource` — по CalDAV/CardDAV учётки. `CalendarHub` и
  `ContactsHub` сводят их в один календарь и одну книгу: действие уходит
  источнику календаря, события или книги; отказ одного источника не мешает
  остальным и ставит состояние его учётке («нужен вход» на 401).
- **Обнаружение** (`DAVClient.discover`): адрес уже коллекция — она; иначе
  `current-user-principal` → `calendar-home-set`/`addressbook-home-set` →
  **все** коллекции дома (лучше десктопа, у которого первая); календари без
  VEVENT (только задачи) пропускаются. Перенаправления — вручную, пароль не
  уходит на другой хост. Адреса находятся при добавлении учётки по домену
  (известные службы, затем `.well-known` на домене адреса и хосте IMAP) тем
  же паролем, не дольше 10 с; правятся в «Настройки → Учётки».
- **iCalendar** (`ICal`): события — в модель сервера (`EventDTO`), развёртка
  повторов, шкалы и напоминания (VALARM) общие с ddmail. Пояса TZID — база
  ОС (лучше десктопа, у которого «как UTC»), имена Windows — таблицей
  частых, неизвестный — пояс устройства; «весь день» — полночь UTC, как у
  сервера. Переопределения вхождений (`RECURRENCE-ID`) — отдельные события,
  их даты — исключения мастера. Запись: новое — `PUT If-None-Match: *`;
  правка — свежий GET и замена только своих полей мастера (`merge_ical`
  десктопа), `If-Match`; удаление — `DELETE If-Match`; ответ на
  приглашение — PARTSTAT своего участника. Правка «этого и следующих» у
  внешнего календаря не поддерживается — правится вся серия.
- **vCard** (`VCard`): порт `build_vcard`/`parse_vcard`; правка меняет только
  имя, адреса, телефоны, организацию и должность — фото и прочее остаются.
- **id** объектов DAV — отрицательные (FNV-1a от учётки и адреса ресурса):
  с id сервера не пересекаются.
- **Живая проверка** (2026-11-12): `lucky` по IMAP — CalDAV нашёлся на
  `mail.letotam.ru/.well-known/caldav`, 5 календарей, сотни событий, виден в
  календаре приложения (`ImapFlowTests`); CardDAV у сервера по `.well-known`
  не отвечает. Mail.ru пароль приложения для CalDAV/CardDAV не принимает
  (только OAuth) — у такой учётки календаря и контактов нет.

### 13.6. Проверка и что не сделано

- **Тесты пакета:** кодеки IMAP/SMTP/MIME на записанных сессиях, построение
  бесед (порт тестов десктопа и сервера), синк на фальшивом IMAP-сервере
  (`FakeIMAPServer`: с QRESYNC, только CONDSTORE и без них; смена
  UIDVALIDITY, удаление, флаги, откат отказа, IDLE), автонастройка (порт
  тестов `discover.rs`), iCalendar/vCard/DAV. Живые проверки — по учёткам
  из окружения: `LiveIMAPTests`, `LiveDiscoveryTests`, `LiveCompareTests`,
  `LiveSendTests`, `LiveDAVTests`.
- **Сквозные UI-тесты** `ImapFlowTests`: Mail.ru через автонастройку
  (`DDMAIL_TEST_MAILRU_*`) и `lucky`: ddmail, затем удалить учётку, затем тот
  же ящик по IMAP вручную — те же id бесед и календарь по CalDAV.
- **Google OAuth не делаем** (решение владельца 2026-11-12): Gmail —
  обычный IMAP паролем приложения.
- **Не сделано:** задачи (VTODO) внешних учёток — раздел «Задачи» только у
  ddmail; правка «этого и следующих» во внешнем календаре; папки диалогов
  без ddmail-учётки живут только на этом устройстве (сервера, который
  хранил бы документ, нет).
