# Контракт поведения iOS / iPadOS / macOS-клиента

Договорённости о поведении и устройстве Apple-клиента ddmail. Пишется **до кода**
и живёт по тем же правилам, что `desktop-behavior-contract.md` и
`android-behavior-contract.md`: **меняешь поведение — правишь этот файл в том же
коммите.** Ссылки — на типы и функции, не на номера строк.

**Основа — Android-контракт.** Семантика (что такое диалог, папки, спам, ветки
отправки, календарь, напоминания) у мобильных клиентов одна, и здесь она не
переписывается: раздел, где сказано «как Android §N», означает «то же правило,
слово в слово». Этот файл описывает только **как** — механизмы Apple — и места,
где платформа вынуждает поступить иначе. Такие места помечены **Отличие от
Android** с причиной.

Статус разделов: **решено** — делаем так; **проверить на устройстве** — решение
держится на допущении, которое подтверждаем живым iPhone/iPad; **открыто** — §12.

## 0. Принципы

- **Нативно, без компромиссов** (как Android §0). Swift + SwiftUI, механизмы
  платформы: URLSession, Keychain, APNs, BackgroundTasks, UserNotifications,
  WKWebView, QuickLook, String Catalog. Rust-ядро через FFI, KMP, Flutter,
  Catalyst — не используются.
- **Один код — три системы.** Одно приложение SwiftUI, собранное нативно под
  iOS, iPadOS и macOS (не Catalyst и не «iPad-приложение на Маке»).
  Платформенные ветки (`#if os(macOS)`) — только там, где механизм разный:
  меню и горячие клавиши Mac, сохранение файлов, фоновая работа.
- **На Маке клиент заменит Slint-десктоп** (решение пользователя 2026-11-11),
  когда догонит его по функциям (§10) и будет выглядеть лучше. До этого Slint
  остаётся основным клиентом Mac, Apple-клиент на Маке — сборка для проверки.
- **Сервер — источник правды о смысле** (как Android §0). Где десктопный или
  Android-контракт говорит **что**, клиент обязан совпадать.
- **Иконки вместо надписей** (правило №1 мобильных клиентов, Android §0) —
  SF Symbols, у каждой кнопки-иконки `accessibilityLabel`. На Маке в меню
  приложения — текст (так устроены меню macOS), в панели окна — иконки.
- **Выглядеть как приложение Apple.** Системные компоненты (`List`,
  `NavigationSplitView`, `.toolbar`, `.searchable`, `.sheet`, `.swipeActions`,
  материалы, Dynamic Type, тёмная тема) — по умолчанию. Свой компонент —
  только там, где системного нет (лента беседы, шкала календаря), и он
  повторяет метрики и анимации системных.
- **Скорость разработки не приоритет.** Решения — по качеству результата.

## 1. Платформа и сборка — решено

- **Код:** `mobile/ios/` в этом репозитории.
- **Минимальные версии: iOS / iPadOS / macOS 27** — те, что стоят на устройствах
  пользователя; совместимость со старыми не нужна, свежий SwiftUI используется
  без обходов. Если какое-то из устройств не получит 27 — опускаемся до 26.
- **Язык:** Swift 6, строгая проверка конкурентности (`complete`).
- **Устройства проверки:** iPhone 15 Pro, iPad Pro 13″, MacBook (Apple Silicon).
- **Bundle ID:** `ru.letotam.ddmail` — как пакет Android.
- **Проект Xcode генерируется** из `mobile/ios/project.yml` (XcodeGen). Сам
  `.xcodeproj` в git не хранится: его правка руками и конфликты слияния —
  главный источник поломок iOS-проектов.
- **Логика — в локальном Swift-пакете** `mobile/ios/DDMailKit`, приложение —
  тонкая оболочка из экранов. Пакет собирается и тестируется `swift test` на
  Маке без симулятора.

### Модули DDMailKit

| Модуль | Что внутри | Аналог Android |
|---|---|---|
| `DDMailAPI` | HTTP-клиент `/api/desktop/v1` (URLSession, `Codable`), WebSocket, refresh токена | `:core:api` |
| `DDMailStore` | кэш на SQLite (GRDB): схема, миграции, запросы | `:core:db` |
| `DDMailSync` | движок синхронизации, доменные типы, папки диалогов, цвета айдентик | `:core:sync` |
| `DDMailAuth` | вход, токен в Keychain, автонастройка | `:core:auth` |
| `DDMailCalendar` | развёртка повторов, планировщик напоминаний | `Recurrence`, `ReminderPlanner` |

Цели Xcode: приложение (iOS + macOS) и Notification Service Extension (§7).

- **Кэш — GRDB, не SwiftData.** Нужны явные миграции, версия схемы, точный
  контроль запросов и один писатель — то, что Android получает от Room.
  SwiftData скрывает SQL и миграции и менялась от версии к версии; ради
  «системности» платить предсказуемостью кэша не стоит. GRDB — единственная
  сторонняя зависимость логики; добавить ещё одну — решение с причиной в этом
  файле.
- **Тесты — Swift Testing.** Порты из Android переносятся **с теми же
  тестовыми векторами** (`IdentityColors`, `DialogFolders`, `Recurrence`,
  `ReminderPlanner`): смысл общий, совпадение проверяется тестами, а не на глаз.

### Сборка и установка — удалённо с Мака

Разработка идёт на станции (WSL), Мак — только сборочный узел; за ним не
работают. Код уезжает на Мак `rsync` по SSH в одну сторону (Мак не в Syncthing
и не в git: иначе получим два источника правды):

```bash
mobile/ios/scripts/mac.sh build      # rsync → xcodegen → xcodebuild (симулятор)
mobile/ios/scripts/mac.sh test       # swift test пакета + тесты приложения
mobile/ios/scripts/mac.sh run-sim    # поставить в симулятор, запустить, скриншот сюда
mobile/ios/scripts/mac.sh device     # собрать и поставить на iPhone/iPad (devicectl)
```

- Хост — алиас `mac` в `~/.ssh/config` станции. Каталог на Маке —
  `~/build/ddmail-ios/` (рабочая копия) и стандартный DerivedData Xcode — вне
  синкаемого дерева, как требует правило workspace.
- Скриншоты и видео симулятора — `xcrun simctl io`, с устройства — по
  `devicectl`; файл забирается на станцию.
- Устройства спарены с Маком один раз кабелем, дальше установка по сети.
- **Подпись в SSH-сессии:** связка ключей login в сессии SSH заблокирована;
  скрипт разблокирует её перед `xcodebuild` (пароль — в Keychain Мака, не в
  репозитории и не в скрипте).
- **Версия** — `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` в `project.yml`;
  бампается при любой правке клиента, как у десктопа и Android.
- **Аккаунт разработчика.** До push хватает бесплатного (сборки на свои
  устройства живут 7 дней). Push (APNs), Notification Service Extension с общей
  App Group и TestFlight требуют платного Apple Developer Program — оформляем
  перед §7.

## 2. API и сессия — решено

Как Android §2, с такими механизмами:

- **Токен — в Keychain**, класс доступа `AfterFirstUnlockThisDeviceOnly`: фон
  (push, BGTask) должен уметь сделать refresh при заблокированном экране, а
  на другое устройство через резервную копию токен уезжать не должен. Группа
  доступа Keychain общая с Notification Service Extension. Пароль не хранится
  нигде.
- **Классификация ошибок** — как Android §2: 401 после неудачного refresh →
  «нужен вход»; 403 — ошибка действия с текстом сервера; отказ самого
  `/auth/refresh` любым кодом → «нужен вход»; таймаут, 5xx, обрыв — временное,
  с бэкоффом.
- **«Нужен вход»** — несмываемая плашка над содержимым с кнопкой «Войти», кэш
  виден.
- **WebSocket** — `URLSessionWebSocketTask`, токен **только заголовком**
  `Authorization: Bearer`. **Отличие от Android:** `?token=` в URL не шлётся
  вовсе — переходный период ему не нужен, клиент новый, а сервер заголовок
  уже принимает.

## 3. Подключение (первый запуск) — решено

Как Android §3 (email → `/.well-known/ddmail` на `mail.<домен>`, `<домен>`,
MX-хостах → вход или ручной адрес), механизмы:

- **MX — через системный резолвер** `DNSServiceQueryRecord`
  (`kDNSServiceType_MX`, `dns_sd`): работают внутренние домены и
  корпоративный DNS, как у Android (`DnsResolver`) и десктопа.
- **Только https.** Доверие — системное хранилище, в том числе корневые CA из
  установленных профилей, если пользователь включил им полное доверие
  (Настройки → Основные → Об этом устройстве → Доверие сертификатам). Своей
  проверки сертификатов клиент не делает.
- Пароль при поиске никуда не уходит. Поле пароля — `textContentType(.password)`,
  связка ключей iCloud может его подставить.

## 4. Синхронизация — решено

Модель — как Android §4 (беседы с водяным знаком `server_now_ms`, журнал
`/changes`, версия формата id в `meta`, тела заранее от свежей беседы к
старой, пустое тело перезапрашивается, мутации оптимистично с откатом).

- **Один писатель кэша:** движок синхронизации — `actor`; все записи в GRDB
  идут через него. Фон, push-расширение и экран не синхронизируют
  одновременно: расширение и BGTask берут межпроцессную блокировку
  (файл в App Group), экран при живом WS фоновые проходы пропускает (как
  Android §7).
- **«Загружать письма заранее?»** — тот же вопрос с тремя ответами и без
  ответа по умолчанию. «Только по Wi-Fi» — запросы докачки с
  `allowsExpensiveNetworkAccess = false` и `allowsConstrainedNetworkAccess =
  false`: система сама не пускает их через сотовую сеть, точку доступа и
  режим экономии трафика. Открытие беседы качает её тела по требованию
  всегда.
- **Когда синхронизируемся:** при выходе приложения на экран; по событию WS;
  по push (§7); `BGAppRefreshTask` — страховка от потерянного push (время
  выбирает iOS, обычно реже, чем раз в 15 минут Android). Докачка тел в фоне —
  `BGProcessingTask` (с сетью; «Только по Wi-Fi» — без дорогой сети).
- **Mac:** приложение живёт и после закрытия окна (как десктоп с треем), WS
  держится, пока оно запущено; BGTask на Маке нет.

## 5. Почта — решено

Всё из Android §5 переносится без изменений смысла: диалог = набор адресов,
роли, табы папок над списком (без «Все»), ветки отправки, optimistic send,
правила уведомлений, спам («В спам» с ответами «Адрес» / «Домен»; отдельный список, не зазывает, не ходит в сеть,
картинки только по плашке на письмо), скрытые папки, `auto_read` исполняет
только десктоп, локальный поиск, цвет строки по группе айдентики, аватарки,
картинки по отправителю, свои имена и аватарки диалогов с сервера, «В папку» /
«Убрать из папки» одной записью документа папок, склеек нет. Порт `folders.rs`
— `DialogFolders.swift` с тестами Android.

Механизмы:

- **Поиск** — `.searchable` над списком; сравнение без учёта регистра и
  диакритики средствами Foundation (`localizedStandardContains` /
  `folding`), кириллица складывается правильно.
- **Множественный выбор** — системный режим правки `List` (`EditMode` на
  iPhone/iPad, выбор Cmd/Shift-кликом на Маке); действия — в нижней панели
  инструментов. Состав действий и подтверждение удаления — как Android §5.
- **Свайпы** (`.swipeActions`) — как предложение Android §11: вправо
  «Прочитано/Непрочитано», влево «В папку…»; удаления и спама свайпом нет.
  На Маке свайпы трекпадом работают так же, плюс контекстное меню по правому
  клику с теми же действиями.
- **Вложения:** касание — просмотр QuickLook (`.quickLookPreview`); долгое
  нажатие — «Открыть», «Поделиться», «Сохранить в Файлы» (`fileExporter`).
  Mac: «Сохранить в Загрузки» и открыть программой по умолчанию.

## 6. Раскладка — решено

Раскладка — по **классу ширины окна** (`horizontalSizeClass` и ширина
контейнера), не по модели устройства: так она работает в Split View, Slide
Over, Stage Manager на iPad и в окне любого размера на Маке.

| Где | Раскладка |
|---|---|
| iPhone 15 Pro (compact) | табы папок + список; беседа — переходом в стеке, «‹» и свайп от края назад |
| iPad, узкое окно Split View | как iPhone |
| iPad / Mac, широкое окно | `NavigationSplitView`: список и беседа рядом; разделы — в боковой панели |

- **Разделы** (почта, календарь, задачи, контакты; Android §16) — `TabView` со
  стилем `.sidebarAdaptable`: таб-бар внизу на iPhone, боковая панель на iPad
  и Маке — ровно то, что Android повторял «как iOS».
- **Смена раскладки не теряет контекст:** открытая беседа, позиция списка,
  черновик, выбранный таб — в `@SceneStorage` / модели сцены.
- **Mac — несколько окон** (`WindowGroup`): беседу можно открыть отдельным окном.
  Меню приложения и горячие клавиши: новое письмо, ответить, переслать,
  удалить, поиск, переход между папками.
- **Клавиатура на iPad** — те же горячие клавиши, что на Маке
  (`.keyboardShortcut`).

## 7. Push и фон — решено, доставку проверить на устройстве

- **На экране** — WebSocket; события как Android §7 запускают синк.
- **В фоне — APNs.** Постоянного соединения нет (iOS его и не даёт).
- **Push не несёт персональных данных** (152-ФЗ: APNs — серверы Apple за
  рубежом, это трансграничная передача третьему лицу). В push — только факт
  «есть изменения». Отправитель, тема, адреса не кладутся **никогда**.
- **Механизм — видимый push + Notification Service Extension.**
  **Отличие от Android:** «тихий» push (`content-available`) iOS
  придерживает по своему усмотрению и не доставляет вовсе, если приложение
  смахнули из переключателя — на нём уведомления не построить. Поэтому сервер
  шлёт видимый push с обезличенным текстом («Новые письма») и
  `mutable-content: 1`; расширение просыпается до показа (до ~30 с), делает
  дельта-синк через общий кэш в App Group и **заменяет текст** на настоящий
  (отправитель, тема) из своего кэша — данные на телефон приходят по нашему
  каналу, а не через Apple. Не успело или нет сети — показывается
  обезличенный текст, тап открывает приложение и синхронизирует.
- Правила «что уведомлять» — как Android §7 (только реальное входящее, не о
  открытой беседе, не о скрытых папках, рубеж по uid). Если по итогам синка
  уведомлять нечего (письмо в скрытую папку, прочитано на другом устройстве)
  — **проверить на устройстве**, как глушить: у расширения есть право
  (entitlement) подавлять показ, его выдаёт Apple по запросу; без него —
  `threadIdentifier` и немедленное снятие уведомления приложением.
- **Бейдж** — число бесед с непрочитанным вне скрытых папок
  (`setBadgeCount`); ставится и из расширения, и из приложения.
- **Сервер:** регистрации токенов на сервере пока нет ни для Android, ни для
  iOS (на 2026-11-11) — заводится один эндпоинт на обе платформы, тип
  токена `hms` / `fcm` / `apns`. Отправка в APNs по HTTP/2 в APNs с ключом `.p8` (token-based auth),
  токены, которые APNs называет недействительными (`410`, `BadDeviceToken`),
  удаляются. Ключ `.p8` — секрет сервера, вне git.
- **Mac:** push работает так же (APNs на macOS), пока приложение не запущено;
  запущенное держит WS.

## 8. Отображение писем — решено

Модель — Android §8 без изменений: **один WKWebView на беседу**,
переиспользуемый; окно отрисовки по 20 писем с удержанием позиции; Shadow DOM
на письмо; нормализатор на JS внутри документа — **тот же код**
`mobile/shared/conversation-doc/`, кладётся в ресурсы приложения при сборке;
кэш результата нормализации с версией нормализатора.

Механизмы WebKit (отличаются от WebView Android и сильнее его):

- **Документ — со своей схемы** `ddmail-doc://` через `WKURLSchemeHandler`:
  `/assets/…` (документ), `/cid/<uid>/<cid>` (части письма),
  `/remote?uid=…&u=…` (внешняя картинка через прокси приложения, правила
  спама — как Android §5). Схема обрабатывается только нашим кодом.
- **Сеть мимо нас закрыта списком правил** `WKContentRuleList`: любые
  `http(s)` и прочие схемы, кроме `ddmail-doc` и `data:`, блокируются движком.
  **Отличие от Android:** WKWebView не даёт перехватить запросы `https` (на
  Android их видит `shouldInterceptRequest`), поэтому нормализатор
  переписывает внешние адреса картинок на `/remote`, а всё, что он пропустил,
  гасит список правил — второй рубеж. Плюс CSP документа (`script-src 'self'`,
  `img-src 'self' data:`), как у Android.
- **Изолированный мир скриптов:** наш мост и нормализатор исполняются в
  `WKContentWorld` приложения, а не в мире страницы — даже уцелевший чужой
  скрипт не видит моста.
- **Мост** — `WKScriptMessageHandlerWithReply`: долгое нажатие на пузырь,
  ссылка, чип вложения, адрес → нативный код. Меню — нативное
  (`UIContextMenuInteraction` / контекстное меню Mac), ссылки — во внешнем
  браузере (`openURL`), вложения — §5.
- **Хранилище WebKit — непостоянное** (`WKWebsiteDataStore.nonPersistent()`):
  куки и кэш письма не переживают беседу.
- Масштаб широких писем — как Android (`zoom` по измеренной ширине, пересчёт
  на смене размера окна); на iPad и Маке окно меняет ширину часто.

## 9. Что на iPhone/iPad/Mac иначе — решено

| Десктоп | iPhone / iPad | Mac |
|---|---|---|
| Enter — отправить | Enter — новая строка, отправка кнопкой; с аппаратной клавиатурой Cmd+Enter | Enter — отправить, Shift+Enter — новая строка (как десктоп) |
| Правый клик → меню | долгое нажатие → контекстное меню; выбор — режим правки | правый клик → контекстное меню |
| Двойной клик — переименовать / аватарка | пункты меню шапки беседы | то же меню шапки |
| Подсказки при наведении | долгое нажатие на пузырь | наведение (`.help`) |
| Тосты | системные уведомления; подтверждения мутаций — inline «✓ …» | то же |
| Точка на трее | бейдж на иконке | бейдж на значке в Dock |
| Вложение: в Downloads и открыть | QuickLook; «Сохранить в Файлы» | в Загрузки и открыть |
| Копирование адреса кликом | долгое нажатие → «Скопировать» | клик → копировать, как десктоп |

## 11. Календарь, напоминания, задачи, контакты — решено

Смысл — Android §12–§15 целиком (окна по месяцу, развёртка повторов по
стенным часам пояса устройства, «весь день», видимость только на этом
устройстве, календарь и книга для новых записей — только назначенные
пользователем, форма по подтверждению, перенос драгом, задачи, сводная книга
контактов). Android копировал вид у Apple — здесь он нативный: шкала дня и
недели, лента месяцев iPhone, сетка месяца и год iPad.

**Напоминания — отличие от Android по механизму:** у iOS нет будильника,
который будит приложение в срок. Поэтому каскад не «взводится по звеньям», а
**планируется целиком** локальными уведомлениями `UNUserNotificationCenter`
(по одному на каждое звено каскада и «Наступило») на окно посева
`[сегодня, +8 суток)`.

- **Лимит iOS — 64 ожидающих локальных уведомления на приложение.**
  Планируются ближайшие по времени; при каждом пересеве (запуск, синк,
  `calendar_updated`, BGTask) окно сдвигается. Переполнение не теряет
  ближайших — теряет только дальние, которые доедут следующим пересевом.
- «Событие уже идёт!» при опоздании больше 2 минут — **не нужно:**
  уведомление показывает система точно в срок, опоздать может только
  выключенное устройство, и тогда оно покажет пропущенное само.
- **Смахнуть = «✕»** (тишина по вхождению): категория с
  `customDismissAction`; приложение получает смахивание и снимает оставшиеся
  звенья этого вхождения. «Напомнить позже» — действия уведомления с
  выбором шага, как Android; каскад заменяется одним сроком.
- Решение пользователя держится за «начало + название» вхождения — как
  Android §13 (и логика — порт `ReminderPlanner` с его тестами).
- Скрытый календарь снимает свои ожидающие и показанные уведомления.
- Отдельного разрешения на «работу в фоне» и точные будильники на iOS нет —
  нужно только разрешение на уведомления (с `timeSensitive`, чтобы
  напоминание пробивалось через «Фокус» — **проверить**, нужен ли для этого
  entitlement).
