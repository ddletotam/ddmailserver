# Этап 3: ящик локального домена — самостоятельная учётка со своим паролем

Подробный план к этапу 3 `docs/server-admin-split-plan.md` (2026-11-16).

## Как сейчас (разбор кода 2026-11-16)

- `mailboxes` — только адрес: `user_id` владельца, `domain_id`, `local_part`, `enabled`.
  Пароля, своих папок, своей сущности в IMAP/API нет.
- Входящее на ящик (`localdelivery.deliverOne`) пишется владельцу: `user_id` владельца,
  `account_id NULL`, общий INBOX пользователя (`GetOrCreateLocalInbox`). Туда же синк
  складывает письма внешних учёток — одна общая папка на все источники.
- IMAP показывает все локальные папки пользователя (`GetLocalFoldersByUser`), разделения по
  ящикам нет. SMTP разрешает From по `SenderIdentities(user)`: ящики дают `accountID 0`
  (прямая отправка с DKIM), адреса учёток — их SMTP.
- `AuthenticateProtocol` отрезает `@домен` и ищет пользователя по имени: ящики при входе не
  участвуют вовсе.

## Решение: ящик — хранилище-принципал

У каждого ящика своя служебная запись в `users` (`kind = 'mailbox'`, `username` = полный
адрес, свой пароль). Вся почта ящика живёт под её `user_id` — в своих INBOX/Sent/Drafts/
Trash. Тогда без переделки работают:

- **IMAP** вход ящиком: `AuthenticateProtocol` находит принципал по адресу — сессия видит
  ровно его папки (код IMAP уже скоупится по `user_id`).
- **SMTP** вход ящиком: `SenderIdentities(принципал)` = только его адрес, `accountID 0`,
  прямая отправка с DKIM — как сейчас.
- **Доставка**: `localdelivery` кладёт письмо принципалу ящика, а не владельцу.
- **Подключение ящика пользователем** (сценарий «Вася добавляет учётку IMAP/SMTP»): обычная
  внешняя учётка, синк по IMAP к нашему же серверу с паролем ящика. Ничего особенного не
  нужно — так и задумано: Вася не знает, что сервер тот же. Как и у любой внешней учётки, у
  Васи хранится копия (агрегатор копирует всё); квота ящика считает оригинал.
  Оптимизация на потом: синк к самому себе — без сети, прямым чтением базы.

Принципал не входит в веб и API клиентов (как админ — `kind` проверяется в тех же местах),
не получает push. Вход в наше приложение адресом ящика — режим IMAP (шаг 3.4).

## Шаги

1. **Принципалы для новых ящиков.** Миграция: `users.kind` (`user`|`mailbox`, по умолчанию
   `user`), `mailboxes.principal_id` (NULL — ящик по-старому). `AuthenticateProtocol`:
   логин с `@` → сначала принципал ящика с таким адресом, иначе по-старому (отрезать домен).
   Веб/API/push принципалу закрыты. Существующие ящики **не трогаются** (`principal_id
   NULL` → доставка владельцу, как сейчас).
2. **Доставка и отправка для ящиков с принципалом:** `localdelivery`, DSN, self-skip
   прямой отправки, identities — по принципалу; ящики без принципала — по-старому.
3. **Админка (этап 4):** создать ящик = создать принципал с паролем (показать один раз),
   сменить пароль, отключить, удалить (вместе с почтой ящика).
4. **Клиенты:** в наших приложениях адрес ящика → вход по IMAP/SMTP, а не как пользователь
   DDMail (автонастройка `/.well-known/ddmail?address=` отвечает `"kind":"mailbox"`).
5. **Перевод существующих ящиков** (`info@help-it-audit.ru`, `review@mail.letotam.ru` и др.)
   — отдельным действием админа по одному ящику: задать пароль → создаётся принципал →
   новая почта идёт в ящик; владелец подключает ящик учёткой IMAP (старые письма у него
   остаются). Демо-ящик ревью переводить последним, после выхода клиентов с шагом 4.
6. **Переходный режим входа** (старые клиенты и демо-учётка): пока у ящика нет принципала,
   вход адресом работает как вход пользователя (как сейчас). После перевода ящика вход
   адресом — это вход ящика.

Шаги 1–3 не меняют поведение существующих ящиков; меняет только шаг 5, и только по
явному действию админа.
