# Контракт поведения Android-клиента

Договорённости о поведении и устройстве Android-клиента ddmail. Пишется **до кода**
и дальше живёт по тем же правилам, что `desktop-behavior-contract.md`:
**меняешь поведение — правишь этот файл в том же коммите.** Ссылки — на классы и
функции, не на номера строк.

Статус разделов: **решено** — делаем так; **проверить на устройстве** —
решение принято, но держится на допущении о Mate XT/EMUI, которое надо
подтвердить живым телефоном; **открыто** — см. §11.

## 0. Принципы

- **Нативно, без компромиссов.** Kotlin + Jetpack Compose, библиотеки и
  механизмы платформы (Room, WorkManager, Android Keystore, WebView,
  `DnsResolver`, системные уведомления). Кроссплатформенный слой
  (Rust-ядро через FFI, KMP, Flutter) не используется: на телефоне он
  означал бы обход платформенной сети, хранилища сертификатов, фонового
  режима и энергосбережения. iOS — отдельный клиент на Swift.
- **Полноценный клиент.** Цель — функционал десктопа. Почта — с v1;
  календарь, напоминания, задачи и контакты — с 0.0.16 (§12–§16); внешние
  IMAP/SMTP-учётки, CalDAV/CardDAV и несколько учёток — обязательны до
  публикации (решение 2026-11-12), контракт — `mobile-external-accounts.md`.
- **Сервер — источник правды о смысле.** Что такое диалог, кто в нём кто,
  папки диалогов, группы айдентик, ветки отправки — всё это уже определено
  десктопным контрактом и сервером. Android не изобретает свою семантику: где
  десктопный контракт описывает **что** (правило), Android обязан совпадать;
  свободен он только в **как** (жесты, раскладка, системные механизмы).
- **Иконки вместо надписей — правило №1 мобильных клиентов** (решено
  2026-11-09). Кнопки, панели действий, свайпы, FAB, кнопки внутри ленты —
  иконки Material (Android; на iOS — SF Symbols) с `contentDescription` для
  озвучки. Текст остаётся там, где без него смысла нет: заголовки, подписи
  полей ввода, пункты меню (иконка + одно слово), текст подтверждения
  удаления. Символы шрифта и эмодзи вместо иконок не годятся — EMUI рисует
  их мелко и по-своему.
- **Скорость разработки не приоритет.** Решения выбираются по качеству
  результата, а не по быстроте старта.

## 1. Платформа и сборка — решено

- **Код:** `mobile/android/` в этом репозитории (рядом с `desktop/`; будущий
  iOS — `mobile/ios/`). Клиент и сервер делят API, общий репозиторий держит их
  в согласии.
- **Первое устройство:** Huawei Mate XT, глобальная EMUI 14.x, без сервисов
  Google.
- **Один код для Huawei и обычного Android** — два product flavor'а:
  `hms` (HMS Push Kit) и `gms` (Firebase Cloud Messaging). Всё, кроме
  доставки push, общее; flavor-специфичный код — только в модуле push.
- **minSdk 29** (Android 10: `DnsResolver.rawQuery` для MX, §3), targetSdk —
  актуальный на момент сборки.
- **Сборка — вне дерева проекта** (правило workspace): каталог сборки Gradle
  направляется в `~/.cache/builds/` (Linux) и `%LOCALAPPDATA%\builds`
  (Windows) через `buildDir`/`layout.buildDirectory` в корневом скрипте.
- **Установка на телефон — по USB через `adb` Windows.** Беспроводной
  отладки в EMUI 14 нет (в «Для разработчиков» только ADB и HDB). Сборка
  идёт в WSL, APK ставится `adb.exe` из `%LOCALAPPDATA%\Android\platform-tools`
  (USB в WSL не пробрасываем):

  ```bash
  cd mobile/android && ./gradlew assembleHmsDebug
  cp ~/.cache/builds/gradle/ddmail-android/app/outputs/apk/hms/debug/app-hms-debug.apk \
     /mnt/c/Users/<user>/.cache/ddmail-apk/
  adb.exe install -r 'C:\Users\<user>\.cache\ddmail-apk\app-hms-debug.apk'
  adb.exe exec-out screencap -p > shot.png   # скриншот с телефона
  ```

  Кабель — короткий, в порт на материнской плате: через передние порты
  соединение рвалось при движении телефона. Станции нужны JDK 17
  (`org.gradle.java.home` в `~/.gradle/gradle.properties`, если в системе
  только JRE) и SDK (`local.properties` → `sdk.dir`, не в git).
- **Версия** — `versionName`/`versionCode` в `app/build.gradle.kts`; бампается
  при любой правке клиента, как у десктопа.

### Модули

| Модуль | Что внутри |
|---|---|
| `:app` | Activity, навигация, экраны Compose, адаптивная раскладка (§6) |
| `:core:api` | HTTP-клиент `/api/desktop/v1` (OkHttp + kotlinx.serialization), WebSocket, refresh токена |
| `:core:db` | Room: схема кэша, DAO, миграции |
| `:core:sync` | движок синхронизации (§4), доменные типы, папки диалогов (порт `folders.rs`) |
| `:core:auth` | вход, хранение токена (Keystore), автонастройка (§3) |
| `:push:hms` / `:push:gms` | регистрация токена устройства и приём push, по flavor'у |

Документ ленты беседы (JS + CSS: шаблон, нормализатор, мост) — вне модулей,
в `mobile/shared/conversation-doc/`, общий с будущим iOS-клиентом (§8);
`:app` кладёт его в assets при сборке.

## 2. API и сессия — решено

- Клиент говорит с тем же `/api/desktop/v1`, что десктоп. Отдельного
  «мобильного» API не заводим, пока не понадобится то, чего в нём нет
  (первое такое — регистрация push-токена, §7).
- **Вход** — `POST /auth/login` (`username` + `password`) → JWT. Пароль не
  хранится нигде: только токен.
- **Токен** живёт 24 часа; `POST /auth/refresh` обменивает и просроченный, но
  не старше 30 суток от выдачи (`maxRefreshAge`). Каждый refresh выдаёт новый
  токен с новой датой — при регулярном использовании (а push будит клиент,
  §7) вход заново не нужен.
- **Хранение токена** — DataStore, значение зашифровано AES-GCM ключом из
  Android Keystore (ключ не покидает аппаратное хранилище). Устаревшую
  `EncryptedSharedPreferences` не используем.
- **Отказ refresh (401/403) — состояние «нужен вход»**, отдельное от «нет связи»
  (как §5д-бис десктопа): ретраи его не лечат. Показывается несмываемой
  плашкой над содержимым с кнопкой «Войти»; кэш при этом виден. Снимают
  состояние только удачный вход или удачный refresh.
- **Классификация ошибок:** 401 → нужен вход (после неудачного refresh);
  **403 — не «нужен вход»**: им сервер отказывает в конкретном действии при
  живой сессии («календарь только для чтения», «адрес отправителя не ваш») —
  это ошибка действия с текстом сервера (`ApiException.Server`). До 0.0.16
  403 считался мёртвой сессией, и попытка записать в календарь только для
  чтения выкидывала бы на вход. Исключение — сам `/auth/refresh`: его отказ
  любым кодом = нужен вход. Таймаут, 5xx, обрыв → временное, повторяем с
  бэкоффом.
- **WebSocket** `/ws` — пока приложение на экране (§7). **Токен — заголовком
  `Authorization: Bearer`**, как у REST: OkHttp задаёт заголовки рукопожатия
  WS. Ограничение «заголовки не задать» есть только у браузерного API, и
  `?token=` в URL — его наследство: строка запроса оседает в access-логе
  nginx, то есть живые JWT лежат в логах. Сервер принимает заголовок
  (`wsToken` в `handlers_desktop_ws.go`, выкачен 2026-11-09), `?token=` оставлен на переходный период — Android пока шлёт
  токен и так, и так; после выкатки и перевода десктопа на заголовок query
  убрать из обоих.

## 3. Подключение (первый запуск) — решено

- Повторяет логику десктопного визарда (§5г-бис десктопа), в v1 — только
  ddmail-учётка:
  1. Вводится email.
  2. Ищется сервер ddmail: `GET https://<хост>/.well-known/ddmail` на
     `mail.<домен>`, `<домен>`, затем на MX-хостах. MX — через
     `android.net.DnsResolver.rawQuery` (системный резолвер, работают и
     внутренние домены). Прогресс — от верхней границы числа проверок.
  3. Найден — экран входа: адрес сервера, логин (подставлена часть адреса до
     `@`, редактируется), пароль.
  4. Не найден — ручной ввод адреса сервера.
- **Только https.** Сертификат проверяется системным хранилищем, **включая
  CA, установленные пользователем** (`network_security_config`:
  `<certificates src="system"/>` и `<certificates src="user"/>`), — как на
  десктопе, который доверяет хранилищу ОС целиком. Иначе сервер за
  корпоративным CA на телефоне не открылся бы.
- Пароль при поиске никуда не уходит.

## 4. Синхронизация — решено

Повторяет модель десктопного native-провайдера; кэш — Room.

- **Список бесед:** `GET /conversations?limit=N&since=<server_now_ms>`. `since=0`
  — полная выдача, заменяющая набор целиком; дальше — дельты по водяному
  знаку `server_now_ms` из ответа.
- **Удаления и всё, чего дельта бесед не сообщает** — журнал
  `GET /changes?since=<seq>`. `reset: true` (курсор старше нижней границы
  журнала или первый запуск) → полная пересинхронизация.
- **Версия формата id бесед** хранится в `meta` кэша (аналог
  `CONV_ID_EPOCH` десктопа); при несовпадении следующий синк — полный.
  Формат id задаёт сервер, клиент его не разбирает.
- **Тела писем качаются заранее** (§4а-бис десктопа): новые письма всех бесед
  оказываются на диске до того, как беседу откроют; открытие рисует из кэша.
  Порядок — от свежей беседы к старой; фоновая докачка уступает любому
  действию пользователя. Вложения заранее **не** качаются — только тела.
- **Можно ли подкачивать — решает пользователь.** После первого входа —
  один вопрос «Загружать письма заранее?» с тремя ответами: «Всегда»,
  «Только по Wi-Fi», «Нет, при открытии». Ответ по умолчанию не выбран —
  трафик чужой, решать не нам. Изменить — «Настройки → Загрузка писем».
  «Только по Wi-Fi» — докачка идёт под ограничением WorkManager
  `NetworkType.UNMETERED`; на мобильной сети открытие беседы качает её тела
  по требованию. «Нет» — всегда по требованию. Список бесед и дельты
  синхронизируются при любом ответе: они маленькие и без них нет
  уведомлений.
- **Когда синхронизируемся:** при открытии приложения; по каждому событию WS
  (пока на экране); по push (§7); по `WorkManager` периодически раз в
  ~30 мин как страховка от потерянного push (ограничения ОС решают точное
  время).
- **Пустое тело** (нет HTML, текста и вложений) считается непригодным и
  перезапрашивается при открытии беседы (§4а десктопа).
- Мутации (флаги, удаление, спам) — оптимистично в кэше, затем запрос; при
  отказе — откат и сообщение.

## 5. Почта: что берём у десктопа как есть

Правила, на которые Android **обязан** совпадать с десктопом (ссылки — на
разделы `desktop-behavior-contract.md`):

- **Диалог = набор адресов** (§4 «Чем опознаётся диалог»), id — от сервера.
- **Роли в диалоге** — собеседники и айдентика (§4 «Роли»).
- **Папки диалогов — табы над списком** (§4 «Папки диалогов»): таба «Все»
  нет, ничего не выбрано = инбокс; выбранный таб помнится. Набор табов
  общий с десктопом (`/dialog-folders`).
- **Ветки отправки** (§1): пересылка / новое / явный ответ / неявный ответ;
  непустое «Кому» и непустая тема побеждают авто-деривацию; письмо из одного
  вложения — валидное.
- **Optimistic send** (§2): мгновенный пузырь, reconcile с настоящим письмом,
  «✓ Отправлено» без тоста, при ошибке пузырь убирается, текст возвращается.
- **Уведомления** (§5): только реальное входящее (не спам, не iTIP, не своё);
  читаешь этот диалог — без уведомления, тихо дописать.
- **Спам** (§5а) и группы айдентик (§1в) — та же семантика, что на сервере.
- **Открыт на старте** — диалог, на котором закончили (§4 «Какой диалог
  открыт на старте»), на раскладках, где беседа видна сразу (§6).
- **Локальный поиск по диалогам** (как «Диалоги» в выпадашке десктопа, §4
  «Поиск»): по имени диалога (в том числе своему), адресу любого участника и
  теме последнего письма; порядок — имя, адрес, тема; по всем папкам.
  Поиск — в памяти, регистр складывается в Kotlin (кириллица складывается
  правильно; у `LOWER` SQLite этого нет). FTS не понадобился: тысячи бесед
  фильтруются мгновенно. Темы всех закэшированных тел (как у десктопа) —
  следующим шагом. Серверный поиск по сообщениям — не в v1.
- **Цвет строки — группа адреса получателя** (десктоп §1в): строка в покое
  залита пастелью группы, в которую входит `received_by` беседы; пустой
  `color` группы — палитра `IDENT_PASTEL` по индексу группы, `user+tag@`
  без своей записи — цвет `user@`, адрес вне групп — серый `#d5d5d0`.
  Документ групп — `/identity-groups` (только чтение; правка групп — на
  десктопе), кэш в meta, обновляется каждым синком (а синк будит и
  `identity_groups_changed` по WS). Открытая беседа — сплошной `#10b981` с
  белым текстом, как выделение на десктопе (светлое выделение на зелёной
  пастели не видно); отмеченная при множественном выборе — голубая с ✓.
  Толкование — `IdentityColors.kt` с тестами.
- **Аватарки** — `/avatars?email=` первого собеседника, кэш в памяти и на
  диске, «нет аватара» запоминается на неделю; SVG (BIMI) не рисуются —
  инициалы.
- **Картинки по отправителю:** под письмом «Показать картинки (N)» (это
  письмо, до закрытия беседы) и «Всегда от <адрес>» (запоминается на
  телефоне). При разрешении позиция ленты удерживается, пока грузятся
  картинки.
- **Вложения:** касание — открыть; долгое нажатие — «Открыть» / «Сохранить
  в «Загрузки»» (MediaStore, без разрешений).
- **Свои имена и аватарки диалогов — на сервере** (решено 2026-11-08), общие
  для всех устройств, как папки диалогов. Сейчас они живут только в
  десктопном `merges.json` и файлах `avatars/`; переезд — серверная задача и
  задача десктопа (локальные при первом подключении уезжают на сервер, как
  было с папками). Android их показывает и правит (меню шапки беседы, §9).
- **Ручное «В папку» и «Убрать из папки»** — та же семантика `assign`, что
  у десктопа (§4 «Папки диалогов»): диалог строго в одной папке, ручное
  назначение побеждает правила, «убрать» вносит в `exclude` ловящих папок.
  Документ папок общий (`/dialog-folders`, версия + `409` при чужой правке).
- **Папки толкуются в `DialogFolders.kt` — портом `folders.rs` десктопа**,
  с теми же тестами: документ общий, смысл обязан совпадать. Ключ ручного
  назначения — `{account, id}`, где `account` = `логин@хост` (как
  `account_key` десктопа, иначе назначения с десктопа не узнаются).
- **Папка «Спам»** — та же системная папка, что у десктопа (§4 десктопа,
  `system = "spam"`), порт `withSpam()`; Android всегда подключён к серверу
  ddmail, поэтому она есть всегда. Вход — пункт «Спам» в меню шапки (таба
  нет, пока в неё не перешли). Спам — отдельный полный список
  (`/conversations?spam=1`) в пространстве кэша `<account>#spam`; в поиск,
  уведомления и бейдж не попадает. В «Спам» нет жестов, панель выбора — только
  «Выбрать все», «Не спам» (`/spam/restore`, письма во «Входящие») и «Не спам
  и доверять отправителю» (тот же запрос с `"trust": true`: сервер заводит
  allow-правило на адрес отправителя и возвращает из спама всё остальное от
  него; оно уходит из «Спам» со следующим синком). Обе — иконками (0.0.21).
- **Спам не зазывает и не ходит в сеть** (0.0.21). Число непрочитанных не
  показывается ни в строках «Спам», ни на её табе (жирность остаётся).
  Аватарки спама не запрашиваются — только инициалы: `/avatars` ходит на
  домен отправителя (favicon, BIMI), то есть по сигналу спамера. Внешние
  картинки письма спама — только по плашке «Показать картинки (N)» на это
  письмо и этот показ беседы: разрешение живёт в памяти (`RemoteImageGate`) и
  забывается с открытием другой беседы; «Всегда от <адрес>» у спама нет, и
  сохранённые разрешения по отправителю на спам не действуют. Блокирует
  перехватчик WebView, а не только чистка HTML: у беседы спама `/remote`
  пропускается, только если письмо (`uid` в запросе) разрешено и запрос —
  за картинкой (`Sec-Fetch-Dest: image`, иначе `Accept` с `image/`); шрифты,
  стили и прочее — 403. Прочие внешние адреса перехватчик режет всегда
  (§8). Нормализатор у спама дополнительно вырезает `@import` и `@font-face`.
- **«В спам»** (0.0.22, как §5а десктопа) — иконкой в панели множественного
  выбора и в шапке открытой беседы (у бесед спама её нет). Подтверждение
  называет число бесед и писем и даёт два ответа: «Адрес» (этот отправитель)
  и «Домен» (против спамеров с меняющейся частью до `@`). Запрос —
  `/spam/blacklist-and-purge` с серверными id писем: отправителя сервер
  берёт из самих писем, а не из участников беседы (в BCC-рассылке среди них
  есть получатель). Беседы уходят из списка сразу, следующий синк полный;
  итог — Snackbar «✓ В спам: домен …, удалено писем: N». До 0.0.22 действия
  не было: в объём v1 «спам» вошёл только папкой и «Не спам».
- **Скрытые папки** (`hidden`) — таба нет, их диалоги не видны нигде;
  «Показать скрытые» в v1 нет. **«Письма сразу прочитаны»** (`auto_read`)
  исполняет десктоп, Android флаги по этому правилу не ставит — иначе две
  станции метили бы одно и то же наперегонки.

### Склейки диалогов — не переносятся

Склейка (`merges.rs`) на десктопе устарела (deprecated, десктопный контракт
§4 «Склеенный диалог»): группировку делают папки. В Android её нет. Следствие:
диалог, склеенный на десктопе, на телефоне виден своими членами по
отдельности; ручное назначение в папку у склейки висит на ключе её
первичного, поэтому остальные члены на телефоне лежат там, куда их кладут
правила, обычно во «Входящих».

### Множественный выбор диалогов (bulk) — решено

- **Вход в режим выбора** — долгое нажатие на строку списка; она становится
  первой выбранной. Дальше касание строки добавляет/снимает её. Выход —
  «Назад», крестик в панели действий или снятие последней выбранной.
- **Панель действий** заменяет шапку списка на время выбора: счётчик
  «Выбрано: N», «Выбрать все» (в пределах текущего таба), действия.
- **Действия:**
  - **«Прочитано» / «Непрочитано»** — «непрочитано» ставит последнее
    письмо беседы снова непрочитанным (локально сразу, на сервере следом).
  - **«В папку…»** — список папок (включая скрытые, как `folder-targets`
    десктопа) и «Убрать из папки». Одна запись документа папок на все
    выбранные, не N записей: N подряд идущих `PUT` упёрлись бы в `409` друг
    с другом.
  - **«Удалить»** — все письма выбранных диалогов (`/messages/delete`), с
    подтверждением, в котором названо число диалогов и писем. После
    удаления — Snackbar «Удалено N» без отмены. Сервер удаляет мягко (в
    vault, `messages.Service.Delete`), но API восстановления у клиента нет,
    а у внешних учёток удаление сразу ставится в очередь на исходный сервер
    — поэтому подтверждение до, а не «отменить» после.
- Выбор переживает смену раскладки (§6) и не переживает смену таба: другой
  таб — другой набор строк, выбор снимается.
- Дельта, пришедшая во время выбора, не сбивает его: выбор хранится по id
  диалога, а не по номеру строки (как контекстное меню десктопа).
- **Десктоп получает тот же множественный выбор** (решено 2026-11-08) —
  с теми же действиями и той же семантикой (одна запись документа папок,
  подтверждение удаления); отличаются только жесты: там Ctrl/Shift+клик.

## 6. Раскладка — решено

Раскладка выбирается по **ширине окна** (`WindowSizeClass`), а не по модели
телефона и не по состоянию шарнира: так она же работает на обычных
телефонах, планшетах и в многооконном режиме.

Размеры окна приложения на Mate XT (GRL-LX9, Android 12 / API 31, 460 dpi)
— замерены на устройстве 2026-11-08, `Configuration.screenWidthDp/HeightDp`:

| Состояние | Окно, px | Окно, dp | Класс ширины | Раскладка |
|---|---|---|---|---|
| Сложен | 1008 × 2232 | **350 × 739** | Compact | табы + список; беседа открывается поверх списка (без шапки приложения — у беседы своя, с «←»), «Назад» возвращает |
| Два экрана | 2048 × 2232 | **712 × 739** | Medium | табы + список и беседа рядом |
| Три экрана | 3184 × 2232 | **1107 × 739** | Expanded | то же; беседа шире (альбомная ориентация) |

Клавиатура EMUI в разложенном виде занимает ~85% высоты: пока она больше
половины окна, шапки (приложения и беседы) прячутся, остаётся строка ввода.
В сложенном виде клавиатура — около трети, шапки остаются.

Высота во всех состояниях одна — 739 dp; меняется только ширина. Смена
состояния Activity не пересоздаёт (`configChanges` в манифесте) — проверено:
цифры на экране меняются на месте.

- **Табы папок — наверху во всех состояниях**, над списком, как на десктопе.
- **Смена состояния не теряет контекст:** открытая беседа, позиция списка,
  черновик композера и выбранный таб переживают пересоздание Activity и смену
  раскладки (state в ViewModel/`SavedStateHandle`). Сложили телефон с
  открытой беседой — видна беседа, «Назад» ведёт в список.
- **Шарнир:** если ОС сообщает `FoldingFeature` с разделением
  (`isSeparating`), граница между списком и беседой ставится на шарнир, а не
  поперёк него — **проверить на устройстве**, сообщает ли EMUI это для Mate XT.

## 7. Push и фон — решено, механику HMS проверить на устройстве

- **Пока приложение на экране** — WebSocket, как у десктопа; события
  (`new_message`, `flags_changed`, `expunge`, `dialog_folders_changed`,
  `identity_groups_changed`, `auth_failed`) запускают синк.
- **В фоне — push.** Постоянного foreground-сервиса с WS нет.
- **Пока push нет (v0.0.6)** — `SyncWorker` (WorkManager) раз в ~15 минут
  (меньше Android не даёт; точное время решает ОС, EMUI может придерживать
  дольше): синхронизация, уведомления, докачка тел. С push он остаётся
  страховкой от потерянного push. Пока приложение на экране, фон
  пропускает проход — синхронизирует экран (и WebSocket), второй движок
  гонялся бы с ним за кэш.
- **Уведомления** собираются на телефоне из кэша: «новое» — непрочитанные
  письма с uid больше последнего, о котором уже уведомили; первый проход
  только запоминает рубеж. Не уведомляем об открытой беседе и о скрытых
  папках. Нажатие открывает беседу (с переходом в её папку).
- **Push не несёт персональных данных** (152-ФЗ: push идёт через серверы
  Huawei/Google за рубежом — передача ПДн третьему лицу и трансграничная).
  В push — только факт «есть изменения» (и, возможно, непрозрачный счётчик).
  Отправитель, тема, адреса в push **не кладутся никогда**; текст
  уведомления клиент собирает сам после синка, из своего кэша.
- **Сервер:** регистрация токена устройства (новый эндпоинт, вне v1-API
  десктопа), хранение токенов по пользователю и flavor'у, отправка через HMS
  Push REST API (OAuth client credentials) при новом письме. Токены, которые
  HMS отвергает как недействительные, удаляются.
- **Проверить на устройстве:** доходит ли data-сообщение HMS до
  остановленного приложения на EMUI 14. Если нет — запасной путь:
  notification-сообщение с **обезличенным** текстом («Новые письма»),
  которое показывает сама система; нажатие открывает приложение и запускает
  синк. Какой путь основной — решаем по результату проверки.
- Подготовка со стороны пользователя: аккаунт разработчика Huawei, проект в
  AppGallery Connect с Push Kit, `agconnect-services.json`.
- **Секреты сборки — вне git:** `agconnect-services.json`, `google-services.json`
  (flavor `gms`) и ключ подписи APK лежат в `~/.config/ddmail-android/` на
  каждой станции (на Windows — `%APPDATA%\ddmail-android\`); Gradle берёт их
  оттуда. Нет файла — сборка соответствующего flavor'а падает с понятной
  ошибкой, а не собирает APK без push.

## 8. Отображение писем — решено

### Почему так: замер (2026-11-08)

Агрегаты по ящику на сервере (3870 писем, один пользователь; содержимое не
выводилось — только числа):

| Что | Значение |
|---|---|
| С HTML / только текст | 3236 / 634 |
| Размер HTML: медиана / p90 / p99 / max | 9 КБ / 34 КБ / 330 КБ / 1 МБ |
| Доля разметки в HTML | 93% (видимого текста: медиана 0,9 КБ) |
| Фиксированная ширина ≥ 480 px | 47% писем с HTML |
| Вложенные таблицы | 59% |
| Внешние картинки / трекинг-пиксели 1×1 | 45% / 19% |
| `<script>` в теле | 15% |
| Есть цитата | 3%; у таких цитата — в среднем 83% текста |
| Писем в беседе: медиана / p90 / p99 / max | 1 / 3 / 47 / 426 |

Беседы посчитаны приближённо, по набору адресов. Выводы: половина писем
свёрстана под фиксированные ~600 px — без масштабирования на узком экране они
либо уезжают вбок, либо разваливаются; «простых» писем, которые можно было бы
рисовать нативно, меньшинство — отдельной нативной формы нет; чистка
обязательна; беседы обычно короткие, но хвост длинный.

### Один WebView на беседу

- **Лента пузырей открытой беседы — один документ в одном WebView**, а не
  WebView на письмо: WebView — это десятки МБ и заметное время на создание,
  в беседе на 50 писем так не жить. Прецедент — беседа в Gmail для Android
  (один WebView, нативные элементы поверх).
- **Экземпляр один и переиспользуется:** создаётся заранее при старте
  приложения, при открытии беседы меняется только документ. Создание
  WebView в путь открытия не входит.
- **Окно отрисовки:** сначала — последние ~20 пузырей, старые
  подгружаются порциями при прокрутке вверх с удержанием позиции (вставка
  сверху не сдвигает то, на что смотрят). Новое письмо дописывается в конец
  без перестройки документа.
- **Нативное — всё вокруг ленты:** шапка беседы, композер, панели, меню.
  Долгое нажатие на пузырь, клик по ссылке, по чипу вложения, по адресу
  уходят через мост (`addJavascriptInterface` / `WebMessagePort`) в нативный
  код: меню — нативное, ссылки — во внешнем браузере
  (`Intent.ACTION_VIEW`), вложения — §9.

### Изоляция письма — Shadow DOM на пузырь

- Каждое письмо — в своём shadow root: CSS письма не выходит наружу, наш —
  не проникает внутрь. На десктопе документ общий, и стили писем (`class="row"`,
  `time`, `inner`…) ломали обвязку пузыря, пока все её классы не получили
  префикс `ddm-` (десктопный контракт §4б). Здесь граница структурная,
  префиксы и выверенная специфичность не нужны.

### Безопасность

- **JavaScript в WebView включён — но только наш.** Документ несёт
  Content-Security-Policy: скрипты — только с nonce нашего документа,
  `unsafe-inline` нет, значит инлайн-обработчики (`onclick`, `onload`…) и
  `javascript:`-ссылки не исполняются. Чужие `<script>` вырезаются ещё до
  вставки (каждое седьмое письмо их несёт); CSP — второй рубеж, не первый.
- **Сеть — только через перехват** `shouldInterceptRequest`: внешние ресурсы
  по политике отправителя (та же модель, что у десктопа: медиа/скрипты по
  отправителю, разрешённые домены); по умолчанию не грузятся. `cid:` —
  из частей письма (`/messages/{id}/parts/{cid}`). Трекинг-пиксели
  вырезаются всегда, независимо от политики.
- Файловый доступ WebView выключен (`allowFileAccess`, `allowContentAccess`
  = false); документ грузится с собственного фиктивного https-источника
  через `WebViewAssetLoader`, а не `file://`.

### Нормализатор — в клиенте, на JS внутри документа

- **Нормализация живёт в клиенте, для любой учётки.** У учётки на обычном
  IMAP нашего сервера нет, значит серверная нормализация не может быть
  единственной, а держать две (на сервере и в клиенте) — значит держать две
  одинаковыми. Сервер нормализацию не делает.
- **Пишется на JS и выполняется в документе беседы** — работает с тем самым
  DOM, который будет нарисован, с реальными ширинами. Тот же код без
  изменений исполнит WKWebView в iOS-клиенте: каждая платформа своим
  штатным движком, функционал одинаковый — правило §0 не нарушается.
  Исходник один: `mobile/shared/conversation-doc/` (JS + CSS шаблона),
  клиенты кладут его в свои ресурсы при сборке.
- **Порядок для каждого письма:**
  1. **Чистка** — разбор в инертный документ (`DOMParser`/`<template>`, где
     ничего не исполняется), удаление `script`, `iframe`, `object`, `embed`,
     `form`, обработчиков `on*`, `javascript:`-URL, внешних `<link>`,
     трекинг-пикселей; только потом — вставка в shadow root.
  2. **Цитаты** — `blockquote`, `gmail_quote`, `divRplyFwdMsg`,
     `moz-cite-prefix`, текстовые «-----Original Message-----» /
     «Пересылаемое сообщение» сворачиваются в «…»; нажатие разворачивает.
     Цитата в начале письма (ответ сверху) и в конце сворачиваются
     одинаково.
  3. **Ширина** — у письма с фиксированной вёрсткой шире пузыря
     **масштабирование целиком** (`transform: scale` по измеренной ширине,
     высота контейнера пересчитывается), а не линеаризация: в линеаризованной
     таблице цифры теряют связь со столбцами (замер на десктопе, §4б).
     Нажатие на масштабированный пузырь открывает письмо во весь экран с
     зумом. Письмо уже пузыря не трогается.
  4. **Длинные слова и URL** — `overflow-wrap: anywhere` внутри пузыря.
  5. **Картинки** — `max-width: 100%` у не масштабированных писем; до
     разрешения внешние картинки заменены местом-заглушкой с размером из
     атрибутов (вёрстка не прыгает после загрузки).
- **Результат нормализации кэшируется** в Room рядом с телом (с версией
  нормализатора — сменилась версия, кэш пересчитывается, как
  `RENDER_TEMPLATE_EPOCH` у десктопа), чтобы повторное открытие не гоняло
  разбор заново.

### Как сделано (v0.0.4)

- **Источник документа** — `https://appassets.androidplatform.net`
  (`WebViewAssetLoader`), не `file://`. Перехватчик (`ConversationWeb`)
  отдаёт только: `/assets/…` (документ), `/cid/<uid>/<cid>` (части письма с
  сервера), `/remote?uid=…&u=…` (внешняя картинка через прокси приложения;
  у спама — только разрешённым письмам, §5 «Спам»); всё остальное — 403. CSP документа: `script-src 'self'`, `img-src 'self' data:`.
- **Внешние картинки** — по кнопке «Показать картинки (N)» под письмом, на
  это письмо и до закрытия беседы; политика по отправителю (как у десктопа)
  — следующим шагом. Прокси ходит без наших заголовков и кук, только
  `image/*`, не больше 10 МБ.
- **Окно отрисовки** — по 20 писем; «последние» — по uid (у ссылок нет
  дат, а качать тела всей беседы ради сортировки — сотни писем на
  открытии). Внутри порции — по дате. Прокрутка — к первому непрочитанному,
  иначе в конец.
- **Открытие беседы ставит `\Seen`** — локально сразу, на сервере следом.
- **Вложения** — скачать в кэш и открыть системным обработчиком через
  `FileProvider`; «Сохранить в Загрузки» (MediaStore) — следующим шагом.
- **Масштаб широких писем** — `zoom` по измеренной ширине, пересчёт на
  смене размера окна (складывание). Отдельного полноэкранного просмотра
  пока нет — вместо него масштаб жестом всего документа.
- Позиция ленты при «Показать картинки» удерживается (якорь — низ пузыря,
  15 с, пока грузятся картинки).

### Сервер — только оптимизации для учёток ddmail

- Нормализация от сервера не зависит. Сервер может (не в v1) отдавать
  картинки, ужатые под ширину экрана, — чистая экономия мобильного трафика,
  путь отрисовки от неё не меняется.

   возвращается на место):
   - **вправо** — «Прочитано» / «Непрочитано» (переключатель): частое,
     обратимое, без подтверждения;
   - **влево** — «В папку…»: открывает тот же выбор папки, что и у
     множественного выбора;
   - **удаления и спама свайпом нет:** удаление необратимо (§5), а свайп
     легко сделать случайно — только через выбор/меню с подтверждением.

### Решено по итогам вычитки (2026-11-08)

- Свои имена и аватарки диалогов — на сервер (§5).
- Пользовательским CA доверяем (§3).
- Секреты сборки — `~/.config/ddmail-android/` (§7).
- Локальный поиск по диалогам — в v1 (§5).
- Подкачка тел — выбор пользователя при первом входе и в настройках (§4).

## 12. Календарь — решено (0.0.16)

- **Вид — как у Apple** (решение пользователя 2026-11-09): сложен (Compact)
  — как iPhone, разложен — как iPad.
  - **iPhone:** лента месяцев (`CompactMonths`, вертикальная прокрутка,
    название месяца над столбцом его первого числа), под числом — точки
    событий цветом календаря (до трёх). Тап по дню — день (`CompactDay`):
    полоса недели сверху (свайп — соседняя неделя), шкала времени (свайп —
    соседний день), «‹ Месяц» — назад к ленте. Системное «Назад» из дня —
    к ленте.
  - **iPad:** боковая панель от 840 dp (мини-месяц + список календарей),
    сверху — заголовок, ‹ ›, «сегодня», переключатель День / Неделя / Месяц /
    Год (иконки, §0). На 712 dp панели нет — список календарей в диалоге.
    Месяц — сетка с названиями событий; Год — 12 мини-месяцев.
  - «Сегодня» — красным (как в iOS), линия «сейчас» на шкале — тоже.
- **Данные — окнами по месяцу** (`/calendar-events?from&to`, с запасом в
  сутки с каждой стороны: даты «весь день» лежат в полночь UTC). Месяц
  знает только свои дни; многодневное событие приходит в обоих месяцах.
  Перечитывается всё загруженное: на возврат в приложение, по WS
  `calendar_updated`, после своей правки.
- **Развёртка повторов — на клиенте** (`Recurrence`, тот же поднабор RRULE,
  что `recurrence.rs`: DAILY/WEEKLY/MONTHLY/YEARLY, INTERVAL, COUNT, UNTIL,
  BYDAY у WEEKLY; EXDATE учитывается). **Отличие от десктопа намеренное:**
  шаг считается по стенным часам пояса телефона, а не по UTC — иначе
  еженедельное «по понедельникам в 01:00 МСК» (в UTC — воскресенье)
  раскладывалось бы на вторники. Тест `bydayUsesLocalWallClock`.
- **«Весь день»:** полночь UTC читается как дата UTC, прочее — как местная
  дата (`Occ.dateOf`); конец исключён. Новые такие события клиент пишет
  местной полночью — как десктоп (`parts_to_ms`).
- **Видимость календаря — только на этом телефоне** (как десктоп §5г):
  `CalendarPrefs.hidden`, серверный `enabled` не трогается; скрытый не
  рисуется и не звонит (§13).
- **Карточка события** (нижний лист): время, повтор словами, место (ссылкой,
  если это ссылка), ссылки на видеовстречу (`EventLinks` — правила §5в
  десктопа: голый хост — только полем целиком или с `www.`), напоминания,
  ответ на приглашение (принять / под вопросом / отклонить — иконки, только
  если я среди участников и календарь записываемый), участники с отметкой
  ответа, описание.
- **Календарь для новых событий — только назначенный пользователем**
  (звезда в списке календарей, `CalendarPrefs.defaultCalendar`). Не назначен —
  форма не выбирает сама и не сохраняет без явного выбора (чипы календарей
  стоят сразу под названием). Раньше молча брался первый записываемый по
  алфавиту — на этом аккаунте это рабочий календарь, и личное событие ушло бы
  на корпоративный сервер, где его видят коллеги.
- **Клавиатура в тесноте** (разложен: EMUI-клавиатура ~85% высоты) — форма
  события и контакта без полей вокруг и без шапки, видно поле ввода; «Готово»
  клавиатуры её закрывает, шапка с «Сохранить» возвращается (`ui.imeCrowds`).
- **Форма события** — по подтверждению, как §5б-бис десктопа: кнопки гаснут
  на время запроса, закрывается только по успеху, отказ — текстом в форме.
  Нет записываемых календарей — сохранить нельзя, и это видно сразу.
  Повторяющееся: «все повторы» (мастер сдвигается на ту же разницу, что и
  вхождение) или «это и следующие» (`scope=future`); «только это» сервер
  пока не умеет. Удаление повторяющегося — вся серия, о чём предупреждает
  подтверждение.
- **Перенос на шкале:** долгое нажатие на событии записываемого календаря и
  ведение — перенос (шаг 15 мин; в неделе — и между днями), за нижнюю кромку
  (12 dp) — растяжение. Повторяющиеся драгом не двигаются — только через
  форму, где выбирается охват. Долгое нажатие на пустом месте — новое событие
  на этом получасе; в месяце iPad — долгое нажатие на дне.

## 13. Напоминания — решено (0.0.16)

- **Модель — десктопная** (`reminders.rs`, спецификация 2026-07-11), логика
  без Android — `ReminderPlanner`, тесты рядом. Каскад — VALARM'ы события
  (`alarm_leads`, по убыванию); звено сработало → уведомление «Скоро: …» и
  взводится следующее; к началу — «Наступило: …»; опоздали больше чем на
  2 минуты — «Событие уже идёт!», остальной каскад гасится; событие уже
  кончилось — молча.
- **Смахнуть уведомление = «✕»**: тишина по этому вхождению навсегда.
  «Напомнить позже» (действие уведомления) — выбор шага, который ложится до
  начала (1 мин … 1 д), и «в момент начала»; каскад заменяется одним сроком.
  Тап — событие в календаре; уведомление «Скоро» при этом остаётся.
- **Решение пользователя держится за логическое вхождение** «начало +
  название», а не за id события — сервер может пересоздать событие с новым
  id. Два одинаковых события в разных календарях звонят один раз.
- **Посев** — окно `[сегодняшняя полночь, +8 суток)`, отдельно от того, что
  на экране: на запуске, по `calendar_updated`, после своей правки и в
  фоновом `SyncWorker` (~15 мин, и при открытом приложении). Вхождения
  окна, которых события больше не производят (перенос, удаление, EXDATE),
  удаляются вместе с висящими уведомлениями. «Весь день» не звонит.
- **Скрытый календарь** снимает свои напоминания целиком (и висящие
  уведомления); включили обратно — пересев из последнего снимка без сети.
  В момент срабатывания видимость проверяется ещё раз.
- **Будильник — один, на ближайший срок**, `setExactAndAllowWhileIdle`
  (срабатывает в Doze). Точные будильники: `SCHEDULE_EXACT_ALARM` до
  Android 12 включительно, `USE_EXACT_ALARM` с 13. Перезагрузка, обновление,
  смена времени/пояса — перевзвести (`RescheduleReceiver`, экспортирован,
  но умеет только это; срабатывание и смахивание — `ReminderReceiver`, не
  экспортирован, иначе чужое приложение могло бы глушить напоминания).
- **Работа в фоне** (`BackgroundWork`): системный диалог «не ограничивать»
  (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`; в AppGallery разрешено) и, на
  Huawei, «Диспетчер запуска» EMUI — его программно не переключить. На EMUI 14
  (Mate XT) его экран закрыт для сторонних приложений (интент под
  разрешением, проверено 2026-11-09), поэтому открывается «Батарея», где он
  пунктом: у ddmail выключить переключатель, в окне «Управление вручную» —
  OK (автозапуск, косвенный запуск, работа в фоне включены по умолчанию). Спрашивается один раз при первом заходе в календарь и живёт в
  настройках. Проверено на Mate XT 2026-11-09 (0.0.17): точный
  будильник срабатывает в срок (`exactAllowReason=permission`), «напомнить
  позже» перевзводит, после обновления приложения будильник на месте.
- Выключатель напоминаний — в настройках; выключение снимает всё взведённое.

## 14. Задачи — решено (0.0.16)

- Как §5е десктопа: отдельный раздел, окна по времени нет (забираются все),
  выполненные скрыты — тумблер меняет запрос к серверу
  (`include_completed=1`); галочка оптимистична, отказ откатывает строку.
- Срок: красный — просрочено, янтарный — сегодня, серый — остальное;
  выполненная теряет красноту сразу. Строки коллекций только для чтения на
  галочку не реагируют. «Ещё грузится» и «правда пусто» различаются.
- Создавать задачи сервер пока не умеет (нет эндпоинта) — и клиент тоже.

## 15. Контакты — решено (0.0.16)

- Одна сводная книга, как её отдаёт сервер (`/contacts`): источник наружу не
  показывается. Поиск — локальный по имени, организации, адресам, цифрам
  телефона; буквенные заголовки липкие.
- Карточка: аватар (та же цепочка `/avatars`, что у бесед), «написать»
  (новое письмо в почте с этим адресом) и «позвонить» (набор номера, без
  разрешения на звонки). Разложен — список и карточка рядом, как в iPadOS.
- Создание/правка/удаление — сервер хранит до трёх адресов и телефонов.
  Книга только для чтения — 403 текстом, не выход из сессии (§2).
- **Книга для новых контактов — только назначенная пользователем**, как
  календарь (§12): звезда в диалоге адресных книг (`/address-books`,
  `CalendarPrefs.defaultAddressBook`); без неё форма требует выбрать книгу
  (чипы под именем) и не сохраняет. Клиент шлёт `address_book_id`, а не
  `from_identity`: «книга основного адреса» бывает рабочей, и личный контакт
  уезжал бы на корпоративный сервер к коллегам.

## 16. Разделы — решено (0.0.16)

- Почта, календарь, задачи, контакты (`AppShell`). Сложен — панель иконок
  снизу (таб-бар iOS); уходит, когда открыта беседа (у неё своя шапка) или
  клавиатура. Повторный тап по «Почте» из беседы — к списку. Разложен —
  колонка иконок слева (как в iPadOS).
- WebView беседы и WebSocket принадлежат оболочке, а не экрану почты: уход
  в календарь и обратно не теряет ленту, а `calendar_updated` приходит,
  пока на экране любой раздел.
