# Контракт поведения Android-клиента

Договорённости о поведении и устройстве Android-клиента ddmail. Пишется **до кода**
и дальше живёт по тем же правилам, что `desktop-behavior-contract.md`:
**меняешь поведение — правишь этот файл в том же коммите.** Ссылки — на классы и
функции, не на номера строк.

Статус разделов: **решено** — делаем так; **проверить на устройстве** —
решение принято, но держится на допущении о Mate XT/EMUI, которое надо
подтвердить живым телефоном; **открыто** — см. §11.

## 0. Принципы

- **Нативно, без компромиссов.** Kotlin + Jetpack Compose, библиотеки и
  механизмы платформы (Room, WorkManager, Android Keystore, WebView,
  `DnsResolver`, системные уведомления). Кроссплатформенный слой
  (Rust-ядро через FFI, KMP, Flutter) не используется: на телефоне он
  означал бы обход платформенной сети, хранилища сертификатов, фонового
  режима и энергосбережения. iOS — отдельный клиент на Swift.
- **Полноценный клиент.** Цель — функционал десктопа. Почта — с v1;
  календарь, напоминания, задачи и контакты — с 0.0.16 (§12–§16); внешние
  IMAP/SMTP-учётки, CalDAV/CardDAV и несколько учёток — обязательны до
  публикации (решение 2026-11-12), контракт — `mobile-external-accounts.md`.
- **Сервер — источник правды о смысле.** Что такое диалог, кто в нём кто,
  папки диалогов, группы айдентик, ветки отправки — всё это уже определено
  десктопным контрактом и сервером. Android не изобретает свою семантику: где
  десктопный контракт описывает **что** (правило), Android обязан совпадать;
  свободен он только в **как** (жесты, системные механизмы). **Компоновка
  экранов — как у десктопа** (`mobile-layout.md`, решение 2026-11-13): где
  этот контракт с ним расходится, прав `mobile-layout.md`.
- **Иконки вместо надписей — правило №1 мобильных клиентов** (решено
  2026-11-09). Кнопки, панели действий, свайпы, FAB, кнопки внутри ленты —
  иконки Material (Android; на iOS — SF Symbols) с `contentDescription` для
  озвучки. Текст остаётся там, где без него смысла нет: заголовки, подписи
  полей ввода, пункты меню (иконка + одно слово), текст подтверждения
  удаления. Символы шрифта и эмодзи вместо иконок не годятся — EMUI рисует
  их мелко и по-своему.
- **Скорость разработки не приоритет.** Решения выбираются по качеству
  результата, а не по быстроте старта.

## 1. Платформа и сборка — решено

- **Код:** `mobile/android/` в этом репозитории (рядом с `desktop/`; будущий
  iOS — `mobile/ios/`). Клиент и сервер делят API, общий репозиторий держит их
  в согласии.
- **Первое устройство:** Huawei Mate XT, глобальная EMUI 14.x, без сервисов
  Google.
- **Один код для Huawei и обычного Android** — два product flavor'а:
  `hms` (HMS Push Kit) и `gms` (Firebase Cloud Messaging). Всё, кроме
  доставки push, общее; flavor-специфичный код — только в модуле push.
- **minSdk 29** (Android 10: `DnsResolver.rawQuery` для MX, §3), targetSdk —
  актуальный на момент сборки.
- **Сборка — вне дерева проекта** (правило workspace): каталог сборки Gradle
  направляется в `~/.cache/builds/` (Linux) и `%LOCALAPPDATA%\builds`
  (Windows) через `buildDir`/`layout.buildDirectory` в корневом скрипте.
- **Установка на телефон — по USB через `adb` Windows.** Беспроводной
  отладки в EMUI 14 нет (в «Для разработчиков» только ADB и HDB). Сборка
  идёт в WSL, APK ставится `adb.exe` из `%LOCALAPPDATA%\Android\platform-tools`
  (USB в WSL не пробрасываем):

  ```bash
  cd mobile/android && ./gradlew assembleHmsDebug
  cp ~/.cache/builds/gradle/ddmail-android/app/outputs/apk/hms/debug/app-hms-debug.apk \
     /mnt/c/Users/<user>/.cache/ddmail-apk/
  adb.exe install -r 'C:\Users\<user>\.cache\ddmail-apk\app-hms-debug.apk'
  adb.exe exec-out screencap -p > shot.png   # скриншот с телефона
  ```

  Кабель — короткий, в порт на материнской плате: через передние порты
  соединение рвалось при движении телефона. Станции нужны JDK 17
  (`org.gradle.java.home` в `~/.gradle/gradle.properties`, если в системе
  только JRE) и SDK (`local.properties` → `sdk.dir`, не в git).
- **Версия** — `versionName`/`versionCode` в `app/build.gradle.kts`; бампается
  при любой правке клиента, как у десктопа.

### Модули

| Модуль | Что внутри |
|---|---|
| `:app` | Activity, навигация, экраны Compose, адаптивная раскладка (§6) |
| `:core:api` | HTTP-клиент `/api/desktop/v1` (OkHttp + kotlinx.serialization), WebSocket, refresh токена |
| `:core:db` | Room: схема кэша, DAO, миграции |
| `:core:sync` | движок синхронизации (§4), доменные типы, папки диалогов (порт `folders.rs`) |
| `:core:auth` | вход, хранение токена и паролей внешних учёток (Keystore), поиск ddmail (§3) |
| `:core:mail` | внешние учётки (§17), чистый Kotlin: IMAP-клиент, разбор и сборка MIME, SMTP, автонастройка, склейка бесед |
| `:push:hms` / `:push:gms` | регистрация токена устройства и приём push, по flavor'у |

Документ ленты беседы (JS + CSS: шаблон, нормализатор, мост) — вне модулей,
в `mobile/shared/conversation-doc/`, общий с будущим iOS-клиентом (§8);
`:app` кладёт его в assets при сборке.

## 2. API и сессия — решено

- Клиент говорит с тем же `/api/desktop/v1`, что десктоп. Отдельного
  «мобильного» API не заводим, пока не понадобится то, чего в нём нет
  (первое такое — регистрация push-токена, §7).
- **Вход** — `POST /auth/login` (`username` + `password`) → JWT. Пароль не
  хранится нигде: только токен.
- **Токен** живёт 24 часа; `POST /auth/refresh` обменивает и просроченный, но
  не старше 30 суток от выдачи (`maxRefreshAge`). Каждый refresh выдаёт новый
  токен с новой датой — при регулярном использовании (а push будит клиент,
  §7) вход заново не нужен.
- **Хранение токена** — DataStore, значение зашифровано AES-GCM ключом из
  Android Keystore (ключ не покидает аппаратное хранилище). Устаревшую
  `EncryptedSharedPreferences` не используем.
- **Отказ refresh (401/403) — состояние «нужен вход»**, отдельное от «нет связи»
  (как §5д-бис десктопа): ретраи его не лечат. Показывается несмываемой
  плашкой над содержимым с кнопкой «Войти»; кэш при этом виден. Снимают
  состояние только удачный вход или удачный refresh.
- **Классификация ошибок:** 401 → нужен вход (после неудачного refresh);
  **403 — не «нужен вход»**: им сервер отказывает в конкретном действии при
  живой сессии («календарь только для чтения», «адрес отправителя не ваш») —
  это ошибка действия с текстом сервера (`ApiException.Server`). До 0.0.16
  403 считался мёртвой сессией, и попытка записать в календарь только для
  чтения выкидывала бы на вход. Исключение — сам `/auth/refresh`: его отказ
  любым кодом = нужен вход. Таймаут, 5xx, обрыв → временное, повторяем с
  бэкоффом.
- **WebSocket** `/ws` — пока приложение на экране (§7). **Токен — заголовком
  `Authorization: Bearer`**, как у REST: OkHttp задаёт заголовки рукопожатия
  WS. Ограничение «заголовки не задать» есть только у браузерного API, и
  `?token=` в URL — его наследство: строка запроса оседает в access-логе
  nginx, то есть живые JWT лежат в логах. Сервер принимает заголовок
  (`wsToken` в `handlers_desktop_ws.go`, выкачен 2026-11-09), `?token=` оставлен на переходный период — Android пока шлёт
  токен и так, и так; после выкатки и перевода десктопа на заголовок query
  убрать из обоих.

## 3. Подключение (первый запуск) — решено

- Повторяет логику десктопного визарда (§5г-бис десктопа), в v1 — только
  ddmail-учётка:
  1. Вводится email.
  2. Ищется сервер ddmail: `GET https://<хост>/.well-known/ddmail` на
     `mail.<домен>`, `<домен>`, затем на MX-хостах. MX — через
     `android.net.DnsResolver.rawQuery` (системный резолвер, работают и
     внутренние домены). Прогресс — от верхней границы числа проверок.
  3. Найден — экран входа: адрес сервера, логин (подставлена часть адреса до
     `@`, редактируется), пароль.
  4. Не найден — ручной ввод адреса сервера.
- **Только https.** Сертификат проверяется системным хранилищем, **включая
  CA, установленные пользователем** (`network_security_config`:
  `<certificates src="system"/>` и `<certificates src="user"/>`), — как на
  десктопе, который доверяет хранилищу ОС целиком. Иначе сервер за
  корпоративным CA на телефоне не открылся бы.
- Пароль при поиске никуда не уходит.

## 4. Синхронизация — решено

Повторяет модель десктопного native-провайдера; кэш — Room.

- **Список бесед:** `GET /conversations?limit=N&since=<server_now_ms>`. `since=0`
  — полная выдача, заменяющая набор целиком; дальше — дельты по водяному
  знаку `server_now_ms` из ответа.
- **Удаления и всё, чего дельта бесед не сообщает** — журнал
  `GET /changes?since=<seq>`. `reset: true` (курсор старше нижней границы
  журнала или первый запуск) → полная пересинхронизация.
- **Версия формата id бесед** хранится в `meta` кэша (аналог
  `CONV_ID_EPOCH` десктопа); при несовпадении следующий синк — полный.
  Формат id задаёт сервер, клиент его не разбирает.
- **Тела писем качаются заранее** (§4а-бис десктопа): новые письма всех бесед
  оказываются на диске до того, как беседу откроют; открытие рисует из кэша.
  Порядок — от свежей беседы к старой; фоновая докачка уступает любому
  действию пользователя. Вложения заранее **не** качаются — только тела.
- **Можно ли подкачивать — решает пользователь.** После первого входа —
  один вопрос «Загружать письма заранее?» с тремя ответами: «Всегда»,
  «Только по Wi-Fi», «Нет, при открытии». Ответ по умолчанию не выбран —
  трафик чужой, решать не нам. Изменить — «Настройки → Загрузка писем».
  «Только по Wi-Fi» — докачка идёт под ограничением WorkManager
  `NetworkType.UNMETERED`; на мобильной сети открытие беседы качает её тела
  по требованию. «Нет» — всегда по требованию. Список бесед и дельты
  синхронизируются при любом ответе: они маленькие и без них нет
  уведомлений.
- **Когда синхронизируемся:** при открытии приложения; по каждому событию WS
  (пока на экране); по push (§7); по `WorkManager` периодически раз в
  ~30 мин как страховка от потерянного push (ограничения ОС решают точное
  время).
- **Пустое тело** (нет HTML, текста и вложений) считается непригодным и
  перезапрашивается при открытии беседы (§4а десктопа). Так же
  перезапрашивается тело своего исходящего, у которого статус доставки в
  ссылке беседы уже не тот, что в теле (§5 «Статус доставки»).
- Мутации (флаги, удаление, спам) — оптимистично в кэше, затем запрос; при
  отказе — откат и сообщение.

## 5. Почта: что берём у десктопа как есть

Правила, на которые Android **обязан** совпадать с десктопом (ссылки — на
разделы `desktop-behavior-contract.md`):

- **Диалог = набор адресов** (§4 «Чем опознаётся диалог»), id — от сервера.
- **Роли в диалоге** — собеседники и айдентика (§4 «Роли»).
- **Папки диалогов — табы над списком** (§4 «Папки диалогов»): таба «Все»
  нет, ничего не выбрано = инбокс; выбранный таб помнится. Набор табов
  общий с десктопом (`/dialog-folders`).
- **Ветки отправки** (§1): пересылка / новое / явный ответ / неявный ответ;
  непустое «Кому» и непустая тема побеждают авто-деривацию; письмо из одного
  вложения — валидное.
- **Optimistic send** (§2; 0.0.27): мгновенный пузырь — тот же HTML, что
  уходит на сервер, картинки тела вшиты `data:`-URI (`stubHtml`; документ
  ленты рисует `st.html`, без него — текст); reconcile с настоящим письмом.
  Успех — зелёная плашка «✓ Отправлено» над композером ~2 с, без тоста; до
  0.0.27 там была одна иконка, и отправку не замечали. Ошибка — пузырь
  убирается, набранное возвращается в композер целиком (со стилями и
  картинками, `Draft.reloaded`), причина — amber-плашкой над композером.
  **Итог — в композер той беседы, откуда ушло письмо** (0.0.34): композер
  один на все беседы, и пока письмо уходило, могли открыть другую.
  `ComposeController.place` — где открыт композер (`ref` беседы или
  `new:<адрес>`); «✓ Отправлено» и возврат набранного — только если он там же
  (или в беседе, сменившей «Новую беседу» своего письма). Иначе не ушедшее
  ждёт в `returned` и возвращается при открытии своей беседы
  (`ComposeController.enter`) вместе с явным ответом и причиной; композер
  чужой беседы не трогается.
  С 2026-11-13 сервер кладёт копию в «Отправленные» **при приёме** письма,
  не после доставки (десктоп §1): `message_sent` приходит сразу, беседа
  есть уже к ответу `/send`, даже если письмо висит в очереди. Поэтому после
  отправки через ddmail (0.0.30) — синк сразу и два повтора (2.5 и 7 с) на
  случай без сокета; основной сигнал — WS `message_sent`. Двухминутные
  повторы 2.5 → 7 → 15 → 30 → 60 с (`schedule_post_send_refetch`
  десктопа) остались только для IMAP-учёток: их копию в «Отправленных»
  кладёт сервер провайдера или мы через 5–20 с (§17). `MailHub.send`
  говорит, какой путь был (`true` — сервер ddmail).
- **Статус доставки** (десктоп §1; сделано в 0.0.30). «✓ Отправлено» =
  сервер принял, не «доставлено». Поля сервера: в теле письма
  (`/conversations/messages`) `delivery_status` — `pending`, `delivered`,
  `failed`, пусто — неизвестно (входящие, старые письма), считать
  доставленным и ничего не рисовать; `delivery_reason` — код причины;
  `delivery_error` — причина словами на языке пользователя; `delivery_failed`
  — кому не доставлено. В ref письма `/conversations` — `delivery_status`,
  у строки беседы — `last_delivery_status`. Смена — WS `delivery_status`
  (`message_id` = uid копии, `rfc_message_id` и те же поля), только при
  изменении; она же двигает `updated_at` и журнал.
  - **Пузырь** (документ ленты, поле письма `delivery`, §8): `pending` —
    серая строка с часами «Отправляется…»; `pending` с причиной — янтарная
    «Не удалось отправить, повторяем: <причина>»; `failed` — красная плашка
    «Не доставлено: <причина>», под ней адреса из `delivery_failed` (при
    частичном отказе видно, кому), пузырь обведён красным; `delivered` и
    пусто — обычное отправленное. Причина — текст сервера, первая буква
    строчная посреди фразы.
  - **Строка списка** — значок у времени по `last_delivery_status`:
    `failed` — маленький красный (`Error`), `pending` — часы (`Schedule`).
  - **Обновление без перезагрузки.** WS `delivery_status` правит ссылку и
    тело в кэше сразу (`SyncEngine.applyDelivery`, Room
    `CacheDao.applyDelivery`), открытая беседа меняет пузырь на месте
    (`ConversationController.delivery` → `ddm.delivery(uid, …)`), и
    событие, как любое, запускает синк — он приносит строку беседы. Без
    сокета то же делает дельта: у ссылки сменился статус — тело в кэше
    устарело (`bodyStale`), открытая беседа перечитывает его и правит пузырь
    (`ConversationController.updated`). Смена одной причины у `pending` без
    сокета видна при следующей смене статуса — дельта о ней не говорит.
    Кэш — Room v5 (автомиграция 4→5: статус у ссылок, тел и строк бесед).
  - **Новый адресат.** Беседа есть уже к ответу `/send`, переход в неё
    (`ComposeController.sentTarget`) — первым же синком, за секунды. Цель —
    поток: синк по `message_sent` мог успеть до ответа `/send`, тогда
    переход делается при появлении цели по уже пришедшему списку.
  - **IMAP-учётки** (свой SMTP) — статус определяет клиент: SMTP принял —
    доставлено, пометки нет. Отказ SMTP (`SmtpFailed` из `MailHub.send`) —
    заглушка в ленте остаётся с той же красной плашкой «Не доставлено:
    <причина>» (`ddm.stubDelivery`), в новой беседе — тот же текст красным
    под пузырём; набранное возвращается в композер, amber-плашки нет.
    Следующая отправка убирает пузыри прежних неудач. Ошибки самого сервера
    ddmail (`/send` не принял) — как раньше: пузырь убирается, причина
    amber-плашкой.
  - **Отказ о недоставке (DSN)** от `MAILER-DAEMON@…` — обычное входящее в
    своей беседе с `MAILER-DAEMON`; с беседой исходного письма не
    склеивается.
- **Новое письмо новому адресату** (§2 десктопа): пузыри в пустой ленте новой
  беседы помечены «Отправляется…» → «✓ Отправлено»; беседа открывается сама,
  как только синк её принёс (`ComposeController.sentTarget`). Цель — набор
  «Кому» + «Копия» (`targetOf`), свои адреса среди адресатов в собеседники не
  входят (`matchesTarget(.., own)`); письмо себе сервер отдаёт беседой, где
  собеседник — свой же адрес, поэтому подходит и точное совпадение. До
  0.0.27 цель была только «Кому»: письмо с копией не находило свою беседу, а
  повторы синка кончались через ~1 мин.
- **Новая беседа встаёт первой строкой — и её видно** (0.0.27, замер на
  Mate XT 2026-11-13). `LazyColumn` держит позицию по ключу прежней первой
  строки: беседа нового письма (и любое свежее входящее) вставала выше края
  экрана, список выглядел так, будто её нет, — это и было «после отправки
  новый диалог не появился». Был в самом верху — верх и остаётся
  (`ListPane`, `scrollToItem(0)`); прокрутил вниз — позиция не трогается.
- **Форматирование тела** (§3а десктопа; 0.0.27) — поле композера
  `RichEditText` (`EditText` со спанами в Compose: у Compose-полей стили не
  переживают правку). Отдельной строки тулбара нет, как у десктопа:
  - **Ж / К / Ч / «Ссылка»** — пункты системного меню выделения текста; с
    аппаратной клавиатуры — Ctrl+B / I / U / K по коду клавиши (любая
    раскладка). Всё выделение уже в стиле — снять, иначе наложить. «Ссылка»
    спрашивает адрес (из буфера, если там ссылка); без выделения вставляет
    сам адрес ссылкой; схемы, кроме http(s)/mailto, в письмо не уходят.
  - **Картинки** — из буфера обмена («Вставить», клавиатура с картинками;
    `OnReceiveContentListener`, до Android 12 — вставка руками) и из галереи
    (пункт «Картинка» в меню долгого нажатия на каретке). Всегда своим
    блоком; больше 2000 px или 1.5 МБ — уменьшаются (PNG остаётся PNG).
    Уходят inline-вложениями с `Content-ID`, HTML ссылается `cid:`.
  - **Тело — две версии**, как `Editor::plain_text` / `Editor::html`
    (`RichBody`): `<div>`-абзацы, `<b>/<i>/<u>/<a>`, пустой абзац —
    `<div><br></div>`, картинка — `<div><img src="cid:…">`, автоссылки. Для
    ddmail — тот же `/send`, что у десктопа (`html` + `text` + вложения с
    `content_id`); для IMAP/SMTP — `Smtp.build`: `alternative{text, html}`,
    `related` с картинками, `mixed` с файлами.
  - Источник истины — редактор; черновик (`Draft`) держит plain-зеркало,
    HTML, картинки и снимок содержимого. Обратно в редактор текст идёт только
    при смене `Draft.epoch` (сброс после отправки, возврат после ошибки).
  - Чего пока нет: стиль «на каретке» для следующего ввода (меню выделения
    без выделения не открывается), списки/цитаты/заголовки.
- **Уведомления** (§5): только реальное входящее (не спам, не iTIP, не своё);
  читаешь этот диалог — без уведомления, тихо дописать.
- **Спам** (§5а) и группы айдентик (§1в) — та же семантика, что на сервере.
- **Открыт на старте** — диалог, на котором закончили (§4 «Какой диалог
  открыт на старте»), на раскладках, где беседа видна сразу (§6).
- **Поиск — выпадашка под полем поиска, как у десктопа** (§4 «Поиск»
  десктопа; 0.0.26). Поле — первая строка экрана, справа от бургера (§6);
  непустая строка открывает карточку поверх табов и списка, список под ней не
  фильтруется. Секции по порядку (`Search.kt`, `MailViewModel.search`):
  - **«Написать по адресу …»** — если введённое похоже на адрес
    (`parseEmailLike` = `parse_email_like` десктопа). Касание или Enter
    («Перейти» клавиатуры, аппаратный Enter) — **новая беседа** с этим
    адресатом (§6 «Новая беседа»). Других способов начать новое письмо нет:
    ни FAB, ни карандаша, ни пункта меню.
  - **«Диалоги»** — только локально: имя диалога (в том числе своё), адрес
    любого участника, тема последнего письма; порядок — имя, адрес, тема; по
    всем папкам; вторая строка — что совпало. Поиск в памяти, регистр
    складывается в Kotlin (у `LOWER` SQLite кириллица не складывается). Темы
    всех закэшированных тел (как у десктопа) — следующим шагом.
  - **«Контакты»** — адресная книга (`/contacts` и CardDAV, её держит
    `ContactsViewModel`) по имени и адресу; адреса собеседников найденных
    диалогов не повторяются. Касание — свежая беседа один на один с этим
    адресом (в любой папке), нет такой — новая беседа с ним.
  - **«Сообщения»** — серверный поиск там, где он у учётки есть
    (`MailSource.searchMessages`): ddmail — `GET /search` (индекс
    Meilisearch; 503 «поиска нет» — пусто), IMAP — `UID SEARCH OR OR SUBJECT
    FROM BODY` во «Входящих» и «Отправленных» (`CHARSET UTF-8` литералом для
    кириллицы), как `search_impl` десктопа. Запрос — через 350 мс после
    последнего нажатия, новая строка отменяет прошлый; учётка, у которой
    поиск не удался, просто ничего не даёт. Показываются только письма,
    лежащие в беседе списка (по uid, иначе по Message-ID): касание открывает
    эту беседу. До 12 строк, новые сверху.
  Спам в поиск не попадает. Выбор строки очищает поле и открывает беседу
  через `open()`, то есть с переходом в её папку (`reveal` десктопа).
  «Назад» при открытой выпадашке — очистить поле.
- **Цвет строки — группа адреса получателя** (десктоп §1в): строка в покое
  залита пастелью группы, в которую входит `received_by` беседы; пустой
  `color` группы — палитра `IDENT_PASTEL` по индексу группы, `user+tag@`
  без своей записи — цвет `user@`, адрес вне групп — серый `#d5d5d0`.
  Документ групп — `/identity-groups` (только чтение; правка групп — на
  десктопе), кэш в meta, обновляется каждым синком (а синк будит и
  `identity_groups_changed` по WS). Открытая беседа — сплошной `#10b981` с
  белым текстом, как выделение на десктопе (светлое выделение на зелёной
  пастели не видно); отмеченная при множественном выборе — голубая с ✓.
  Толкование — `IdentityColors.kt` с тестами.
- **Аватарки** — `/avatars?email=` первого собеседника, кэш в памяти и на
  диске, «нет аватара» запоминается на неделю; SVG (BIMI) не рисуются —
  инициалы.
- **Картинки по отправителю:** под письмом «Показать картинки (N)» (это
  письмо, до закрытия беседы) и «Всегда от <адрес>» (запоминается на
  телефоне). При разрешении позиция ленты удерживается, пока грузятся
  картинки. **«Настройки → Внешний контент»** (0.0.34, десктоп §5г, вкладка
  1): список «Всегда показывать картинки от» с отзывом по одному и «Отозвать
  все»; отозванным — снова по нажатию. Удалили последнюю учётку — список
  стирается вместе с остальным.
- **Вложения:** касание — открыть; долгое нажатие — «Открыть» /
  «Поделиться» (`ACTION_SEND` через `FileProvider`, 0.0.34) / «Сохранить
  в «Загрузки»» (MediaStore, без разрешений). Скачанное для просмотра лежит в
  `cacheDir/attachments/<FNV учётки>/<uid>/` (uid разных учёток
  пересекаются) и стирается на каждом запуске.
- **Меню пузыря** (долгое нажатие; 0.0.34 — как меню пузыря десктопа,
  `app.slint`): «Ответить», «Переслать», «Копировать текст», «Копировать
  адрес», «Показать…» (раскрывается на месте: «Заголовки», «Исходник
  сообщения», «Исходник тела (HTML)», «Текстовую версию» / «HTML-версию»),
  «Удалить письмо». **С 0.0.36 — меню-поповер у пузыря** (как
  `UIContextMenuInteraction` iOS и меню по правому клику десктопа; до 0.0.35
  был диалог посреди экрана). Меню вложения — так же, у чипа.
  - Мост: `bubbleMenu(uid, x, y, w, h, px, py, vw)` и
    `attachmentMenu(uid, index, x, y, w, h, px, py, vw)` — прямоугольник
    элемента и точка нажатия в CSS px от угла видимой области
    (`visualViewport`: прокрутка и щипок учтены) и её ширина. Пиксели окна =
    угол WebView в окне + CSS px × (ширина WebView в px / `vw`) — так
    учтены плотность и щипок (`MenuAnchor.fromDocument`). Число аргументов
    `@JavascriptInterface` — часть подписи: JS (`askMenu`) и
    `ConversationWeb.Bridge` меняются вместе; ветка WebKit (iOS/Мак) в
    `askMenu` не тронута.
  - Место (`menuPlacement`, тесты `MenuAnchorTest`): по горизонтали — по
    краю пузыря с его стороны (входящие слева, исходящие справа); по
    вертикали — под видимым низом пузыря, не влезает — над видимым верхом,
    пузырь выше ленты — у пальца; всегда целиком в окне с полем 8 dp,
    длинное меню прокручивается. Тап мимо и «Назад» закрывают.
  - **Заголовки / Исходник** — письмо целиком (`MailSource.source`): ddmail —
    `GET /messages/{id}/source`, IMAP — `BODY.PEEK[]` из кэша сырых писем;
    заголовки — до первой пустой строки (`MessageSource`), текст — UTF-8,
    иначе Latin-1. Окно на весь экран, моноширинно, с выделением; больше
    256 тыс. символов — показывается начало, «Скопировать» берёт всё.
    «Исходник тела» — HTML, который уже пришёл в теле.
  - **Текстовая версия** — `ddm.view(uid, 'text'|'html')` на месте, до
    следующего открытия беседы; пункты — как у десктопа: «Текстовую версию»,
    если есть и HTML, и текст; «HTML-версию» — пока показан текст.
  - **Удалить письмо** — с подтверждением (необратимо), как удаление беседы:
    пузырь уходит сразу (`ddm.remove`), кэш — сразу (ddmail —
    `CacheDao.deleteMessages`, беседа без писем уходит; IMAP — после ответа
    сервера, `\Deleted` + `EXPUNGE`, беседы пересобираются), сервер —
    `/messages/delete` (`MailSource.deleteMessages`). Последнее письмо беседы
    — беседа закрывается. Отказ — Snackbar с причиной, лента открывается
    заново из кэша. Письма, пропавшие из беседы (удалены здесь или на другом
    устройстве), лента убирает и при обновлении беседы (`feedRemoved`;
    пустая беседа — не удаление: так выглядит пересборка кэша).
- **Свои имена и аватарки диалогов — на сервере** (решено 2026-11-08), общие
  для всех устройств, как папки диалогов. Сейчас они живут только в
  десктопном `merges.json` и файлах `avatars/`; переезд — серверная задача и
  задача десктопа (локальные при первом подключении уезжают на сервер, как
  было с папками). Android их показывает и правит (меню шапки беседы, §9).
- **Ручное «В папку» и «Убрать из папки»** — та же семантика `assign`, что
  у десктопа (§4 «Папки диалогов»): диалог строго в одной папке, ручное
  назначение побеждает правила, «убрать» вносит в `exclude` ловящих папок.
  Документ папок общий (`/dialog-folders`, версия + `409` при чужой правке).
- **Папки толкуются в `DialogFolders.kt` — портом `folders.rs` десктопа**,
  с теми же тестами: документ общий, смысл обязан совпадать. Ключ ручного
  назначения — `{account, id}`, где `account` = `логин@хост` (как
  `account_key` десктопа, иначе назначения с десктопа не узнаются).
- **Папка «Спам»** — та же системная папка, что у десктопа (§4 десктопа,
  `system = "spam"`), порт `withSpam()`; без ddmail-учётки — в локальном документе (§17);
  она есть всегда. **«Спам» всегда скрыт**, как у десктопа (0.0.35): таб —
  только по «Показать скрытые» или когда в папку привели, бледнее, как прочие
  скрытые (`FoldersDoc.tabVisible`, `folderTabs`); в настройках папок, в
  «В папку» и в пунктах «Настроить…»/«Удалить» её нет; пункта «Спам» в меню
  нет. «Скрыта» чинится при каждом чтении документа — серверного и
  локального (`withSpam()`: другой клиент снял флаг — снова `hidden: true`).
  С 0.0.26 по 0.0.34 «Спам» был табом всегда — ошибка редакции
  `mobile-layout.md`, исправлено 2026-11-14. Спам — отдельный полный список
  (`/conversations?spam=1`) в пространстве кэша `<account>#spam`; в поиск,
  уведомления и бейдж не попадает. В «Спам» нет жестов, панель выбора — только
  «Выбрать все», «Не спам» (`/spam/restore`, письма во «Входящие») и «Не спам
  и доверять отправителю» (тот же запрос с `"trust": true`: сервер заводит
  allow-правило на адрес отправителя и возвращает из спама всё остальное от
  него; оно уходит из «Спам» со следующим синком). Обе — иконками (0.0.21).
- **Спам не зазывает и не ходит в сеть** (0.0.21). Число непрочитанных не
  показывается ни в строках «Спам», ни на её табе (жирность остаётся).
  Аватарки спама не запрашиваются — только инициалы: `/avatars` ходит на
  домен отправителя (favicon, BIMI), то есть по сигналу спамера. Внешние
  картинки письма спама — только по плашке «Показать картинки (N)» на это
  письмо и этот показ беседы: разрешение живёт в памяти (`RemoteImageGate`) и
  забывается с открытием другой беседы; «Всегда от <адрес>» у спама нет, и
  сохранённые разрешения по отправителю на спам не действуют. Блокирует
  перехватчик WebView, а не только чистка HTML: у беседы спама `/remote`
  пропускается, только если письмо (`uid` в запросе) разрешено и запрос —
  за картинкой (`Sec-Fetch-Dest: image`, иначе `Accept` с `image/`); шрифты,
  стили и прочее — 403. Прочие внешние адреса перехватчик режет всегда
  (§8). Нормализатор у спама дополнительно вырезает `@import` и `@font-face`.
- **«В спам»** (0.0.22, как §5а десктопа) — иконкой в панели множественного
  выбора и в шапке открытой беседы (у бесед спама её нет). Подтверждение
  называет число бесед и писем и даёт два ответа: «Адрес» (этот отправитель)
  и «Домен» (против спамеров с меняющейся частью до `@`). Запрос —
  `/spam/blacklist-and-purge` с серверными id писем: отправителя сервер
  берёт из самих писем, а не из участников беседы (в BCC-рассылке среди них
  есть получатель). Беседы уходят из списка сразу, следующий синк полный;
  итог — Snackbar «✓ В спам: домен …, удалено писем: N». До 0.0.22 действия
  не было: в объём v1 «спам» вошёл только папкой и «Не спам».
- **Скрытые папки** (`hidden`) — таба нет, их диалоги не видны нигде.
  «Показать скрытые (N)» / «Не показывать скрытые» — в меню полосы табов, на
  сессию (не запоминается); показанный скрытый таб бледнее. N — скрытые
  папки, «Спам» тоже (`hidden-folders` десктопа). Все папки скрыты (хотя бы
  «Спам») — полоса есть, пустая, ради этого меню; при выключенных папках
  полосы нет, спам не виден нигде. **«Письма сразу прочитаны»**
  (`auto_read`) правится в редакторе, но исполняет его десктоп: Android
  флаги по этому правилу не ставит — иначе две станции метили бы одно и то
  же наперегонки.
- **Управление папками** (0.0.27, как §4 «Папки диалогов» и §5г десктопа):
  - **Меню полосы табов — долгое нажатие** (правый клик десктопа): на табе —
    «Все прочитаны», «Настроить…», «Удалить» (с подтверждением: диалоги
    вернутся во «Входящие»); у «Спама» — только «Все прочитаны»; везде (и на
    пустом месте полосы, и на «← Входящие») — «Новая папка» (создаётся
    «Папка N» 📁 и сразу открывается редактор) и «Показать скрытые (N)».
  - **Редактор папки** (`FolderEditorDialog`) — иконка (до 4 символов,
    `clipIcon` = `clip_icon`), название, «Получено на», «Домены»,
    «Диалоги: все / только 1:1 / только группы», «Не показывать в списке»,
    «Письма сразу прочитаны», «Положено руками: N — Сбросить». Пишется одной
    правкой по «Сохранить» (десктоп пишет по полям с дебаунсом — на телефоне
    запись на каждую букву не нужна).
  - **«Настройки → Папки»** (`FolderSettings`): «Показывать папки» —
    выключатель **локальный** (DataStore `folders_enabled`, как
    `calendar.json` десктопа), выключен — список ровно как без папок (всё,
    кроме спама); список папок без «Спама» — касание/карандаш = редактор,

    берётся, своя правка отбрасывается и об этом Snackbar (как amber-тост
    десктопа). Без ddmail-учётки — локальный документ (`MailHub.editFolders`).
    Запись документа (`DialogFolder.toJson`) пишет все поля модели поверх
    исходного JSON: неизвестные поля папки и `rules` переживают правку.

### Склейки диалогов — не переносятся

Склейка (`merges.rs`) на десктопе устарела (deprecated, десктопный контракт
§4 «Склеенный диалог»): группировку делают папки. В Android её нет. Следствие:
диалог, склеенный на десктопе, на телефоне виден своими членами по
отдельности; ручное назначение в папку у склейки висит на ключе её
первичного, поэтому остальные члены на телефоне лежат там, куда их кладут
правила, обычно во «Входящих».

### Множественный выбор диалогов (bulk) — решено

- **Вход в режим выбора** — долгое нажатие на строку списка; она становится
  первой выбранной. Дальше касание строки добавляет/снимает её. Выход —
  «Назад», крестик в панели действий или снятие последней выбранной.
- **Панель действий** заменяет шапку списка на время выбора: счётчик
  «Выбрано: N», «Выбрать все» (в пределах текущего таба), действия.
- **Действия:**
  - **«Прочитано» / «Непрочитано»** — «непрочитано» ставит последнее
    письмо беседы снова непрочитанным (локально сразу, на сервере следом).
  - **«В папку…»** — список папок (включая скрытые, как `folder-targets`
    десктопа) и «Убрать из папки». Одна запись документа папок на все
    выбранные, не N записей: N подряд идущих `PUT` упёрлись бы в `409` друг
    с другом.
  - **«Удалить»** — все письма выбранных диалогов (`/messages/delete`), с
    подтверждением, в котором названо число диалогов и писем. После
    удаления — Snackbar «Удалено N» без отмены. Сервер удаляет мягко (в
    vault, `messages.Service.Delete`), но API восстановления у клиента нет,
    а у внешних учёток удаление сразу ставится в очередь на исходный сервер
    — поэтому подтверждение до, а не «отменить» после.
- Выбор переживает смену раскладки (§6) и не переживает смену таба: другой
  таб — другой набор строк, выбор снимается.
- Дельта, пришедшая во время выбора, не сбивает его: выбор хранится по id
  диалога, а не по номеру строки (как контекстное меню десктопа).
- **Десктоп получает тот же множественный выбор** (решено 2026-11-08) —
  с теми же действиями и той же семантикой (одна запись документа папок,
  подтверждение удаления); отличаются только жесты: там Ctrl/Shift+клик.

## 6. Раскладка — решено (0.0.26: компоновка десктопа)

Компоновка — **как у десктопа**, подробно — `mobile-layout.md`; решение
владельца 2026-11-13: «решение, которое отличается компоновкой от
десктопа — неприемлемо». Раскладка выбирается по **ширине окна** (600 dp),
а не по модели телефона и не по состоянию шарнира: так она же работает на
обычных телефонах, планшетах и в многооконном режиме.

### Колонка почты

Сверху вниз, ничего больше (`MailColumn` в `MailScreen.kt`):

1. **Бургер + круглое поле поиска** («Поиск или новый адресат…») на всю
   оставшуюся ширину. Над ними нет ни заголовка «Почта», ни подписи учётки,
   ни кнопок: ни иконки поиска, ни меню «три точки». Выпадашка поиска — §5.
2. **Полоса табов папок** — текст, выбранный зелёный с подчёркиванием,
   «Входящие» со счётчиком, пока выбрана папка. **«Спам» всегда скрыт**
   (таб — по «Показать скрытые», §5). Папок нет — полосы нет; все скрыты —
   полоса пустая, с меню по долгому нажатию. На время множественного выбора её место
   занимает панель действий (§5).
3. **Диалоги.** «Потянуть» — обновить.

**Нет и не будет:** FAB/карандаша «Написать», меню «три точки», пункта
«Спам» в меню, заголовка раздела, нижней панели вкладок, боковой колонки
иконок разделов. «Нужен вход» — несмываемая плашка у учётки (§2) — стоит
внизу колонки, под списком: над поиском ничего нет.

### Ширина

| Состояние Mate XT | Окно, dp | Раскладка |
|---|---|---|
| Сложен | **350 × 739** | колонка почты на весь экран; беседа открывается поверх (у неё своя шапка с «←»), «Назад» возвращает |
| Два экрана | **712 × 739** | колонка 340 dp слева, беседа справа |
| Три экрана | **1107 × 739** | колонка 400 dp слева, беседа справа |

Размеры окна замерены на устройстве 2026-11-08 (GRL-LX9, Android 12 / API
31, 460 dpi, `Configuration.screenWidthDp/HeightDp`). Высота во всех
состояниях одна — 739 dp; меняется только ширина. Смена состояния Activity
не пересоздаёт (`configChanges` в манифесте).

Клавиатура EMUI в разложенном виде занимает ~85% высоты: пока она больше
половины окна и печатают в беседе, первая строка и табы колонки и шапка
беседы прячутся, остаётся строка ввода. Печатают в поиск — первая строка и
выпадашка остаются. В сложенном виде клавиатура — около трети, всё на месте.

### Новая беседа

«Написать по адресу …» (и «Написать» в карточке контакта, §15) открывает
**новую беседу** — compose-режим десктопа (`enter_compose_mode`): справа
(сложен — поверх списка) шапка с адресатом и «Новая беседа», пустая лента,
композер внизу с фокусом. Под «@» — «Кому» (пусто = введённый адресат),
«Копия», «Тема», «От». Отправка — ветка «новое письмо» (§1 десктопа);
ушедший текст стоит пузырём в пустой ленте, а когда беседа с этими
адресатами приходит с сервера, она открывается вместо заготовки
(`ComposeController.sentTarget`). «Назад» закрывает заготовку. Ответ и
пересылка — как раньше, из беседы (пересылка — отдельным окном).

### Прочее

- **Смена состояния не теряет контекст:** открытая беседа, позиция списка,
  черновик композера и выбранный таб переживают пересоздание Activity и смену
  раскладки (state в ViewModel). Сложили телефон с открытой беседой — видна
  беседа, «Назад» ведёт в список.
- **Шарнир:** если ОС сообщает `FoldingFeature` с разделением
  (`isSeparating`), граница между колонкой и беседой ставится на шарнир, а не
  поперёк него — **проверить на устройстве**, сообщает ли EMUI это для Mate XT.

## 7. Push и фон — решено, механику HMS проверить на устройстве

- **Пока приложение на экране** — WebSocket, как у десктопа; события
  (`new_message`, `flags_changed`, `expunge`, `dialog_folders_changed`,
  `identity_groups_changed`, `auth_failed`) запускают синк. Сокет снова
  открылся после обрыва — синк сразу (0.0.34, `onOpen`): события за обрыв
  потеряны, и пропущенное иначе ждало бы следующего события.
- **В фоне — push.** Постоянного foreground-сервиса с WS нет.
- **Пока push нет (v0.0.6)** — `SyncWorker` (WorkManager) раз в ~15 минут
  (меньше Android не даёт; точное время решает ОС, EMUI может придерживать
  дольше): синхронизация, уведомления, докачка тел. С push он остаётся
  страховкой от потерянного push. Пока приложение на экране, фон
  пропускает проход — синхронизирует экран (и WebSocket), второй движок
  гонялся бы с ним за кэш.
- **Уведомления** собираются на телефоне из кэша: «новое» — непрочитанные
  письма с uid больше последнего, о котором уже уведомили; первый проход
  только запоминает рубеж. Не уведомляем об открытой беседе и о скрытых
  папках. Нажатие открывает беседу (с переходом в её папку). При холодном
  старте выбор приходит раньше списка (кэш ещё читается, учётки грузятся):
  беседа остаётся выбранной и открывается по-настоящему — папка, лента,
  «прочитано», — как только её строка пришла (`MailViewModel.reveal`,
  0.0.34; до этого лента оставалась пустой). Экран ищет открытую беседу во
  всём списке, а не только в видимой папке.
- **Push не несёт персональных данных** (152-ФЗ: push идёт через серверы
  Huawei/Google за рубежом — передача ПДн третьему лицу и трансграничная).
  В push — только факт «есть изменения» (и, возможно, непрозрачный счётчик).
  Отправитель, тема, адреса в push **не кладутся никогда**; текст
  уведомления клиент собирает сам после синка, из своего кэша.
- **Сервер — регистрация общая с iOS (сделано 2026-11-12, подробно —
  ios-behavior-contract.md §7.1):** `POST /api/desktop/v1/push/token` под JWT
  с `{"kind":"hms"|"fcm","token":…,"topic":<имя пакета>}` (без
  `environment` — оно только у APNs), идемпотентно; `DELETE` того же пути
  (`{"kind","token"}`) — выход из учётки. Ответ `delivery` — умеет ли сервер
  сейчас доставлять этой службой. Таблица `push_tokens` (миграция 055), push
  — только на настоящее новое входящее (не спам), не чаще раза в 10 с на
  пользователя. **Отправители HMS и FCM не реализованы:** есть интерфейс
  `push.Sender` и секции `push.hms` / `push.fcm` конфига; HMS Push REST API
  (OAuth client credentials) — следующий шаг, когда будет
  `agconnect-services.json`. Токены, которые служба отвергает как
  недействительные, удаляются (общий механизм `TokenRejectedError`).
- **Проверить на устройстве:** доходит ли data-сообщение HMS до
  остановленного приложения на EMUI 14. Если нет — запасной путь:
  notification-сообщение с **обезличенным** текстом («Новые письма»),
  которое показывает сама система; нажатие открывает приложение и запускает
  синк. Какой путь основной — решаем по результату проверки.
- Подготовка со стороны пользователя: аккаунт разработчика Huawei, проект в
  AppGallery Connect с Push Kit, `agconnect-services.json`.
- **Секреты сборки — вне git:** `agconnect-services.json`, `google-services.json`
  (flavor `gms`) и ключ подписи APK лежат в `~/.config/ddmail-android/` на
  каждой станции (на Windows — `%APPDATA%\ddmail-android\`); Gradle берёт их
  оттуда. Нет файла — сборка соответствующего flavor'а падает с понятной
  ошибкой, а не собирает APK без push.

## 8. Отображение писем — решено

### Почему так: замер (2026-11-08)

Агрегаты по ящику на сервере (3870 писем, один пользователь; содержимое не
выводилось — только числа):

| Что | Значение |
|---|---|
| С HTML / только текст | 3236 / 634 |
| Размер HTML: медиана / p90 / p99 / max | 9 КБ / 34 КБ / 330 КБ / 1 МБ |
| Доля разметки в HTML | 93% (видимого текста: медиана 0,9 КБ) |
| Фиксированная ширина ≥ 480 px | 47% писем с HTML |
| Вложенные таблицы | 59% |
| Внешние картинки / трекинг-пиксели 1×1 | 45% / 19% |
| `<script>` в теле | 15% |
| Есть цитата | 3%; у таких цитата — в среднем 83% текста |
| Писем в беседе: медиана / p90 / p99 / max | 1 / 3 / 47 / 426 |

Беседы посчитаны приближённо, по набору адресов. Выводы: половина писем
свёрстана под фиксированные ~600 px — без масштабирования на узком экране они
либо уезжают вбок, либо разваливаются; «простых» писем, которые можно было бы
рисовать нативно, меньшинство — отдельной нативной формы нет; чистка
обязательна; беседы обычно короткие, но хвост длинный.

### Один WebView на беседу

- **Лента пузырей открытой беседы — один документ в одном WebView**, а не
  WebView на письмо: WebView — это десятки МБ и заметное время на создание,
  в беседе на 50 писем так не жить. Прецедент — беседа в Gmail для Android
  (один WebView, нативные элементы поверх).
- **Экземпляр один и переиспользуется:** создаётся заранее при старте
  приложения, при открытии беседы меняется только документ. Создание
  WebView в путь открытия не входит.
- **Окно отрисовки:** сначала — последние ~20 пузырей, старые
  подгружаются порциями при прокрутке вверх с удержанием позиции (вставка
  сверху не сдвигает то, на что смотрят). Новое письмо дописывается в конец
  без перестройки документа.
- **Нативное — всё вокруг ленты:** шапка беседы, композер, панели, меню.
  Долгое нажатие на пузырь, клик по ссылке, по чипу вложения, по адресу
  уходят через мост (`addJavascriptInterface` / `WebMessagePort`) в нативный
  код: меню — нативное, ссылки — во внешнем браузере
  (`Intent.ACTION_VIEW`), вложения — §9.

### Изоляция письма — Shadow DOM на пузырь

- Каждое письмо — в своём shadow root: CSS письма не выходит наружу, наш —
  не проникает внутрь. На десктопе документ общий, и стили писем (`class="row"`,
  `time`, `inner`…) ломали обвязку пузыря, пока все её классы не получили
  префикс `ddm-` (десктопный контракт §4б). Здесь граница структурная,
  префиксы и выверенная специфичность не нужны.

### Безопасность

- **JavaScript в WebView включён — но только наш.** Документ несёт
  Content-Security-Policy: скрипты — только с nonce нашего документа,
  `unsafe-inline` нет, значит инлайн-обработчики (`onclick`, `onload`…) и
  `javascript:`-ссылки не исполняются. Чужие `<script>` вырезаются ещё до
  вставки (каждое седьмое письмо их несёт); CSP — второй рубеж, не первый.
- **Сеть — только через перехват** `shouldInterceptRequest`: внешние ресурсы
  по политике отправителя (та же модель, что у десктопа: медиа/скрипты по
  отправителю, разрешённые домены); по умолчанию не грузятся. `cid:` —
  из частей письма (`/messages/{id}/parts/{cid}`). Трекинг-пиксели
  вырезаются всегда, независимо от политики.
- Файловый доступ WebView выключен (`allowFileAccess`, `allowContentAccess`
  = false); документ грузится с собственного фиктивного https-источника
  через `WebViewAssetLoader`, а не `file://`.

### Нормализатор — в клиенте, на JS внутри документа

- **Нормализация живёт в клиенте, для любой учётки.** У учётки на обычном
  IMAP нашего сервера нет, значит серверная нормализация не может быть
  единственной, а держать две (на сервере и в клиенте) — значит держать две
  одинаковыми. Сервер нормализацию не делает.
- **Пишется на JS и выполняется в документе беседы** — работает с тем самым
  DOM, который будет нарисован, с реальными ширинами. Тот же код без
  изменений исполнит WKWebView в iOS-клиенте: каждая платформа своим
  штатным движком, функционал одинаковый — правило §0 не нарушается.
  Исходник один: `mobile/shared/conversation-doc/` (JS + CSS шаблона),
  клиенты кладут его в свои ресурсы при сборке.
- **Порядок для каждого письма:**
  1. **Чистка** — разбор в инертный документ (`DOMParser`/`<template>`, где
     ничего не исполняется), удаление `script`, `iframe`, `object`, `embed`,
     `form`, обработчиков `on*`, `javascript:`-URL, внешних `<link>`,
     трекинг-пикселей; только потом — вставка в shadow root.
  2. **Цитаты** — `blockquote`, `gmail_quote`, `divRplyFwdMsg`,
     `moz-cite-prefix`, текстовые «-----Original Message-----» /
     «Пересылаемое сообщение» сворачиваются в «…»; нажатие разворачивает.
     Цитата в начале письма (ответ сверху) и в конце сворачиваются
     одинаково.
  3. **Ширина** — у письма с фиксированной вёрсткой шире пузыря
     **масштабирование целиком** (`transform: scale` по измеренной ширине,
     высота контейнера пересчитывается), а не линеаризация: в линеаризованной
     таблице цифры теряют связь со столбцами (замер на десктопе, §4б).
     Нажатие на масштабированный пузырь открывает письмо во весь экран с
     зумом. Письмо уже пузыря не трогается.
  4. **Длинные слова и URL** — `overflow-wrap: anywhere` внутри пузыря.
  5. **Картинки** — `max-width: 100%` у не масштабированных писем; до
     разрешения внешние картинки заменены местом-заглушкой с размером из
     атрибутов (вёрстка не прыгает после загрузки).
- **Результат нормализации кэшируется** в Room рядом с телом (с версией
  нормализатора — сменилась версия, кэш пересчитывается, как
  `RENDER_TEMPLATE_EPOCH` у десктопа), чтобы повторное открытие не гоняло
  разбор заново.

### Как сделано (v0.0.4)

- **Источник документа** — `https://appassets.androidplatform.net`
  (`WebViewAssetLoader`), не `file://`. Перехватчик (`ConversationWeb`)
  отдаёт только: `/assets/…` (документ), `/cid/<uid>/<cid>` (части письма с
  сервера), `/remote?uid=…&u=…` (внешняя картинка через прокси приложения;
  у спама — только разрешённым письмам, §5 «Спам»); всё остальное — 403. CSP документа: `script-src 'self'`, `img-src 'self' data:`.
- **Внешние картинки** — по кнопке «Показать картинки (N)» под письмом, на
  это письмо и до закрытия беседы; политика по отправителю (как у десктопа)
  — следующим шагом. Прокси ходит без наших заголовков и кук, только
  `image/*`, не больше 10 МБ.
- **Окно отрисовки** — по 20 писем; «последние» — по uid (у ссылок нет
  дат, а качать тела всей беседы ради сортировки — сотни писем на
  открытии). Внутри порции — по дате. Прокрутка — к первому непрочитанному,
  иначе в конец.
- **Открытие беседы ставит `\Seen`** — локально сразу, на сервере следом.
- **Вложения** — скачать в кэш и открыть системным обработчиком через
  `FileProvider`; «Сохранить в Загрузки» (MediaStore) — следующим шагом.
- **Процесс отрисовки WebView упал** (память, ОС выгрузила в фоне) —
  `onRenderProcessGone` (0.0.34): без него Android завершает всё приложение.
  Старый WebView уничтожается, создаётся новый с тем же документом
  (`ConversationWeb.generation` — экран вставляет новый вид), на его `ready`
  открытая беседа открывается заново (`Host.onRestarted`).
- **Масштаб широких писем** — `zoom` по измеренной ширине, пересчёт на
  смене размера окна (складывание). Отдельного полноэкранного просмотра
  пока нет — вместо него масштаб жестом всего документа.
- Позиция ленты при «Показать картинки» удерживается (якорь — низ пузыря,
  15 с, пока грузятся картинки).
- **Доставка своего письма (0.0.30)** — общий JS API с iOS
  (`mobile/shared/conversation-doc/conversation.js`): у письма поле
  `delivery: {status, error, failed[]}` — `status` как `delivery_status`
  сервера, `error` — причина словами (`""` — нет), `failed` — адреса отказа.
  Нет поля или пустой статус — пометки нет. Смена на месте —
  `ddm.delivery(uid, delivery)`, статус заглушки — `ddm.stubDelivery(key,
  delivery)` (заглушка с `failed` не сверяется с настоящим письмом и не
  уходит по таймеру). Рисует документ (Android-сторона); нативные клиенты
  только передают поле. `ddm.set` сбрасывает заглушки прежней беседы.
- **Выделение текста (0.0.31)** — как у десктопа (§4в «Серия кликов»), общий
  код с iOS (`wireTapSeries` в `conversation.js`, устройство — README
  документа). Долгое нажатие занято меню письма, поэтому:
  - **двойной тап** по тексту письма — слово под пальцем, **тройной** —
    фраза: предложение (`Intl.Segmenter`), без него — строка до переноса;
  - у выделения — системные маркеры (тянуть, чтобы расширить) и панель
    «Копировать / Поделиться / Выбрать всё»;
  - одиночный тап — как раньше: ссылка, вложение; тап по выделенному —
    панель выделения, а не меню письма;
  - долгое нажатие — меню письма, выделение при этом снимается;
  - двойной тап не масштабирует (`touch-action: manipulation`), щипок —
    масштабирует.

  Как: выделение, поставленное скриптом, Chromium показывает без маркеров и
  панели, а тап по уже выделенному тексту — с ними. Поэтому документ ставит
  слово/фразу на `touchstart` второго/третьего тапа, и сам тап приходится на
  выделение. `contextmenu`, пришедший после тапа (палец поднят или опущен
  < 350 мс назад), при непустом выделении уходит системе. Первый тап серии —
  обычный: двойной тап по ссылке её откроет (первым тапом); текст ссылки
  выделяется маркерами от соседнего слова.

  Проверено на эмуляторе Android 15 (WebView 124): слово, предложение,
  перетаскивание маркера, панель «Копировать», долгое нажатие → меню письма,
  одиночный тап по ссылке → браузер. На Huawei — не проверено.

### Сервер — только оптимизации для учёток ddmail

- Нормализация от сервера не зависит. Сервер может (не в v1) отдавать
  картинки, ужатые под ширину экрана, — чистая экономия мобильного трафика,

## 12. Календарь — решено (0.0.16)

- **Вид — как у Apple** (решение пользователя 2026-11-09): сложен (Compact)
  — как iPhone, разложен — как iPad.
  - **iPhone:** лента месяцев (`CompactMonths`, вертикальная прокрутка,
    название месяца над столбцом его первого числа), под числом — точки
    событий цветом календаря (до трёх). Тап по дню — день (`CompactDay`):
    полоса недели сверху (свайп — соседняя неделя), шкала времени (свайп —
    соседний день), «‹ Месяц» — назад к ленте. Системное «Назад» из дня —
    к ленте.
  - **iPad:** боковая панель от 840 dp (мини-месяц + список календарей),
    сверху — заголовок, ‹ ›, «сегодня», переключатель Год / Месяц / Неделя /
    День — по убыванию охвата, как `mobile-layout.md` (иконки, §0; до 0.0.34
    был обратный порядок). На 712 dp панели нет — список календарей в диалоге.
    Месяц — сетка с названиями событий; Год — 12 мини-месяцев.
  - **Месяц: «ещё N» видна всегда** (0.0.36; правило iOS-контракта
    «плашек в дне столько, сколько влезает, остальное — «ещё N»»; у
    десктопа месячного вида нет — только сетка недели, §5и). Число плашек
    считается по высоте ячейки (`monthChipsShown`, тест
    `MonthChipsShownTest`): не влезли все — под показанными целиком встаёт
    «ещё N». До 0.0.35 плашек было «до четырёх» при любой высоте строки, и в
    низкой строке «ещё N» срезалась. Тап по «ещё N» — этот день в виде
    «День» (у iOS тап по ячейке только выбирает день; на Android тап по
    ячейке выбирает, повторный — «День»).
  - «Сегодня» — красным (как в iOS), линия «сейчас» на шкале — тоже.
- **Данные — окнами по месяцу** (`/calendar-events?from&to`, с запасом в
  сутки с каждой стороны: даты «весь день» лежат в полночь UTC). Месяц
  знает только свои дни; многодневное событие приходит в обоих месяцах.
  Перечитывается всё загруженное: на возврат в приложение, по WS
  `calendar_updated`, после своей правки.
- **Развёртка повторов — на клиенте** (`Recurrence`, тот же поднабор RRULE,
  что `recurrence.rs`: DAILY/WEEKLY/MONTHLY/YEARLY, INTERVAL, COUNT, UNTIL,
  BYDAY у WEEKLY; EXDATE учитывается). **Отличие от десктопа намеренное:**
  шаг считается по стенным часам пояса телефона, а не по UTC — иначе
  еженедельное «по понедельникам в 01:00 МСК» (в UTC — воскресенье)
  раскладывалось бы на вторники. Тест `bydayUsesLocalWallClock`.
- **«Весь день»:** полночь UTC читается как дата UTC, прочее — как местная
  дата (`Occ.dateOf`); конец исключён. Новые такие события клиент пишет
  местной полночью — как десктоп (`parts_to_ms`).
- **Видимость календаря — только на этом телефоне** (как десктоп §5г):
  `CalendarPrefs.hidden`, серверный `enabled` не трогается; скрытый не
  рисуется и не звонит (§13).
- **Карточка события** (нижний лист): время, повтор словами, место (ссылкой,
  если это ссылка), ссылки на видеовстречу (`EventLinks` — правила §5в
  десктопа: голый хост — только полем целиком или с `www.`), напоминания,
  ответ на приглашение (принять / под вопросом / отклонить — иконки, только
  если я среди участников и календарь записываемый), участники с отметкой
  ответа, описание.
- **Календарь для новых событий — только назначенный пользователем**
  (звезда в списке календарей, `CalendarPrefs.defaultCalendar`). Не назначен —
  форма не выбирает сама и не сохраняет без явного выбора (чипы календарей
  стоят сразу под названием). Раньше молча брался первый записываемый по
  алфавиту — на этом аккаунте это рабочий календарь, и личное событие ушло бы
  на корпоративный сервер, где его видят коллеги.
- **Клавиатура в тесноте** (разложен: EMUI-клавиатура ~85% высоты) — форма
  события и контакта без полей вокруг и без шапки, видно поле ввода; «Готово»
  клавиатуры её закрывает, шапка с «Сохранить» возвращается (`ui.imeCrowds`).
- **Форма события** — по подтверждению, как §5б-бис десктопа: кнопки гаснут
  на время запроса, закрывается только по успеху, отказ — текстом в форме.
  Нет записываемых календарей — сохранить нельзя, и это видно сразу.
  Повторяющееся: «все повторы» (мастер сдвигается на ту же разницу, что и
  вхождение) или «это и следующие» (`scope=future`); «только это» сервер
  пока не умеет. Удаление повторяющегося — вся серия, о чём предупреждает
  подтверждение.
- **Перенос на шкале:** долгое нажатие на событии записываемого календаря и
  ведение — перенос (шаг 15 мин; в неделе — и между днями), за нижнюю кромку
  (12 dp) — растяжение. Повторяющиеся драгом не двигаются — только через
  форму, где выбирается охват. Долгое нажатие на пустом месте — новое событие
  на этом получасе; в месяце iPad — долгое нажатие на дне.

## 13. Напоминания — решено (0.0.16)

- **Модель — десктопная** (`reminders.rs`, спецификация 2026-07-11), логика
  без Android — `ReminderPlanner`, тесты рядом. Каскад — VALARM'ы события
  (`alarm_leads`, по убыванию); звено сработало → уведомление «Скоро: …» и
  взводится следующее; к началу — «Наступило: …»; опоздали больше чем на
  2 минуты — «Событие уже идёт!», остальной каскад гасится; событие уже
  кончилось — молча.
- **Смахнуть уведомление = «✕»**: тишина по этому вхождению навсегда.
  «Напомнить позже» (действие уведомления) — выбор шага, который ложится до
  начала (1 мин … 1 д), и «в момент начала»; каскад заменяется одним сроком.
  Тап — событие в календаре; уведомление «Скоро» при этом остаётся.
- **Решение пользователя держится за логическое вхождение** «начало +
  название», а не за id события — сервер может пересоздать событие с новым
  id. Два одинаковых события в разных календарях звонят один раз.
- **Посев** — окно `[сегодняшняя полночь, +8 суток)`, отдельно от того, что
  на экране: на запуске, по `calendar_updated`, после своей правки и в
  фоновом `SyncWorker` (~15 мин, и при открытом приложении). Вхождения
  окна, которых события больше не производят (перенос, удаление, EXDATE),
  удаляются вместе с висящими уведомлениями. «Весь день» не звонит.
- **Скрытый календарь** снимает свои напоминания целиком (и висящие
  уведомления); включили обратно — пересев из последнего снимка без сети.
  В момент срабатывания видимость проверяется ещё раз.
- **Будильник — один, на ближайший срок**, `setExactAndAllowWhileIdle`
  (срабатывает в Doze). Точные будильники: `SCHEDULE_EXACT_ALARM` до
  Android 12 включительно, `USE_EXACT_ALARM` с 13. Перезагрузка, обновление,
  смена времени/пояса — перевзвести (`RescheduleReceiver`, экспортирован,
  но умеет только это; срабатывание и смахивание — `ReminderReceiver`, не
  экспортирован, иначе чужое приложение могло бы глушить напоминания).
- **Работа в фоне** (`BackgroundWork`): системный диалог «не ограничивать»
  (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`; в AppGallery разрешено) и, на
  Huawei, «Диспетчер запуска» EMUI — его программно не переключить. На EMUI 14
  (Mate XT) его экран закрыт для сторонних приложений (интент под
  разрешением, проверено 2026-11-09), поэтому открывается «Батарея», где он
  пунктом: у ddmail выключить переключатель, в окне «Управление вручную» —
  OK (автозапуск, косвенный запуск, работа в фоне включены по умолчанию). Спрашивается один раз при первом заходе в календарь и живёт в
  настройках. Проверено на Mate XT 2026-11-09 (0.0.17): точный
  будильник срабатывает в срок (`exactAllowReason=permission`), «напомнить
  позже» перевзводит, после обновления приложения будильник на месте.
- Выключатель напоминаний — в настройках; выключение снимает всё взведённое.

## 14. Задачи — решено (0.0.16; создание — 0.0.27)

- Как §5е десктопа: отдельный раздел, окна по времени нет (забираются все),
  выполненные скрыты — тумблер меняет запрос к серверу
  (`include_completed=1`); галочка оптимистична, отказ откатывает строку.
- Срок: красный — просрочено, янтарный — сегодня, серый — остальное;
  выполненная теряет красноту сразу. Строки коллекций только для чтения на
  галочку не реагируют. «Ещё грузится» и «правда пусто» различаются.
- **Создание, правка, удаление (0.0.27).** «+» в первой строке (последним,
  как «+» в «Контактах») открывает форму: заголовок (обязателен), список,
  срок — выключен / датой («Весь день») / датой и временем, заметка. Список —
  только у новой задачи: чипы коллекций, куда можно писать задачи
  (`can_write`, не ICS, `components` содержит `VTODO`), по умолчанию первая;
  нет таких — форма говорит об этом и не сохраняет. Тап по строке открывает
  ту же форму с «Удалить» (с подтверждением); задача из списка только для
  чтения открывается без правки. Перенос между списками не делается.
- **Сохранение оптимистично** (`tasks/TaskBoard.kt`): форма закрывается,
  строка появляется/меняется/исчезает сразу; новая — с временным
  отрицательным id (галочка и форма на ней не работают), ответ сервера
  подменяет её настоящей. Отказ — строка возвращается как была (удалённая —
  на прежнее место) и снизу причина: «…: список только для чтения» (403),
  «…: этот список не принимает задачи» (422), «…: нет связи с сервером»;
  401 — выход из сессии, как везде (§2).
- **Правка шлёт только изменённые поля.** Срок, которого не трогали, не
  переписывается: у задачи Apple он бывает в своём поясе, а сервер пишет
  срок в UTC.
- Срок «Весь день» уходит полуночью UTC выбранной даты (так сервер хранит
  даты), со временем — моментом по часам устройства.
- **Сервер** (`internal/web/handlers_desktop_task_write.go`):
  - `POST /api/desktop/v1/tasks` — `{calendar_id, summary, description?,
    due?, all_day?, priority?}` → 201 и задача в виде `GET /tasks`.
    Коллекция — своя, включённая, `can_write`, не ICS, принимает `VTODO`;
    иначе 404 / 403 / 422. Пустой заголовок, приоритет вне 0..9 — 400.
  - `PATCH /api/desktop/v1/tasks/{id}` — те же поля, кроме `calendar_id`;
    нет поля — не трогать, `due: 0` снимает срок, `priority: 0` —
    приоритет. → 200 и задача.
  - `DELETE /api/desktop/v1/tasks/{id}` → 204.
  - Чужая задача — 404, как несуществующая; событие вместо задачи — 400;
    коллекция только для чтения — 403 (и у `/completion` тоже).
  - UID новой задачи — `…@ddmailserver`; тело — VTODO с `DTSTAMP`,
    `CREATED`, `LAST-MODIFIED`, `STATUS:NEEDS-ACTION`. Правка — по строкам
    (`caldav.SetTodoFields`): свойства Apple и `VALARM` переживают её; смена
    срока двигает и `DTSTART`, если он был.
  - Наверх (iCloud и другие CalDAV-источники с обратной синхронизацией) —
    той же очередью, что правки событий: `create`/`update` — PUT VTODO,
    `delete` — DELETE по `remote_id`.
  - `/calendars` отдаёт `components` (`["VEVENT"]`, `["VTODO"]`, оба) — по
    нему клиент выбирает списки задач.
- Десктоп создавать задачи пока не умеет — эндпоинты для него готовы.

- Первая строка — как у десктопа: бургер, «Контакты», «+» (новый контакт);
  ниже поле «Поиск контактов», ниже список. Адресные книги — в «Настройках →

  разрешения на звонки). Разложен — список и карточка рядом, как в iPadOS.
- Создание/правка/удаление — сервер хранит и отдаёт **все** адреса и
  телефоны, предела нет (до миграции 057 было три). Форма показывает и шлёт
  все; урезать список в клиенте нельзя — урезанный список сервер примет как

  `address_book_id` и `can_write`. `can_write: false` — книга только для
  чтения (корпоративная «GAL», каталог LDAP; для CardDAV сервер берёт права
  из `current-user-privilege-set`): нет «Изменить» и «Удалить контакт»,
  вместо них — «Только чтение» с замком (0.0.34). Старый сервер поля не
  шлёт — считается записываемым, отказ придёт ответом.
  Запись в такую книгу — 403 `{"error", "code": "address_book_read_only",
  "message"}`, `message` — текст на языке пользователя; показать его, не
  выход из сессии (§2).
- **Внешние CardDAV IMAP-учёток** (без сервера, `PimHub`) правятся так же
  без потерь (0.0.34): GET карточки → правка по строкам (`VCardEdit` — порт
  `internal/carddav/vcardedit` сервера, с его тестами) → PUT с `If-Match`.
  Меняются FN/N, EMAIL, TEL, первый компонент ORG (отдел остаётся), TITLE и
  REV; фото, дни рождения, адреса, заметки, X-свойства, группы с подписями
  Apple — байт в байт. Форма без изменений карточку не пишет. До 0.0.34
  карточка пересобиралась из полей формы, и всё прочее стиралось. Права —
  у книги: контакты книги без записи — `can_write = false`.
- Выбранная строка списка — сплошной `#10b981` с белым текстом, как
  открытая беседа (была бледно-зелёная `primaryContainer`).
- Отказ сервера с кодом (`{"error","code","message"}`) показывается текстом
  `message` — он на языке пользователя (`errorText` в `:core:api`).
- PATCH меняет только присланные поля, значение которых отличается от
  карточки; поле, которого нет в теле, не трогается. Остальное в vCard
  (фото, день рождения, адреса, заметки, X-свойства) сервер сохраняет байт в
  байт и во внешний CardDAV отправляет правку, а не пересобранную карточку
  (GET → правка по строкам → PUT с `If-Match`). Ответ PATCH — контакт в виде
  строки `/contacts`.
- **Книга для новых контактов — только назначенная пользователем**, как
  календарь (§12): звезда в списке адресных книг в настройках (`/address-books`,
  `CalendarPrefs.defaultAddressBook`); без неё форма требует выбрать книгу
  (чипы под именем) и не сохраняет. Клиент шлёт `address_book_id`, а не
  `from_identity`: «книга основного адреса» бывает рабочей, и личный контакт
  уезжал бы на корпоративный сервер к коллегам.

## 17. Внешние учётки — сделано (0.0.23)

Контракт **что** — `mobile-external-accounts.md`; здесь — **как** на Android.

### Учётки и источники

- **Несколько учёток вперемешку:** не больше одной ddmail (токен в
  `SessionStore`, как раньше) и сколько угодно IMAP (`AccountStore`:
  настройки — DataStore открыто, пароли — AES-GCM ключом Keystore
  `ddmail-accounts`, общий код с токеном — `SecretBox`). Ключ IMAP-учётки —
  `логин@хост` (`ImapAccount.key`). Вторая ddmail-учётка не поддерживается:
  поиск, нашедший ddmail при уже подключённой, предлагает этот ящик по IMAP.
- **Источник почты** — `MailSource`: `SyncEngine` (сервер ddmail) и
  `ImapEngine` (IMAP+SMTP). `MailHub` сводит их беседы в одну ленту и
  отправляет каждую правку источнику беседы по `Conversation.accountKey`;
  экран почты источника не знает. В интерфейсе беседа опознаётся
  `Conversation.ref` = учётка + id (одинаковые id разных учёток — разные
  беседы): выбор, открытая беседа, уведомления, «открыть из уведомления».
- **Состояние у каждой учётки своё** (`AccountStatus`): «нужен вход» —
  несмываемая плашка с именем учётки и «Войти» (ddmail — вход на сервер,
  IMAP — форма учётки с паролем); ошибка одной учётки не мешает синку других.
- **Окно подключения** — одно для первого запуска и «Добавить учётку»
  («Настройки → Учётки»; меню шапки почты больше нет, §6):
  адрес → `Discovery` (порт `discover.rs`: фазы, порядок
  кандидатов, `mx_provider`, `MailPresets`, autoconfig, TCP 3 с / ответ 8 с,
  побеждает первый успешный по порядку доверия) → ddmail — вход на сервер;
  иначе — найденные IMAP/SMTP и пароль (подсказка про пароль приложения у
  известных служб). «Я знаю все настройки» — ручная форма; «Сервер ddmail…» —
  ручной вход в ddmail. Перед сохранением — вход на IMAP, затем на SMTP
  (`ImapEngine.check`, по 25 с), ошибка — с префиксом шага.
- **Настройки → Учётки:** список с состоянием, «Войти заново», «Изменить»
  (та же форма: серверы, логин, «SMTP без авторизации», «Другие мои адреса»,
  CalDAV/CardDAV), «Удалить» с подтверждением — уходят пароль, кэш (беседы,
  заголовки, тела, сырые письма) и рубеж уведомлений учётки; последняя
  учётка — на телефоне не остаётся ничего, снова окно подключения.

### IMAP-клиент — свой, MIME и SMTP — Angus Mail

- IMAP написан в `:core:mail` (`ImapReader`, `ImapConnection`, `ImapClient`):
  Jakarta Mail выбирает письма номерами сообщений (а сервер ddmail считал их
  неверно — комментарий к `search_impl` десктопа), а QRESYNC и IDLE у неё
  — блокирующие события без контроля над командами. Свой клиент ходит
  только UID-командами, разбирает литералы, ENVELOPE, `VANISHED`, коды
  ответов, имена папок в modified UTF-7; TLS — `Tls` (системное хранилище с
  пользовательскими CA, TLS 1.2+, проверка имени хоста), 143 — только
  STARTTLS.
- MIME (разбор и сборка) и SMTP — Angus Mail 2.0 (`MimeParse`, `Smtp`).
  Ключи R8 и слияние `META-INF/javamail.*` — в `app/build.gradle.kts` и
  `proguard-rules.pro`.

### Синк и кэш

- Папки по ролям (`FolderRoles`: SPECIAL-USE, затем имена, в т.ч. русские);
  синкаются INBOX, Sent, Drafts и Junk (окна 5000/2500/1250/500 по UID).
  `FolderSync`: UIDVALIDITY сменилась — кэш папки (заголовки и тела) заново;
  новые — `UID FETCH <последний+1>:*`, только если вырос UIDNEXT; флаги —
  QRESYNC прямо в SELECT, иначе `CHANGEDSINCE` (если сдвинулся
  HIGHESTMODSEQ), иначе флаги всего окна; удалённые — `VANISHED`, иначе
  `UID SEARCH UID <окно>`. Состояние папки — таблица `imap_folders`,
  заголовки — `imap_headers` (Room v4, автомиграция с v3).
- **Беседы строятся на телефоне** из всего кэша заголовков после каждого
  изменившего его прохода (`Conversations`, порт `fetch_conversations_impl`
  + `groupConversations` сервера, группировка по id) и кладутся в те же
  таблицы бесед, что у ddmail; Junk — в пространство `<учётка>#spam` с id
  `spam:…`. Свои адреса — email учётки, логин-адрес, «Другие мои адреса» и,
  если IMAP-сервер — ddmail, его айдентики по `GETMETADATA` (как десктоп,
  раз в 6 ч). Всё в «Черновиках» — черновик, даже без `\Draft`.
- **UID в кэше упакован** с ролью папки (`FolderRole.pack`: `роль shl 32 |
  uid`): ключ тел — (учётка, uid), а UID разных папок пересекаются. Рубеж
  уведомлений у каждой учётки свой; у IMAP считаются только письма INBOX.
- **Тела** — `UID FETCH (BODY.PEEK[])`, разбор `MimeParse` в модель сервера
  (html, text, вложения с индексом листа, `cid:`-части прячутся, как
  `hideInlineAttachment`); кодировки — UTF-8/1251/KOI8-R/ISO-8859-*,
  без charset — UTF-8, если байты им являются, иначе 1251. Сырое письмо —
  в `cacheDir/imap-raw` (до 64 МБ) для вложений и `cid:`; нет в кэше —
  повторный `BODY.PEEK[]`. Подкачка заранее — тот же выбор «Всегда / Wi-Fi /
  Нет», что у ddmail; порциями по 10 писем, письма больше 5 МБ
  (`RFC822.SIZE`) заранее не качаются — только при открытии.
- **Порядок писем беседы** — порядок ссылок в кэше (источник кладёт их по
  дате; `observeRefs` — `ORDER BY rowid`): упакованные UID разных папок
  несравнимы. «Непрочитано» ставится на последнее входящее из INBOX.
- Флаги без CONDSTORE приходят по всему окну — в кэш и в пересборку бесед
  идут только изменившиеся.
- **Одно командное соединение на учётку**, переиспользуется минуту, обрыв
  на старом — один повтор на новом.

### Правки и отправка

- Прочитано/непрочитано, удаление, «В спам», «Не спам» — оптимистично в
  кэше бесед; кэш заголовков меняется только после ответа сервера; отказ —
  беседы пересобираются из заголовков (откат) и текст ошибки в Snackbar.
  Удаление — `\Deleted` + `UID EXPUNGE` (без UIDPLUS — `EXPUNGE`), с тем же
  подтверждением. «В спам» — `UID MOVE` в Junk (без MOVE — COPY и
  удаление); у IMAP одна кнопка «В спам», у ddmail — «Адрес»/«Домен»; в
  выборе из разных учёток кнопки «адрес/домен» есть, только если все они
  ddmail. Нет папки Junk — «В спам» объясняет, что переносить некуда.
- **Отправка** — учёткой-владельцем адреса From (`MailHub.send`; адрес у
  нескольких учёток — та, где беседа). SMTP 465 — TLS, 587/25/2525 —
  STARTTLS обязателен; сборка как у десктопа (`alternative`/`related`/`mixed`,
  `Message-ID <hex.hex@домен-from>`). Копия в «Отправленные»: через ~5 с
  `UID SEARCH HEADER Message-ID`, не нашлась за ~15 с — `APPEND` с `\Seen`;
  у Gmail — нет (кладёт сам).

### Новая почта

- На экране: у ddmail — WebSocket, у каждой IMAP-учётки — IDLE на INBOX своим
  соединением (`ImapEngine.watch`): событие — синк, IDLE перевыдаётся каждые
  25 мин, обрыв — переподключение с бэкоффом от 30 с, без IDLE у сервера —
  опрос раз в 2 мин (без открытого соединения); «нужен вход» — IDLE учётки
  ждёт входа. Ушли с экрана — IDLE-сокет закрывается сразу, а не по таймауту
  (иначе висящие соединения упирались бы в лимит сервера). Короткий таймаут
  опроса стоит только на ожидание начала ответа: оборванный посреди ответа
  разбор сбил бы чтение. Битый ответ (лишняя скобка, литерал больше 64 МБ) —
  ошибка соединения, а не зависание.
- Удаление учётки ждёт идущий синк и запрещает ему дописывать в кэш; смена
  ключа учётки в «Изменить» стирает кэш прежнего ключа.
- В фоне — `SyncWorker` по всем учёткам (процесс, поднятый ради задачи,
  сначала загружает учётки — `DdmailApp.ensureAccounts`); уведомления — те же
  правила тишины (спам, скрытые папки, открытая беседа).
- **Папки диалогов** без ddmail-учётки — локальный документ в том же формате
  (meta `local:dialog_folders`): только системная «Спам», свои папки
  заводятся на десктопе.

### Календарь и контакты внешних учёток (0.0.24)

- **Один календарь и одна книга на всё** (`PimHub`, интерфейс `PimApi`):
  сервер ddmail и CalDAV/CardDAV IMAP-учёток вместе; экраны календаря,
  контактов и напоминания работают с `PimApi` и источника не различают.
  Элементы внешних учёток — с отрицательными id (FNV учётки и ресурса): с
  id сервера не пересекаются, знак решает, куда уходит правка. Задачи — только
  у сервера ddmail (без него в разделе «нет источника»).
- **Обнаружение** (`DavPim.collections`): адрес сам коллекция — она одна;
  иначе `current-user-principal` → `calendar-home-set`/`addressbook-home-set` →
  **все** календари и книги home-set (у десктопа — первый). Права — из
  `current-user-privilege-set`, цвет — `calendar-color`. Адреса находятся при
  добавлении учётки (`PimHub.discover`: `/.well-known/caldav|carddav` и
  `/caldav/`, `/carddav/` на хосте IMAP и домене адреса, вход — паролем
  учётки), правятся в «Изменить» учётки.
- **Чтение** — `REPORT calendar-query` с time-range окна месяца,
  `addressbook-query`; multistatus — DOM-парсер с пространствами имён,
  свойства только со статусом 200. **Часовые пояса** (`Ical`): `TZID` — по
  базе ОС, незнакомое имя (Windows-стиль) — по `VTIMEZONE` календаря,
  плавающее время — в поясе телефона (у десктопа всё «как UTC»); «весь
  день» — полночь UTC, как у сервера; EXDATE, участники, организатор,
  VALARM (`TRIGGER` → минуты каскада напоминаний §13).
- **Запись** — `PUT If-None-Match: *` (новое: `<uuid>@ddmail.ics`, vCard —
  `build_vcard` десктопа), правка — GET, слияние (`Ical.merge`: заменяются
  только переданные свойства мастера, RRULE/участники/будильники и
  переопределения повторов остаются) и `PUT If-Match`; удаление —
  `DELETE If-Match`. 412 — «изменено на сервере». Правка «это и следующие» и
  ответ на приглашение — только у ddmail (как у десктопа), во внешнем
  календаре форма говорит это текстом.
- Сбой одной учётки или коллекции не прячет остальные; 401 — «нужен вход» этой
  учётки.
